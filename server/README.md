# Teamspace API

Run with `node --import tsx server/index.ts`. The process listens on `127.0.0.1:5181` by default; `PORT` changes the port and `TEAMSPACE_DATA_DIR` changes the local `data/` directory. The browser development server proxies `/api` to this process.

`createApp({dataDir, seed})` exports an Express app, `attachWebSocket(httpServer)`, and a `close()` function for isolated tests. Attach WebSocket handling to the same HTTP server before accepting live document clients. Seed data is clearly synthetic and is created only when no projects or users exist. No Jira, Confluence, Plane, or Docmost data is read or modified.

Storage is SQLite WAL with foreign keys, transactions, per-project issue sequences, and JSON for rich content/arrays. Tickets, documents, workflows, and saved views carry monotonically increasing versions. Send `expectedVersion` when patching, restoring, or applying schedules; a stale version returns HTTP 409. Live documents store authoritative Yjs state and a derived JSON snapshot in the same transaction.

Use `X-Actor-Id` to attribute operations to a team member. This identifies the actor and is **not authentication**. The first team member is used when no actor is supplied. This development API must not be exposed as a multi-user authenticated service without adding access controls. Account editing here changes team contact data; there is no email login, verification, SSO, or password system.

## Schedule behavior

Dates may be partial or absent. A start after an end is rejected. Dependencies support FS, SS, FF and SF relationships inside one project and form a directed acyclic graph. Predecessor/successor relationships are distinct from parent/child grouping.

Bulk moves first return a preview and warnings. Working days use each project's calendar (Mon–Fri by default), including explicit nonworking and working-day overrides. Working-day previews return `calendarVersions`; apply checks them when supplied. Direct manual date edits retain their original version checks. Dependency gap warnings use the project working calendar and are scoped to changed projects. Creating or editing a dependency keeps current dates until a schedule change is applied.

Bulk date editing previews up to 100 issues in one project using the submitted issue versions. It accepts absolute start, end and target due dates with per-field keep and clear semantics. The actor-bound proposal checks relevant dependency and rule changes before applying. Retries return the same result, and the shared undo restores each changed due date along with the planned dates. [Bulk date API](../docs/API.md#선택-업무의-날짜-일괄-편집)

Plan moves bind an actor to a preview of the plan dates and eligible linked issue dates. A linked preview checks plan and member versions, dependency endpoints, and relevant settings before applying. The shared schedule undo record carries the applied plan version and previous dates. The plan, issues, audit events, undo record, and retry receipt use one transaction. See the [plan move API](../docs/API.md#계획과-연결-업무-일정-이동).

Manual and automatic apply use one shared mutation hook inside their caller's transaction, including issue validation, per-issue/project history, and undo creation. Undo checks every applied version, refuses if anything changed afterward, and creates new versions instead of rewinding counters. It restores exact prior dates and recomputes warnings with the current calendar. Undo is persisted but does not survive native export/import.

Automatic previews accept `{projectId, issueIds?, anchorDate?, defaultDuration?, seedChanges?}`. They include selected tasks and their successors, preserve working duration, and push unseeded dates later to satisfy start and finish constraints with signed working-day gaps. Explicit seed changes use expected issue versions. The anchor and default duration apply only to fully undated tasks when explicitly supplied; estimates are never treated as duration. Partial/zero-workday periods, missing predecessor anchor dates, fixed completed/cancelled conflicts, and cycles block the whole apply. There is no resource leveling or automatic transition to a completed state.

The server persists a 30-minute actor-bound proposal containing all project issue versions, calendar/workflow/issue-schema versions, dependency fingerprint, and generated dates. `/auto-apply {previewId}` checks them and applies only the stored proposal. A workflow reclassification also invalidates the proposal even when issue versions did not change. Results are retained seven days for idempotent retries. Expired unused proposals and old receipts are pruned on startup/new preview; active proposals are not evicted by a count limit. The current limits are 10,000 project issues, 1,000 changed issues per apply, and 3,650 working days per automatically planned duration. Calendar math supports valid four-digit ISO dates with analytical counts and bounded searches.

Milestones use CAS, owner/date/status and same-project ticket links. Ticket deletion removes current milestone links and increments their versions in the same transaction. Baseline capture requires exact `expectedIssueVersions`, `expectedMilestoneVersions` maps and `expectedCalendarVersion`, then atomically captures every project ticket/milestone and the calendar. Captured values are immutable; only deletion with CAS is supported. Missing historical ticket/milestone IDs remain valid snapshots, while live IDs from another project are rejected. Baseline comparison is between planned dates in calendar days, not actual completion timestamps.

## Schedule slack analysis

`GET /api/projects/:id/schedule-analysis` uses the same calculation as the Gantt. It projects the earliest feasible finish from saved active schedules, task durations, dependency types, signed offsets and the project work calendar. Working backward from that finish gives each task's latest dates and slack in working days. An incomplete connected set reports exclusions while other sets remain available as a partial result. The route also accepts project-scoped API keys through `/api/v1`.

## Project workflows and saved views

Each project starts with six states and all directed transitions allowed. A workflow may rename, reorder, recolor, add, or remove unused states; it must retain a valid initial state. State categories determine completion and overview totals independently of the state ID. Allowed edges may restrict project issue types and require built-in or `custom:fieldId` fields. Additional rules apply required fields by type and destination state. Existing issues are preserved when stricter rules are introduced; their next edit must satisfy the rules. Schedule changes use the same validation.

Workflow PATCH requires `expectedVersion`, `initialStatusId`, `statuses`, `transitions`, and `fieldRules`. Removing an in-use state is rejected. Saved views persist a unique project name, list/board layout, and query/status/assignee/type filters. They are shared team resources; PATCH and DELETE require an expected version. A removed state in a saved filter stays explicit instead of expanding silently to all states.

## Project issue types and custom fields

`GET|PATCH /api/projects/:id/issue-schema` manages one CAS-versioned definition per project. Defaults preserve the original nine Korean type IDs. Type, field, and option IDs remain references when labels change. Types have a name, color, and archive flag. Fields have a name, description, kind, required flag, applicable type IDs (empty means all), option definitions, and archive flag.

Supported kinds are `text`, `number`, `date`, `select`, `multi_select`, `checkbox`, `user`, and `url`. Values live in `Issue.customFields` as an object keyed by field ID. Numbers and booleans remain JSON numbers and booleans; zero and false satisfy required presence. Selections use option IDs, user values use actual team-member IDs, and dates use valid four-digit ISO dates. URL values must use HTTP(S) without embedded credentials and contain at most 4,000 characters. Unknown keys and invalid values fail the mutation rather than being dropped.

PATCH omits `customFields` to preserve values or supplies the entire replacement map. Archived or inapplicable historical values can remain unchanged or be cleared but cannot be assigned afresh. Used field/type/option removal is rejected, and a saved field kind cannot be changed. Referenced workflow rules and saved-view types are also protected. Metadata changes preserve existing nonempty values and do not silently fill required fields; subsequent edits use current definitions. Search uses current type/field/option/user labels, including historical values. Automatic proposals capture the schema version as another stale-plan guard.

A project supports at most 50 types, 100 fields and 200 options per selectable field. Active schemas retain at least one active type and active selectable fields retain at least one active option. Names are unique within each definition list. Fields required by a workflow must be removed from those rules before archiving. Empty stored field keys may be removed together with their definition; affected ticket versions advance to reject stale drafts.

The scoped automation API exposes schema GET and reuses ticket validation for custom values. Definition writes remain on the browser management route; they are not part of the automation allowlist. See [automation examples](../docs/API.md).

## Collaborative documents

Documents retain manual editing until explicitly enabled with the document's current `expectedVersion`. Enabling seeds the Yjs document once from its rich content. Subsequent clients bind only after the server handshake. `shared/collaboration.ts` defines the JSON WebSocket protocol and `shared/editor-schema.ts` defines the common rich document schema.

Clients send a schema version, epoch, and optional Yjs state vector in `hello`. Incoming updates are applied to a candidate Yjs document and validated before commit. The server commits Yjs state, the derived content/plain text, document version, and request receipt together, then acknowledges and broadcasts. Repeated request IDs are idempotent; reusing an ID with different bytes is rejected. A save indicator must use the durable acknowledgment, not socket delivery alone. Updates are limited to 1MiB, rich content to 8MiB, and accumulated Yjs state to 16MiB.

Schema 3 introduced `issueList`. Schema 4 adds `issueSummary`, with status, assignee and priority grouping by project and optional saved view. Startup validates schema 1–3 rooms and upgrades them in one transaction, preserving Yjs bytes, advancing document versions, rotating epochs and clearing old request receipts. Clients can recover pending edits from older schemas as read-only copies. Manual REST edits to an existing summary document require `contentSchemaVersion: 4`. Clients removing the last issue list from a list-only document can send version 3 or 4.

Reconnection merges edits only within the same epoch. REST body replacement, revision restore, and native import rotate epochs and reset open clients. Clients preserve pending old edits for explicit recovery instead of replaying them over restored content. Metadata-only edits keep the epoch. Checkpoints add recoverable document revisions without replacing the live body; revision restore uses the usual version check.

Clients can negotiate ephemeral text cursors with `cursorProtocol: 1` in `hello`. The server confirms the capability and assigns the connection's `peerId` in `welcome`. A `cursor` message carries the current epoch and a selection with Yjs relative anchor and head positions. Each position is canonical base64 with at most 256 decoded bytes. The server forwards updates only within the same negotiated room and epoch, accepts non-null updates at least 50ms apart, and clears the display on explicit null, disconnect, room reset or 30 seconds of inactivity. Focused clients refresh the active position every 10 seconds.

## Planning items

Cycles, modules, and releases have independent project-scoped records, owner, dates, status, and metadata versions. Tickets store canonical `cycleId`, `moduleId`, and `releaseId`; the old `cycle`, `module`, and `release` fields are derived display names. Runtime legacy label requests resolve existing exact names and never create records implicitly. Startup and legacy native import migrate those names, preserving case and whitespace. Startup migration bumps changed issue versions once and is idempotent on reopen.

Names are unique within project and kind using exact binary equality. A rename updates linked display names and issue versions in the same transaction. Metadata changes do not shift ticket schedules or transition their workflow states. Archived plans retain existing links but reject new assignments. Deletion requires `expectedVersion` and no linked tickets. Metadata PATCH uses CAS and cannot change project or kind.

Bulk membership POST accepts `{expectedVersion, assignments: [{issueId, expectedVersion, assigned}]}`. It checks the plan version and every ticket version, then applies shared workflow and required-field validation before writing tickets and audit records atomically. Independent membership edits do not bump the plan metadata version. No-op assignments do not rewrite tickets; an empty request list is rejected.

## Automation API keys

The local browser surface and actor selector remain trusted development features. `/api/v1` requires Bearer keys, enforces read/write and project scope, and binds writes to the key's actor. It exposes the explicit issue/document/comment mutation and lookup surface documented in [API usage](../docs/API.md); unsupported paths cannot fall through to management, export/import, integrations, or collaboration endpoints.

Keys use 32 random bytes. Only SHA-256 digests and public metadata/prefixes are stored; creation returns the secret once. Revocation and expiry reject subsequent requests, including requests authenticated before revocation whose JSON body arrives later. Management create/revoke and audit changes commit together. Last-use metadata does not change the revocation version. Native JSON excludes keys; successful replacement of users revokes all keys through foreign-key cascade, while a failed import restores them with the transaction.

## Document references, includes and history

Rich documents use one canonical editor schema for manual REST writes, revisions, native import and live Yjs updates. Document bodies are limited to 8MiB, 30,000 nodes and 60 levels. Unknown nodes/attributes, invalid reference IDs and malformed structures fail before persistence. Plain text retains stored reference labels/IDs and folded text; it does not materialize another document's live body.

`issueReference` stores `{issueId,label}`. `documentReference` and `documentInclude` store `{documentId,label}`. `documentRevisionInclude` stores `{documentId,revisionId,label}`. `documentExcerptInclude` stores `{documentId,label,noPanel}` and renders the source document's first excerpt. Each is a block atom. `documentExcerpt` wraps one or more rich blocks and stores `hidden`, which controls visibility on the original document's reading surface. `details` contains exactly a `detailsSummary` with inline content and a `detailsContent` with one or more blocks. Fold open and closed state is local to the reader.

References display current workspace titles and statuses, with the saved label and ID as a fallback if a target disappears. Live includes render the last-loaded source snapshot read-only. The UI can refresh references while preserving the current draft. Rendering allows at most five include levels, sixty combined structural levels, and 4,000 expanded nodes across direct include blocks, with an explicit notice at the limit. Live includes must form an acyclic graph. Ordinary references and pinned revision includes can point back to the same document. New missing targets fail validation. Existing missing references can be retained during edits, and historical restore and import allow missing targets. Automation writes check project scope for embedded issue and document targets. Automation document reads return the stored IDs and labels for embedded reference blocks.

Pinned includes load the exact revision from active or archived document history. The server validates the relationship between the source document and revision IDs. The reader shows nested references and dynamic blocks using their stored labels and settings. The inline image route checks that the exact revision references the requested file ID, then checks the bytes using live attachment metadata or the source document’s archived file metadata. External images load from their saved addresses. Permanent deletion of the source makes the pinned revision unavailable. Revision listing, detail, and image routes use the browser API. Individual document JSON format 5 records the pinned IDs. Workspace backups preserve the source history and retained files.

Collaboration protocol 11 adds `documentExcerpt` and `documentExcerptInclude`. Protocol 10 introduced `documentChildList`. Protocol 9 introduced `documentLabelList`. Protocol 8 introduced the `documentToc` block with title-level bounds and list or flat layout. Protocol 7 introduced stable heading section IDs. Startup upgrades rooms from versions 1–10 atomically, preserving Yjs data and history while advancing document versions and rotating epochs. Invalid rooms roll back the migration. Live edits require protocol 10. The browser validates compatible pending caches from versions 1–9 for read-only viewing, download, and explicit recovery as a separate copy. A successful copy removes only the selected cache. Malformed or unknown caches remain downloadable. Native import validates the live include graph, checks the stored revision ownership across active and archived document histories, and verifies that each CRDT state's JSON agrees with the document snapshot. The host document stores the inclusion IDs in Yjs.

History comparison is read-only and accepts any pair of saved revisions or an explicitly labeled current draft. It compares structural signatures and bounded text chunks, including marks, attributes, tables, images and reference IDs. Comparison accepts body JSON up to 8MiB, a separately bounded 64KiB title, 30,000 nodes and 256 structural levels, with a global 250,000-step matching budget and at most 60 displayed rows per page. A bounded algorithm may show a conservative whole gap as removal/addition when its matching budget is reached; both inputs remain reconstructable. Pagination and collapsed unchanged runs bound DOM size without dropping differences. Restore still uses the original expected-version and unsaved/live-pending checks.

Native JSON is not a full SQLite backup and is not a Jira/Confluence importer. Import replaces workspace data and should be used with a prior export. Deleting an issue or document moves it to the trash and detaches its live metadata. Restoration reuses the resource ID and advances its edit version. Parent resources must be restored before children, and permanently deleting a parent with archived children fails.

## Attachments

Each upload is a nonempty raw binary body of at most 20MiB, with a safe filename in the query string. Storage uses generated UUID filenames under private `data/uploads/`; original filenames are never storage paths. Files carry SHA-256 checksums and author/resource metadata. The attachment list advertises a stable grouping ID and a separate current version ID. Appending allocates a new immutable file ID and checks the last observed current version. The append recovery journal keeps the file only if its version row committed. Older links and embedded images keep the bytes addressed by their file IDs. Uploads survive restart. The `X-File-Type` hint is untrusted: MIME metadata comes from content signatures, with unknown files treated as `application/octet-stream`.

Downloads use an encoded Content-Disposition filename and `nosniff`. `?inline=1` is allowed only for signature-checked PNG/JPEG/GIF/WebP; SVG/HTML and unrecognized files cannot be served inline. This checks image container signatures, not full image decoding. Downloads and exports verify stored byte length and checksum. Deleting an attachment moves its metadata and all versions to the item trash and retains their files. Restoring verifies every stored version and preserves its original ID. Permanently deleting the attachment or its parent queues file cleanup in the same transaction. The server resumes any pending cleanup on startup. There is no antivirus or object-storage backend in this development bundle.

## GitLab and transactional webhooks

`GitlabIntegrationService` uses explicitly configured base URL/project IDs, sealed read credentials, legacy secret-token or Standard Webhooks signature authentication, and CAS connection versions. Manual sync performs only read-only GETs (up to1000 MRs and50 pipelines per project) and never runs state automation. Results/errors from an old configuration cannot replace newer settings. Link IDs retain the existing instance prefix; object/branch cursors and link timestamps reject stale incoming metadata.

`jiraRoutes` scopes a GitLab repository to a Teamspace project and a Jira source instance. Matching uses the migrated issue key from preserved source records. If a key names two issues in that project, preview reports the conflict and leaves it unlinked. Saved links keep `originalJiraKey` in native backup format 35. The route itself lives in the local connection settings and travels with physical backups.

With `includeHistory: true`, preview and manual sync verify the numeric GitLab project and scan up to 500 branch rows and 100 recent commits. Match branch names and commit titles/messages against ticket keys, and build links from the configured repository URL. Persist read snapshots with `branchObservationSource: 'sync'` to keep webhook ordering independent from a sampled SHA. Native backup format 28 preserves this field. An authenticated push supersedes a read snapshot using the same link ID, including after a ticket enters the trash or is restored. Repository scans preserve any existing authenticated branch observation. [GitLab branches](https://docs.gitlab.com/api/branches/#list-repository-branches), [GitLab commits](https://docs.gitlab.com/api/commits/#list-repository-commits)

MR open/reopen, merge and close actions and successful/failed pipeline statuses are the five automation triggers. Authenticated push hooks attach a branch by ticket keys in its reference and attach up to 20 included head-push commits by message keys or the branch keys. An accepted head change also updates the branch observation. Deleted branches retain their last confirmed SHA. The receiver follows before/after SHA continuity and retains the last confirmed observation when consecutive changes are missing. Events need valid object IDs/timestamps; stale, equal-time conflicting, missing-time and pre-activation events cannot mutate status. Newer pipeline IDs on a branch prevent late older results from changing current intent. Pipeline inheritance from stored MR links requires matching branch and head SHA. `AutomationService` chooses the first matching priority/id rule per issue without chaining; current workflow/type/required-field rules apply, and validation failure logs blocked without a fallback rule. No-op results advance event ordering without changing issue versions. Unexpected audit/persistence errors roll back the whole webhook transaction.

Authenticated deployment hooks persist the lifecycle state and full commit SHA for each instance, project, and deployment ID. Explicit repository sync uses the verified Deployments API to read up to 50 recent records and up to 200 confirmed merge requests per successful deployment. The transaction preserves a webhook observed during the read and applies positive association evidence for the same artifact. Teamspace joins that evidence to existing links by instance, project, MR ID, and IID. Repository history uses the current saved instance and project. Ticket history derives exact revision matches from stored commits, pipelines, or verified merged MR commit and squash SHAs. The browser and scoped automation API expose read-only ticket history through `/api/issues/:id/gitlab-deployments` and `/api/v1/issues/:id/gitlab-deployments`. [GitLab deployment event](https://docs.gitlab.com/user/project/integrations/webhook_events/#deployment-events)

`Store.onChange` runs filtered synchronous listeners inside domain transactions, wrapping observed standalone writes in a transaction. AsyncLocalStorage carries actor/origin/source-event context for HTTP, API-key and collaboration writes. `OutboundWebhookService` stores minimal issue/document/comment envelopes and matching deliveries atomically; it omits raw bodies, comments, custom values and credentials. Seven event types and project scopes are configured on explicitly enabled destinations. Imported writes and semantic no-ops emit no events.

The leased worker claims up to4 deliveries, signs exact persisted bytes, forbids redirects, applies a10-second timeout and retries automatically at most5 times with exponential delay. It provides at-least-once delivery: receivers deduplicate stable event IDs. Configuration-version, owner-lease and import-generation checks reject late completions after disable/rotation/import/restart. Closing releases owned leases and aborts before DB closure. Terminal records expire after30 days; a50000-row backlog cap rejects the canonical write atomically instead of silently dropping an event. Destinations, secrets and delivery history are excluded from native JSON and cleared on successful import. Detailed routes and signing contract are in [API usage](../docs/API.md).

GitLab payload/authentication formats follow the [official webhook documentation](https://docs.gitlab.com/user/project/integrations/webhooks/) and [event definitions](https://docs.gitlab.com/user/project/integrations/webhook_events/). Tests use local mock GitLab and receiver servers; production connectivity and automatic webhook registration are not implemented or verified.

## Offline legacy-source analysis

`LegacyImportService` provides `/api/legacy-import/packages` on the trusted browser management surface; API keys cannot access it. It accepts raw XML/CSV/JSON/ZIP uploads with an explicit source-instance namespace. Actual parsing runs in one bounded worker thread, keeping the main API available. No external attachment downloads or writes to current users/projects/issues/documents occur. Use the migration API to map and apply analyzed packages.

`legacy-import-archive.ts` validates UTF decoding, strict XML structure and rejection of DTD/custom entity declarations, central-directory paths/types/duplicates, expanded byte limits and CRC/SHA integrity without extracting arbitrary paths. Limits are64MiB input/member,256MiB expansion,5000 files, XML depth128/500000 nodes,100000 normalized records and10000 diagnostics. Individual text is capped at16MiB and normalized output at128MiB. Unsupported or excessive input fails explicitly rather than dropping bytes. The archive and full source text remain private; only allowlisted platform data enters normalized records. Jira administrator XML, search RSS XML, repeated-header CSV and REST/Importers JSON have distinct adapters and partial-export diagnostics. Recognized content restrictions block applying the affected records unless explicitly excluded. Source permissions require separate review. Only synthetic fixtures have been exercised, including pre-8.1 and versioned Confluence attachment layouts.

Original bytes are flushed as a0600 pending file under0700 `data/legacy-imports`; successful analysis writes records/diagnostics/manifest/audit in one SQLite transaction and moves the original to its bundle name before commit. ## Applying legacy packages

The migration service builds a server-side plan on a worker thread using the analyzed dataset, selected mappings and verified input files. The 30-minute preview binds the requesting actor, workspace generation, package hashes and generated record IDs. Apply rechecks the preview and files, requires acknowledgement of specific conversion notices and commits only newly allocated project records. Source IDs and Jira keys are bound to their targets, and a retry of the same apply request returns the committed receipt. Applied receipts keep the reviewed notices and original normalized records, independently of the analysis uploads.

A configured package base also lets the worker prepare an Atlassian link for each eligible Jira issue or Confluence page. It uses the original Jira key or page ID and validates the resulting browser address offline with the existing link parser. Apply stores the reviewed links in the canonical transaction. The receipt retains the original link counts and omission notices. Schema 27 native backup and physical backup preserve the saved links.

A separate append journal covers new attachment files. Stage writes use generated UUIDs. Installation takes place in the SQLite transaction and the applied receipt is its recovery marker. Startup reconciles uncommitted journal files with the receipt and removes leftover temporary stages. This append path shares the attachment integrity and download checks with the existing workspace. The normal backup retains historical attachment files and verifies them during restore.

Confluence storage XML, Jira wiki, ADF and plaintext use the same editor schema as existing documents. Unsupported content uses visible fallbacks with review notices. References resolve against the opted-in packages using source IDs, titles and configured source base URLs. Issue relations have their own records. An imported Jira link does not create a scheduling dependency.


## Project reporting

The reporting ledger observes issue and workflow writes in the same SQLite transaction as the canonical change. It stores the report-relevant before and after fields with event source, actor, workflow version, collection epoch and sequence. The first run and successful legacy migration record existing records as baselines. A native export closes the current epoch in the package. A native restore keeps validated closed epochs from the package, begins a new epoch and records restored issues as a baseline. A failed restore rolls back the reporting state, snapshots and workspace together.

Date boundaries use the requested IANA zone. Reports expose current status and due metrics alongside actual period transitions, separate workflow reclassifications and daily coverage. The snapshot endpoint recalculates at capture time and stores the immutable result, editable weekly draft, revision and issue links atomically. See [local reporting routes](../docs/API.md#프로젝트-보고서와-주간-문서).


## Spreadsheet schedule paste

Paste resolves headed CSV or TSV against the current project's unique ticket keys. A blank date leaves the stored date in place. A hyphen clears it. A row can also add, update, or remove the connection between its successor key and a specified predecessor key. The server checks the projected graph for cycles when the paste adds a relationship. A successful preview stores normalized changes and a read guard for referenced and directly linked tickets, incident dependencies, workflow, field schema and calendar. The apply transaction checks that guard and revalidates the graph. It commits dates, connections, audit entries, the shared undo record and the idempotent response together. Undo checks for changed connections and cycles before restoring. Native restore clears proposals, receipts and undo records. The [paste API](../docs/API.md#스프레드시트-일정-붙여넣기) documents sizes and retention.


## Actual work time

Time entries record an explicit calendar date, integer minutes, author and an optional note. Author checks and CAS apply to edits and deletes. Creating with the same request ID and payload returns the original entry or its current version without creating another. Deleted records retain their ID and request fingerprint and clear their note. Deleting a ticket preserves its time in project reports, using the captured issue key and title when the ticket is unavailable. Entry mutations and activity records share a transaction and leave the ticket version untouched. The same routes are available under the scoped automation API. See the [work time API](../docs/API.md#티켓과-프로젝트-작업-시간).


Jira worklogs are promoted during reviewed migration when the owning issue, mapped author, local work date and duration are known. The original metadata is kept in the source archive. Restricted worklogs block migration until the record is explicitly excluded. Archive-only worklogs require review when authors or time fields cannot be mapped. Imported worklogs, source records, issues and migration receipts are written in one transaction.
