# 업무 상세 화면 개편 설계

작성일: 2026-11-27 · 상태: 승인됨(2026-11-27)

## 의도

업무(티켓) 상세 화면을 Plane의 업무 화면처럼 단순하게 바꾼다. 본문을 글처럼 크게 읽고 쓰는 화면이 중심이 되고, 속성은 옆으로 비켜서 필요할 때만 본다. 본문은 Markdown을 기본으로 하고, 편집할 때는 쓰는 대로 서식이 보인다. 저장 버튼을 누르지 않아도 바꾼 내용이 바로 저장된다.

지금 화면은 690px 서랍 안에 제목 입력칸, 평문/Markdown을 고르는 설명 입력칸, 속성 16개짜리 2열 폼, 저장 버튼이 있다. 그 아래로 이정표·의존성·하위 업무·연결 문서·GitLab·자동화 이력·첨부·댓글·삭제 영역이 항상 이어지고, 상단 탭 5개(상세 정보·변경 이력·작업 시간·시간 배정·원본 기록)가 따로 있다. 사용자는 이 화면이 복잡하다고 느낀다.

참고 화면: Plane 업무 상세(왼쪽 본문, 오른쪽 Properties 칸, 본문 아래 버튼 한 줄, Activity와 댓글).

## 목표

1. 화면을 본문 영역과 속성 칸으로 나눈다. 속성 칸은 오른쪽에 두고 접었다 펼 수 있다.
2. 속성 칸을 접으면 제목 아래에 핵심 속성 요약 칩 한 줄이 나타난다(사용자 선택: 시안 B).
3. 본문은 Markdown으로 저장하고, 문서 화면과 같은 편집기(TipTap)에서 쓰는 대로 서식이 보이게 편집한다.
4. 속성은 바꾸는 즉시 저장한다. 제목·본문은 입력을 멈추면 자동 저장한다. 저장 버튼을 없앤다.
5. 의존성·하위 업무·업무 관계·문서 연결·첨부는 본문 아래 버튼 한 줄로 시작하고, 내용이 있는 섹션만 화면에 나타난다.
6. 변경 이력·작업 시간·시간 배정·원본 기록은 본문 아래 활동 영역의 탭으로 옮긴다. 댓글은 활동 영역의 기본 탭이다.

## 비목표

- 업무 본문의 실시간 공동 편집. 문서 화면에는 있지만 이번에는 넣지 않는다.
- 업무 설명의 저장 형식 변경. 설명은 계속 Markdown(또는 기존 평문) 문자열이다.
- 해시 주소 변경. `#/{project}/issues?issue={id}`와 기존 쿼리(`gitlab`, 검토 순서 등)는 그대로 열린다.
- 새 업무 만들기 대화상자, 목록·보드·간트 화면의 개편.
- 사용자 정의 필드, 일정 편집 대화상자 등 기존 하위 기능의 동작 변경. 위치만 옮긴다.

## 반목표 (기술적으로 동작해도 실패로 보는 것)

- 저장하지 않은 입력이 조용히 사라지는 것. 즉시 저장 중 오류·충돌·새로고침·탭 닫기에서도 내 입력은 남아야 한다.
- 다른 사람의 변경을 모르고 덮어쓰는 것. 버전 충돌 검사는 유지한다.
- 속성 하나 바꿀 때마다 화면이 깜빡이거나 입력 포커스를 잃는 것.
- 기존 평문 설명의 `*`, `#`, `1.` 같은 글자가 열기만 해도 서식으로 바뀌어 보이는 것.
- 360px 모바일 폭에서 쓸 수 없게 되는 것. 기존 브라우저 검사 다수가 360px에서 동작을 확인한다.

## 제약

- `AGENTS.md`: 업무는 서버 저장소가 원본이고, 브라우저 저장소는 보기 설정과 미저장 초안에만 쓴다. 변경은 버전 충돌을 검사하고 미저장 내용을 버리지 않는다. 색·글자 크기는 의미 토큰만 쓰고, 새 요소는 Tailwind 유틸리티와 `src/components/ui`의 shadcn 컴포넌트로 만든다. 아이콘은 `lucide-react`를 쓴다.
- 서버 `PATCH /api/issues/:id`는 일부 필드만 보내는 수정, `expectedVersion` 충돌 검사, `requestId` 재시도 응답 재사용을 이미 지원한다. 즉시 저장은 이 API를 그대로 쓴다. 상태 변경은 워크플로 전이 규칙·필수 속성·차단 관계 검사와 GitLab 상태 제안 토큰 검증이 붙어 있으므로 같은 경로로 보낸다.
- 문서 화면에는 Markdown ↔ 편집기 형식 변환기가 있다(`shared/document-markdown-import.ts`, `shared/document-export-markdown.ts`의 `renderTicketDescriptionMarkdown`). 업무 본문 편집기는 이것을 재사용한다.
- 업무 상세를 여는 브라우저 검사가 59개이고, 그중 40개가 저장 버튼을 누른다. 저장 방식이 바뀌므로 이 검사들도 함께 고친다.
- 업무 상세는 `role="dialog"` 오버레이이며 포커스 가두기, 닫기 전 미저장 확인, 검토 순서 이동(이전·다음 업무)이 있다.

## 고려한 방식

**화면 여는 방식**
- (선택) 기존 `?issue=` 오버레이를 유지하고 폭을 넓힌다. 주소가 그대로이고 목록·보드로 돌아가는 흐름이 유지된다.
- 별도 전체 페이지 주소를 만든다. 해시 주소를 바꾸지 말라는 규칙과 맞지 않고, 기존 링크·검사가 모두 바뀌어 제외했다.

**본문 편집기와 저장 형식**
- (선택) A. Markdown 문자열로 저장하고 편집만 문서 편집기로 한다. API·이관·검색·GitLab 연동·외부 API 키 사용자가 그대로다. 대신 Markdown으로 표현하지 못하는 블록(색, 열 배치, 문서 속성 블록 등)은 업무 본문에서 쓰지 않는다.
- B. 문서처럼 편집기 형식(JSON)으로 저장한다. 문서 블록을 모두 쓸 수 있지만 업무 설명의 데이터 계약이 바뀌어 이관·검색·내보내기·API를 모두 고쳐야 하고, "Markdown 기본"이라는 요청과 어긋나 제외했다.

**저장 방식**
- (선택) 속성은 즉시 저장, 제목·본문은 입력이 멈춘 뒤 자동 저장, 충돌 시 내 입력을 유지한 채 안내. 기존 API 위에서 동작한다.
- 실시간 공동 편집(Yjs). 문서 화면의 구조를 업무로 옮기는 큰 작업이라 이번 범위에서 제외했다.

사용자는 세 영역 모두 추천안을 골랐다.

## 결정된 설계

### 화면 구성

- 오버레이 폭: 넓은 화면에서 최대 약 1200px(뷰포트 대부분). 머리줄에는 경로(프로젝트 › 업무 › 키)와 오른쪽에 구독·즐겨찾기·업무 복제·프로젝트 이동·속성 접기·닫기를 둔다. 자주 쓰지 않는 동작(복제·이동·휴지통 이동)은 더보기 메뉴로 모아도 된다.
- 본문 영역(왼쪽, 남은 폭): 업무 키·유형, 제목, 상위 업무 링크, 본문 편집기, "마지막 저장" 상태 줄, 기능 버튼 한 줄, 내용이 있는 관련 섹션, 활동 영역.
- 속성 칸(오른쪽, 약 260px): 속성을 "이름 · 값" 한 줄씩 보여 주고, 값을 누르면 그 자리에서 고른다(선택 목록·날짜 선택·사람 선택). 기본으로 보이는 속성은 상태·담당자·우선순위·시작일·종료일·목표 마감일·사이클·상위 업무·라벨·참여자다. 나머지(유형·요청자·모듈·릴리스·예상 소요·계획 작업 시간·사용자 정의 필드)는 "속성 더 보기"로 펼친다. 일정 관련 버튼(일정과 연결 편집, 간트에서 보기, 프로젝트 간 일정 검토, 되돌리기)과 일정 경고는 날짜 속성 아래에 둔다.
- 속성 칸 접기: 머리줄 버튼으로 접고 펴며, 상태는 브라우저 보기 설정으로 기억한다. 접으면 제목 아래에 요약 칩(상태·담당자·우선순위·기간·사이클)이 나타나고, 칩을 누르면 그 속성을 바로 바꿀 수 있다.
- 좁은 화면(속성 칸과 본문이 함께 들어가지 않는 폭, 360px 포함): 오버레이가 전체 화면이 되고, 속성 칸은 항상 접힌 상태(요약 칩)로 시작한다. 펼치면 칩 아래에 속성 목록이 세로로 나온다.

### 기능 버튼과 관련 섹션

- 버튼 한 줄: 하위 업무 추가, 업무 관계 추가, 의존성 추가, 문서 연결, 첨부. 각 버튼은 지금 섹션 안에 있던 추가 흐름(대화상자·검색)을 그대로 연다.
- 섹션은 내용이 있을 때만 보인다: 연결된 이정표, 업무 의존성, 하위 업무, 업무 관계, 연결된 문서(결정 근거 포함), 본문에서 참조한 문서, GitLab 활동, 자동화 이력, 첨부. 버튼으로 추가를 시작하면 내용이 없어도 해당 섹션이 열린다.
- 휴지통 이동은 더보기 메뉴로 옮긴다. 확인 흐름은 지금과 같다.

### 활동 영역

- 탭: 댓글(기본) · 변경 이력 · 작업 시간 · 시간 배정 · 원본 기록. 상단에 있던 탭 5개를 여기로 옮기고, 기존 탭 내용 컴포넌트를 그대로 넣는다.
- 탭은 화면을 다시 그려도 입력 중인 댓글·작업 시간 초안을 잃지 않아야 한다. 지금처럼 숨겨도 마운트를 유지하거나 기존 초안 저장을 쓴다.

### 본문 편집기

- 문서 화면의 TipTap 편집기 구성을 재사용하되, 업무 본문에서 허용하는 블록은 Markdown으로 왕복 가능한 것으로 제한한다: 문단, 제목(h1~h3), 굵게·기울임·취소선·인라인 코드, 링크, 글머리·번호 목록, 체크리스트, 인용, 코드 블록, 표, 이미지, 구분선.
- 이미지(사용자 결정): 이미지를 붙여넣거나 끌어다 놓으면 업무 첨부로 올리고 본문에 그 첨부를 가리키는 이미지로 넣는다. 업로드 중에는 자리 표시를 보여 주고, 업로드가 끝나기 전에는 본문 자동 저장을 미룬다. 업로드가 실패하면 자리 표시를 오류 상태로 바꾸고 다시 시도·삭제를 고르게 하며, 본문에 깨진 링크를 저장하지 않는다.
- 입력 규칙: `# `, `## `, `- `, `1. `, `[ ] `, `> `, ```` ``` ```` 등 Markdown 입력이 바로 서식으로 바뀐다. 슬래시 명령과 서식 도구 모음은 문서 화면과 같은 방식으로 허용 블록만 보여 준다.
- 불러오기: 저장된 Markdown을 문서 변환기로 편집기 형식으로 바꿔 연다. 저장: 편집기 내용을 `renderTicketDescriptionMarkdown`으로 Markdown 문자열로 바꿔 보낸다. 변경이 없으면 같은 문자열이 나와야 한다(왕복 안정성).
- 기존 평문 설명(`descriptionFormat` 없음 또는 `plain`): 줄바꿈을 문단으로, 나머지 글자는 그대로 보이게(이스케이프) 편집기에 연다. 사용자가 본문을 처음 고쳐 저장할 때 `descriptionFormat: 'markdown'`과 이스케이프된 Markdown으로 저장한다. 고치지 않으면 저장 형식을 바꾸지 않는다.
- 왕복이 깨지는 기존 Markdown(설계자 결정): 이관한 Jira 설명처럼 편집기가 만든 형식이 아닌 Markdown(HTML 조각, `<details>`, 각주, 다른 목록 기호·간격 등)은 불러온 뒤 다시 내보내면 글자가 달라질 수 있다. 열 때 "불러오기 → 내보내기" 결과가 원문과 같은지 확인하고, 다르면 그 업무는 서식 편집기 대신 Markdown 원문 편집칸과 미리보기로 열고 "이 설명은 원문 형식을 보존하기 위해 Markdown으로 편집합니다"를 알린다. 사용자가 서식 편집기로 바꾸겠다고 고르면 그때 정규화된 형식으로 저장한다. 내용이 조용히 다시 쓰이거나 사라지지 않게 하기 위함이다.
- Confluence 이관 원본 링크(`migratedDocuments`)처럼 지금 미리보기에서 제공하던 동작은 편집기 링크 동작으로 유지한다.
- 평문/Markdown 선택 상자와 편집·미리보기 전환은 없앤다. 새 업무의 기본 형식은 Markdown이다.

### 저장 방식

- 속성: 값을 고르는 즉시 그 필드만 `PATCH`로 보낸다(`expectedVersion`, `requestId` 포함). 저장 중에는 해당 속성에 진행 표시를 하고, 실패하면 값을 되돌리지 않은 채 오류와 다시 시도를 보여 준다. 응답이 끊기면 같은 `requestId`로 결과를 확인한다.
- 같은 업무에 대한 저장 요청은 순서대로 보낸다. 앞 요청의 응답 버전을 다음 요청의 `expectedVersion`으로 쓴다.
- 제목·본문: 입력이 약 1초 멈추면 자동 저장한다. 포커스를 벗어나거나 업무를 닫거나 다른 업무로 이동할 때도 즉시 저장을 시도한다. 저장 전 내용은 브라우저 저장소에 업무·작업자별 초안으로 보관하고, 서버 저장이 확인되면 지운다. 새로고침 후 초안이 남아 있으면 복원하고 "저장하지 않은 본문을 복원했습니다"를 알린다.
- 병합 단위(설계자 결정): 사용자 정의 필드는 필드 ID마다 별도 필드로 본다. 라벨·참여자 같은 목록은 목록 전체를 한 필드로 보아, 양쪽이 모두 바꿨으면 충돌 안내를 띄운다. 서버는 409와 현재 버전만 돌려주므로, 클라이언트가 편집 시작 시점의 업무를 기준으로 비교한다.
- 충돌: 서버 버전이 내가 편집을 시작한 버전보다 높으면 필드 단위로 판단한다. 다른 사람이 바꾼 필드가 내가 바꾸려는 필드와 다르면 최신 버전 위에 내 변경만 다시 보낸다. 같은 필드(특히 본문)를 바꿨으면 내 입력을 유지한 채 "다른 사람의 변경사항이 있습니다" 안내를 띄우고 최신 내용 보기·내 내용으로 덮어쓰기를 고르게 한다.
- 상태와 필수 속성(설계자 결정): 서버는 상태를 바꿀 때 새 상태의 필수 속성을 같은 요청에서 검사하고, 현재 표시 조건에서 숨은 사용자 정의 필드는 받지 않는다. 그래서 새 상태에서만 보이거나 필수인 속성이 있으면 상태를 고른 순간 작은 "필수 속성 입력" 단계를 상태 옆에 열고, 입력을 마치면 상태와 그 속성을 한 요청으로 보낸다. 취소하면 상태는 바뀌지 않는다.
- 상태 변경: 워크플로 전이 거부, 필수 속성 누락, 차단 업무 오류는 지금 오류 안내(차단 업무 보기 버튼 포함)를 속성 칸 상태 옆에 보여 준다. 일정 저장 검토(`IssueScheduleSaveReview`)처럼 저장 전에 확인이 필요한 흐름은 날짜를 바꾼 순간 같은 검토 대화상자를 연다.
- "마지막 저장 · 방금 전 / 저장 중 / 저장하지 못함" 상태를 본문 아래에 보여 준다.
- 닫기·검토 순서 이동: 저장 중이거나 저장하지 못한 내용이 있으면 지금처럼 확인을 받는다. 저장이 끝났으면 바로 닫는다.

### 검증

- 단위 테스트: Markdown 왕복 안정성(허용 블록별), 평문 이스케이프 변환, 필드 단위 충돌 병합 규칙, 저장 요청 순서화.
- 브라우저 검사: 기존 업무 상세 검사 59개를 새 구조(즉시 저장, 속성 칸, 활동 탭)에 맞게 고친다. 새 검사로 속성 칸 접기·펴기와 기억, 요약 칩 수정, 360px 레이아웃, 즉시 저장 중 응답 유실 재시도, 본문 자동 저장과 새로고침 후 초안 복원, 같은 필드 충돌 안내, 평문 설명을 열어도 글자가 바뀌지 않음을 확인한다.
- `npm test`, `npm run typecheck`, `npm run build`, 관련 브라우저 검사를 통과한다.

## 구현자에게 맡기는 것

이 문서가 정하지 않은 동작이 애매하면 Plane 또는 Notion의 방식을 따른다(사용자 지시).


- 오버레이의 정확한 폭·여백, 속성 칸 폭(260px 안팎), 좁은 화면 전환 기준 폭.
- 속성 값 선택 UI의 세부 컴포넌트(shadcn Popover·Command 등) 선택.
- 자동 저장 대기 시간(1초 안팎)과 저장 상태 문구.
- 편집기 구성을 문서 화면과 공유하는 방법. 문서 편집기는 공동 편집(`CollaborativeEditor.tsx`) 중심이라 그대로 가져다 쓸 수 없고, 허용 블록만 담은 비공동 편집용 확장 목록을 따로 만들어야 한다.
- 작업 순서와 단계 나누기. 검사 수정량이 크므로 단계별로 검사를 통과하며 진행한다.
