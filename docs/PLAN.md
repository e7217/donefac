# Teamspace 개발 계획

목표는 Jira·Confluence의 핵심 업무를 대체하고 Plane·Docmost의 빠른 입력·보기·문서 편집 방식을 반영한 독립적인 팀 프로젝트·지식 관리 제품이다. 초기 사용자는 20명 이하이다. 복잡한 보안, SSO, 기업용 계정 관리 기능은 현재 범위에서 제외한다. 기존 Jira/Confluence/Docmost/Plane 운영 데이터와 서비스는 변경하지 않는다.

## 제품 범위

- 팀 개요: 프로젝트·팀원·기준일 필터와 열린 업무 집계, 가까운 마감, 문서 검토 대기, 최근 GitLab 활동, 당일 시간 배정과 원래 항목 열기.
- 티켓: 기본 9개와 사용자 정의 유형, 담당자·협력자, 상태·전이, 우선순위, 프로젝트별 업무 순서, 계층·연관, 댓글·첨부, 실제 작업 시간 기록·집계, 사용자 정의 필드·유형별 필수 입력, 변경 이력, 검색·필드 조건·저장 보기.
- 계획: 목록·보드·간트에서 같은 티켓 사용, 인라인 일정 입력·수정, 스프레드시트에서 날짜와 선후행 연결 붙여넣기, FS·SS·FF·SF 연결과 근무일 간격, 다중 일정 이동·되돌리기, 마일스톤·달력·기준 계획, 팀원별 시간 배정과 프로젝트 간 겹침 검사.
- 지식: 문서 트리, 서식 편집·표·체크리스트·코드·이미지, 문서/티켓 참조, 템플릿, 버전 이력·복구, 댓글·검색, 공동 편집.
- GitLab: 저장소·브랜치·MR·커밋·파이프라인 연결, 검증된 웹훅·재동기화, 명시적 상태 자동화.
- API·자동화: 공개 API 계약, 개인/자동화용 API 키 발급·회수, 외부 웹훅과 도구 연결. 복잡한 계정 체계와 별도로 간단한 연동 수단을 제공한다.
- 데이터: 실제 서버 저장, 버전 충돌 검사, 문서·티켓·관계 내보내기, 기존 도구 이관, 백업·복원.
- 팀: 간단한 팀원 관리·작업자 기록, 담당자 배정·댓글·문서 검토 알림, 업무·문서·프로젝트 업무·문서 공간 구독. SSO와 복잡한 권한 엔진은 제외.

## 구현 원칙

하나의 저장소에서 웹 UI, 독립 API, 공통 타입을 관리한다. 초기 로컬 개발은 Node 24와 SQLite WAL을 사용하며 UI의 localStorage를 데이터 원본으로 사용하지 않는다. 저장 형식·API·일정 규칙은 참고 제품이나 화면 라이브러리에 종속시키지 않는다. 기존 설계의 PostgreSQL 도입은 규모·운영 요구 검증 후 판단한다.

파일럿은 빌드한 정적 웹, SQLite API와 공동 편집을 단일 루프백 주소로 실행한다. 팀 접속은 HTTPS 프록시 뒤에서 공용 키로 브라우저 세션을 열고, 각 작업자는 앱에서 선택한다. GitLab 웹훅과 개인 API 키는 각각의 자격 증명으로 요청한다. 물리 백업은 파일럿과 같은 데이터 잠금을 사용해 식별 키, 첨부, 이관 원본과 저장소를 함께 보관한다. 별도 데이터 경로로 복원하고 실제 브라우저와 로컬 모의 GitLab을 사용하는 합성 리허설로 확인한다. 실제 팀 접속 경로 및 운영 데이터 적용은 환경이 정해진 뒤 검증한다.

20명 합성 리허설은 20개의 브라우저 컨텍스트에서 공동 편집과 티켓·간트 사용을 함께 실행한다. 같은 편집 세대로의 재접속, 복원 이후 이전 편집의 사본 저장, 프로세스 재시작과 별도 경로 복원 뒤의 문서 일치를 검증한다.

업무와 문서의 첨부는 고정 ID를 유지하고 각 파일 버전의 바이트를 따로 보관한다. 목록에서 최신 파일을 선택하고 이력에서 당시 파일을 내려받는다. 문서에 삽입한 이미지는 저장 당시 파일 ID를 참조한다. 버전 추가는 확인한 최신 ID가 여전히 일치할 때 진행하며, 파일과 메타데이터는 장애 후 복구할 수 있도록 함께 반영한다. 자체 JSON과 파일럿 전체 백업에 이력을 포함한다.

업무와 문서를 휴지통으로 보내면 일반 조회·검색에서 사라지고 댓글·첨부 버전·연결과 문서 이력을 함께 보관한다. 복원은 원래 ID와 업무 키를 유지하며 편집 버전과 공동 편집 세대를 갱신한다. 상위 항목을 먼저 복원하고, 상대가 아직 휴지통에 있는 연결은 두 항목이 모두 돌아올 때 복원을 시도한다. 새 생성과 복원을 보고서에서 구분한다. 보관본은 전체 백업에 포함하며 휴지통에서 별도로 영구 삭제할 수 있다.

작성자는 개별 댓글을 휴지통에 보낼 수 있다. 댓글은 본문·작성자·작성 시각과 원래 ID를 보존하며 복원 후 작성 시각순으로 표시한다. 첨부파일은 최신 버전을 확인한 뒤 원본 및 모든 버전의 메타데이터와 바이트를 보존한다. 파일 복원 전에 각 버전의 크기와 SHA-256을 검사한다. 원래 업무·문서를 먼저 복원하고 개별 항목을 이어서 복원한다. 상위 항목을 영구 삭제하면 개별 휴지통 항목까지 지우며, 중단된 파일 정리는 재시작 후 이어진다. 자체 백업 형식 31과 전체 데이터 백업은 개별 휴지통을 포함한다.

공동 편집 문서는 Yjs 상태를 원본으로 삼고 JSON·검색용 평문을 같은 트랜잭션에서 생성한다. 복구·가져오기는 편집 세대를 바꾸어 오래된 오프라인 편집을 분리한다. 문서 참조는 ID를 유지하고 최신 원문을 가리키는 포함 본문은 읽기 전용으로 표시한다. 최신 원문 포함 관계의 순환은 저장·복원·가져오기·공동 편집에서 같은 규칙으로 거절한다. 이력 비교는 제목·본문과 서식·속성·블록 구조를 보존하며, 대규모 비교도 유한한 계산량으로 수행한다.

문서 목차는 편집기의 현재 본문 또는 읽기 화면에서 선택한 저장본의 제목을 순서대로 나열한다. 반복된 제목은 순서로 구별하고, 접힌 블록의 제목은 그 절의 상위 블록을 열어 이동한다. 포함 문서의 제목은 해당 원문 목차의 범위다. 목차 이동과 펼치기는 현재 브라우저에서만 적용한다.

결정 기록과 설계 검토에서는 포함할 원본의 이력 ID를 지정한다. 편집기·이력·검토본·발행본에서 해당 저장본을 펼칠 수 있다. 저장본 안의 동적 블록은 당시 저장한 이름을 표시한다. 전체 백업 형식 26에 고정 포함 ID와 원본의 활성·휴지통 이력을 보존한다. 공동 편집 프로토콜 5는 기존 형식 1~4의 Yjs 데이터를 보존한 채 편집 세대를 갱신한다. [Confluence의 페이지 이력과 버전 비교](https://confluence.atlassian.com/doc/page-history-and-page-comparison-views-139379.html)

공동 편집의 커서와 텍스트 선택은 Yjs 상대 위치로 공유하고, 같은 문서와 편집 세대의 수신자가 화면에 표시한다. 서버가 접속자 정보를 제공하고 브라우저가 그 위치를 현재 편집기에 연결한다. 본문 저장과 커서 통신은 별도로 처리하며, 본문 변경을 저장한 뒤 새 위치를 보내고 연결 종료나 유효 시간 만료 시 표시를 지운다.

문서 업무 목록은 프로젝트와 선택한 공유 보기의 ID를 저장한다. 편집 화면에서는 보기의 필터를 적용한 현재 업무와 상태·담당자를 최대 20개까지 보여주며 원래 업무를 열 수 있다. 이력과 검토·발행본에는 당시 저장된 목록 설정을 보존한다. 공유 보기가 삭제되면 그 설정의 이름과 오류를 표시한다.

문서 업무 현황은 같은 공유 보기 조건으로 업무를 상태·담당자·우선순위 중 하나로 묶는다. 편집 화면에서 개수와 비율을 읽고 그룹을 펼쳐 실제 티켓을 연다. 현재 수치는 업무 데이터를 갱신할 때 다시 계산한다. 이력과 검토·발행본에는 저장한 범위와 집계 기준을 보존한다.

회의록과 결정 문서의 연결 화면에서 후속 업무를 만든다. 프로젝트 문서는 현재 프로젝트에 연결하고 공통 문서는 사용자가 프로젝트를 선택한다. 기존 업무 양식과 필수 속성을 적용한다. 문서 버전을 확인한 뒤 업무와 연결을 한 번에 저장하며, 응답 유실 시 요청 ID로 같은 결과를 다시 확인한다. 작성 중인 문서에서는 본문과 댓글 초안을 유지한다.

저장되거나 동기화된 본문의 문장을 티켓의 결정 근거로 연결한다. 서버는 요청의 문서 버전과 선택 범위를 대조해 원문을 구하고, 당시 저장본 ID를 티켓 연결에 기록한다. 공동 편집에서 해당 버전의 이력이 필요하면 티켓을 만드는 트랜잭션에서 기록한다. 티켓에서 발췌와 당시 저장본을 읽고, 자체 백업은 활성·휴지통 연결의 발췌와 원문을 대조해 복원한다.

문서 검토는 요청 당시 서버 저장본을 이력 ID로 고정한다. 지정한 팀원은 발행하거나 수정을 요청하고, 요청자는 철회할 수 있다. 발행 상태는 최신 승인 저장본을 가리키며 편집기는 이후 초안을 계속 저장할 수 있다. 승인 저장본의 제목·본문과 결정 메모는 백업에 보존한다. 작업자별 검토함·요청함과 프로젝트별 발행본 목록에서 고정된 이력을 연다. 상단에 배정된 대기 건수를 표시한다.

팀 알림은 변경과 같은 트랜잭션에 수신자별로 저장한다. 담당자 변경, 업무·문서 댓글과 문서 검토·수정 요청·발행·철회를 알린다. 사용자 본인과 중복 수신자는 제외한다. 알림에서 대상에 이동하고 읽음 여부를 저장한다. 모두 읽음은 목록의 첫 알림까지 적용하여 이후 도착한 알림을 보존한다. 자체 JSON 백업의 15번 형식부터 알림과 읽음 시각을 포함한다.

개인 구독은 업무의 상태 변경·댓글과 문서의 저장·이력 복구·발행·댓글을 앱 알림으로 전달한다. 실시간 공동 편집은 새 버전 기록을 만들 때 구독자에게 알린다. 구독은 작업자·대상별로 관리하며, 휴지통에서 대상을 복원하면 다시 적용한다. 자체 JSON 백업의 25번 형식에 구독과 새 알림을 보존한다. [Jira 업무 구독](https://support.atlassian.com/jira-software-cloud/docs/watch-share-and-comment-on-a-work-item/), [Confluence 페이지 구독](https://confluence.atlassian.com/doc/watch-pages-spaces-and-blogs-139579.html)

프로젝트 업무 구독은 새 업무·상태 변경·댓글을 전달한다. 프로젝트 문서 공간과 팀 공통 문서 공간은 따로 구독하며 새 문서·저장·버전 복구·발행·댓글을 전달한다. 업무나 문서의 개별 구독과 범위 구독이 겹쳐도 같은 이벤트는 한 번 받는다. 각 범위 구독은 기존 자료와 이관 대상의 소급 알림 없이 켤 수 있다. 문서를 다른 공간으로 옮긴 뒤에는 도착 공간의 구독을 적용한다. 자체 백업 형식 29에 범위 구독과 생성 알림을 저장한다.

프로젝트 워크플로는 상태 ID와 집계 분류를 구분하고 모든 업무 수정·일정 API에서 같은 규칙을 적용한다. 공유 보기도 서버에서 버전 충돌을 검사한다.

사용 중인 상태의 활성 티켓은 워크플로의 상태 일괄 변경에서 다른 기존 상태로 옮긴다. 출발 상태의 전체 업무를 조회해 도착 상태·업무 양식의 필수 입력과 자동 배정을 미리 확인한다. 관리 작업의 상태 매핑은 개별 전이의 방향·조건과 별도로 처리한다. 검토 후 출발 업무의 구성·버전과 설정을 다시 확인하고 상태·이력·알림·발신 이벤트를 함께 저장한다. 워크플로 정의와 휴지통의 원래 상태를 보존한다.

내 업무는 선택한 작업자가 담당하거나 협력하는 업무를 프로젝트 전체에서 읽는다. 기본 마감 묶기는 브라우저의 현지 날짜와 `목표 마감일 → 계획 종료일` 순서로 계산한다. 각 프로젝트 워크플로의 분류를 적용해 상태별로 묶거나 완료·취소 업무를 포함할 수 있다. 프로젝트와 참여 범위 필터는 티켓 상세를 여는 경로와 독립적으로 유지한다.

팀 개요는 서울 시간의 기준일과 프로젝트·팀원 조건을 주소로 보관한다. 열린 업무의 마감 초과·7일 이내·일정 미정·미배정 수를 집계하고, 문서 검토의 고정 저장본과 최근 7일간 저장된 GitLab 연결 및 당일 확정 시간 배정을 같은 읽기 트랜잭션에서 조회한다. 팀원 조건은 업무·GitLab의 담당자 또는 협력자, 문서 검토자, 배정된 팀원으로 적용한다. 열린 티켓과 고정 검토본으로 이동하고, 프로젝트 개요·간트·개발 화면에서 브라우저 뒤로 가기로 같은 범위에 돌아올 수 있다.

프로젝트의 수동 업무 순서는 목록, 보드, 문서 안의 업무 목록과 현황에 공통으로 적용한다. 필터를 사용한 순서 변경은 선택한 이웃의 앞이나 뒤에 배치하며 다른 업무끼리의 상대 순서를 보존한다. 다른 상태 열의 카드에 놓는 경우 상태 전이와 순서를 같은 트랜잭션에서 검사하고 저장한다. 자체 백업은 프로젝트별 활성 티켓의 순서를 보존한다.

간트에서 같은 프로젝트의 공유 보기를 선택하고 목록·보드에 저장한 조건으로 업무를 찾는다. 간트의 업무 검색·완료 숨기기·계획 연결 조건을 함께 적용한다. 주소에 보기 ID를 보관해 직접 열기와 업무 상세 이동 이후에도 같은 보기를 사용한다. 삭제됐거나 다른 프로젝트의 보기를 가리키면 안내와 함께 빈 차트를 표시하고 사용자가 다른 범위를 선택한다. 선후행 계산에는 전체 프로젝트의 연결을 사용한다.

업무 목록의 일괄 편집은 검색·필터로 표시된 티켓을 최대 100개 선택해 상태·우선순위·담당자를 바꾼다. 개별 업무와 같은 워크플로·필수 필드·담당자 배정 규칙으로 각 업무의 변경 전후와 차단 이유를 계산한다. 일괄 편집에서 담당자를 직접 선택하거나 해제하면 그 입력을 적용한다. 적용할 때 티켓과 설정 버전을 검사하고 변경·이력·알림·발신 이벤트를 한 트랜잭션에서 저장한다. 같은 미리보기 ID로 적용을 재시도하면 이미 저장된 결과를 반환한다. [Jira의 업무 일괄 변경](https://support.atlassian.com/jira-software-cloud/docs/edit-multiple-issues-at-the-same-time/)

계획 작업 시간은 업무별 정수 분으로 저장한다. 프로젝트의 근무일과 팀원별 가용 시간을 사용해 간트의 표시 기간에 대한 계획 작업량을 계산한다. 가용 시간 설정은 프로젝트 기본값, 팀원별 기본값, 날짜 예외를 지원한다. 일정 변경 미리보기에서 초과 날짜를 비교하며 초과 여부로 업무 날짜를 자동으로 바꾸지 않는다.

프로젝트 간트에서는 담당자 작업량의 초과를 줄일 일정 변경을 계산해 검토 후 적용한다. 표시 기간과 선택한 담당자를 기준으로 우선순위가 낮은 업무부터 뒤로 옮길 후보를 찾고, 근무일 수·마감일·선후행 연결을 지킨다. 변경 전후 초과 시간과 프로젝트 계획 종료일, 남는 초과 날짜를 함께 표시한다. 같은 미리보기를 재시도하면 적용 결과를 돌려주며, 업무·연결·가용 시간·달력·워크플로 설정이 바뀌면 다시 계산한다. [Microsoft Project의 자원 초과 조정 방식](https://support.microsoft.com/en-us/project/distribute-project-work-evenly-level-resource-assignments)

프로젝트 간 작업량은 각 프로젝트의 달력에 따라 배분한 계획 시간을 팀원의 날짜별 합계로 보여준다. 비교 기준으로 팀 근무일과 개인 예외를 적용한 하루 가용 시간을 한 번 사용한다. 기본·팀원별·날짜별 가용 시간과 공통 달력 예외를 자체 백업에 보존한다. 날짜별 배분에서 원래 업무를 바로 연다.

시간 배정은 티켓 ID와 팀원 ID에 연결한다. 팀 일정은 서울 시간의 날짜별로 조회하고, 서버는 분 단위 UTC 시각과 편집 버전을 저장한다. 모든 프로젝트에서 같은 팀원의 시작·종료 구간이 겹치는지를 같은 저장 트랜잭션에서 검사한다. 날짜 단위 계획 작업량과 업무 시간 기록은 각자 기존 방식으로 계산한다. 휴지통의 배정은 시간을 점유하지 않으며, 충돌하는 기간에 업무를 복원하면 편집할 수 있는 재검토 상태로 돌려준다. 자체 백업 형식 30은 배정 ID·버전·재검토 상태를 보존한다.

프로젝트 간 과부하 조정은 모든 프로젝트의 업무를 같은 팀 가용 시간에 합산한다. 사용자가 고른 프로젝트의 업무만 이동 대상으로 삼고, 각 업무의 기간·마감과 해당 프로젝트 근무일·선후행 조건을 보존한다. 조정 전후의 과부하와 변경된 각 프로젝트의 계획 종료일을 검토하고 적용한다. 작업량을 제공한 모든 프로젝트의 업무·달력·워크플로와 팀 가용 시간의 변경을 적용 전에 확인한다. 적용과 전체 되돌리기는 기존 일정 변경 기록을 사용한다.

사이클·모듈·릴리스는 프로젝트별 독립 항목으로 관리하고 업무에는 ID를 저장한다. 이름은 참조에서 생성하며, 이름 변경과 일괄 업무 연결도 버전 충돌을 검사한다. API 키는 자동화 경로의 작업자·읽기/쓰기·프로젝트 범위를 고정한다. 복잡한 로그인·SSO 계정 체계는 추가하지 않는다.

간트에서 계획 기간·목표일·업무 연결을 확인하고, 연결된 업무만 보거나 업무를 선택해 연결을 변경할 수 있다. 업무와 계획의 날짜는 각각 저장하며, 목록의 기간 밖 집계로 차이를 확인한다. 계획 일정 저장은 계획 버전을 검사하고 연결 일괄 적용은 계획과 각 업무의 버전을 함께 검사한다. 계획 상세와 간트는 같은 항목 ID로 이동한다.

계획 일정 함께 이동은 지정한 달력일·근무일 수로 계획 날짜와 해당 업무 날짜의 미리보기를 만든다. 업무를 함께 이동할 때 계획 버전, 연결된 업무와 선후행 조건, 관련 설정을 고정한다. 계획·업무 날짜와 이력·되돌리기 기록을 같은 트랜잭션에서 저장하며 원래 미리보기 ID로 적용 결과를 다시 확인할 수 있다.

업무 유형·사용자 정의 필드·선택지는 프로젝트별 고유 ID로 참조한다. 이름 변경은 값을 바꾸지 않으며 사용 중인 항목을 제거해 자료를 잃지 않는다. 입력 종류와 범위·필수 규칙은 서버에서 검사하고 목록·상세·간트·API·백업이 같은 설정을 사용한다. 공유 보기는 형식에 맞는 필드 조건과 결합 방식을 저장한다. 목록·보드와 프로젝트 범위 자동화 조회는 같은 비교 규칙을 적용한다. 저장된 조건이 사용하는 필드·선택지는 보기에서 참조를 해제한 뒤 삭제할 수 있다.

사용자 정의 필드는 표시할 상태와 기준 체크 또는 단일 선택 값으로 티켓 양식에 표시할 수 있다. 기준 필드가 표시되고 입력한 값까지 일치해야 하며, 연결된 조건은 순환 없이 평가한다. 표시 중인 필드의 필수 입력과 별개로 워크플로의 상태·전이별 필수 규칙을 적용한다. 숨겨진 값은 보존한다. 표시 조건에 쓰는 상태·필드·선택지는 활성 참조가 해제되면 제거할 수 있다. 자체 백업 형식 34에 표시 조건을 보존한다.

일정은 프로젝트 달력의 근무일로 계산하며 변경은 미리 검토한다. 자동 제안은 업무·달력·의존성·워크플로의 버전을 고정하고, 같은 트랜잭션 안에서 날짜·이력·되돌리기·적용 기록을 저장한다. 스프레드시트 붙여넣기는 같은 프로젝트의 업무 키로 날짜와 선후행 연결을 찾는다. 변경 전후와 연결 경고를 검토하고, 제안된 연결을 모두 반영한 그래프의 순환 여부를 검사한 뒤 날짜와 연결을 함께 적용한다. 기준 계획은 당시 날짜와 달력을 변경하지 않고 보존하며 현재 계획과 비교한다. 마일스톤의 현재 업무 연결과 과거 캡처 기록을 구분한다.

선후행 연결은 관계 유형에 따라 각 업무의 시작일 또는 종료일을 사용한다. 간트에서 선행·후행 업무의 끝점이나 행을 선택하면 연결 검토 창에 두 업무와 유형이 채워진다. 같은 방향의 기존 연결은 간격을 불러와 수정한다. 자동 일정은 시작·종료 조건을 함께 만족하면서 근무일 기간을 유지한다. 연결 변경은 버전을 검사하며 이미 만든 일정 제안은 새로 계산한다. 자체 백업 형식 21에 연결 유형과 버전을 보존한다.

간트 일정 여유 분석은 저장 일정과 프로젝트 근무일을 기준으로 연결 조건을 충족하는 가장 이른 전체 완료일을 계산한다. 각 업무를 그 완료일 안에서 늦출 수 있는 근무일 수와 여유 0일 연결을 표시한다. 날짜가 부족한 연결 일정을 제외한 경우 계산 범위를 알려준다. 간트와 프로젝트 범위 API는 같은 읽기 전용 계산을 사용한다.

GitLab 상태 자동화는 명시적으로 활성화한 규칙과 현재 워크플로의 검증을 함께 적용한다. 수신 이벤트·상태 변경·이력·외부 웹훅 대기는 같은 트랜잭션에서 저장한다. 외부 전송은 서명과 영속 재시도를 사용하며 수신 측은 이벤트 ID로 중복을 처리한다. 자체 백업으로 복원한 규칙은 비활성 상태로 시작한다.

상태별 담당자 배정은 상세 편집·보드 이동·업무 API·인증된 GitLab 자동화의 실제 상태 전이에 적용한다. 출발·도착 상태와 업무 유형이 맞는 활성 규칙을 우선순위 숫자와 ID 순으로 평가해 첫 규칙을 사용한다. 같은 저장에서 담당자를 직접 바꾸거나 비우면 그 값을 우선하며, 미배정에만 적용하는 규칙은 기존 담당자를 유지한다. 제안된 담당자를 포함해 워크플로를 검증한 뒤 티켓 버전·배정 결과·활동 이력·알림·발신 이벤트를 한 트랜잭션에서 저장한다. 미리보기는 입력한 한 규칙의 결과와 전이 차단 이유를 조회한다. 형식 32 자체 백업의 복원은 규칙을 비활성 상태로 시작하며, 전체 데이터 백업은 실행 기록도 보존한다.

GitLab 연결 미리보기는 현재 입력한 주소·저장소·읽기 토큰으로 저장소별 조회 가능 여부와 티켓 연결을 계산한다. 설정·연결·업무를 읽기 전용으로 확인한다. 실제 수동 동기화에서도 같은 연결 계산을 쓰고, 파이프라인이 MR에서 티켓 키를 가져올 때는 브랜치와 head SHA가 함께 일치해야 한다.

Jira 이관 뒤 기존 개발 이력을 연결할 때 저장소별로 Teamspace 프로젝트와 Jira 원본을 지정한다. 현재 키와 원래 키는 그 프로젝트에서 찾으며, 두 업무에 해당하는 키는 미리보기에 표시하고 연결을 보류한다. 원래 키로 만든 링크에는 이관 키를 기록한다. 매핑을 변경하면 해당 저장소의 활성 상태 자동화 규칙을 비활성화하고 다시 검토할 수 있게 한다.

기존 개발 이력을 포함하는 미리보기와 수동 동기화는 브랜치 이름과 최근 커밋 메시지의 명시적인 업무 키로 링크를 만든다. 같은 저장소·SHA·업무의 커밋 링크를 재사용한다. 브랜치의 조회 관측과 인증된 푸시 관측을 구분하고, 푸시로 확인한 활성·삭제 상태를 우선한다.

Push 웹훅은 브랜치 이름과 커밋 메시지의 티켓 키로 MR 전 개발 기록을 연결한다. 브랜치의 마지막 확인 SHA와 삭제 상태를 저장하며 푸시의 `before`와 `after`로 이어지는 변경을 반영한다. 티켓과 개발 화면에서 브랜치·커밋·MR·파이프라인을 구분해 표시하고, 프로젝트 범위 API 키는 티켓의 GitLab 활동을 조회할 수 있다.

현재 구현 다음에는 계획·업무 보기, 문서의 고급 매크로, 시간대별 일정, 알림·보고와 기존 도구 이관을 확장한다. 실제 구현과 검사 결과는 [개발 상태](STATUS.md)에 기록한다.

## 기존 도구 원본 이관

병행 기간에는 업무와 문서에 Jira 티켓 및 Confluence 페이지 주소를 연결한다. 조회 버튼을 누르면 설정한 각 서버의 읽기 API에서 제목·상태·식별자와 수정 시각을 가져온다. 팀에서 사용할 연결의 자격 증명은 서버의 별도 파일에 둔다. 연결 주소는 전체 백업에서 보존하며, 원본 조회는 GET 요청으로 처리한다. [Jira 이슈 읽기 API](https://developer.atlassian.com/server/jira/platform/rest/v11000/api-group-issue/), [Confluence Server 6.9.1 REST API](https://docs.atlassian.com/ConfluenceServer/rest/6.9.1/)

기존 `/api/import`는 자체 백업으로 워크스페이스를 교체하는 기능이다. Jira·Confluence 이관은 별도 흐름으로 구현하며, 기본값은 새 프로젝트/문서 영역에 추가한다. 패키지 분석 → 작성자·상태·유형·필드 매핑 → 변환 샘플과 손실 미리보기 → 명시적 적용 순서다. 오프라인 분석과 원문 보관에 이어 작성자·상태·유형·필드 매핑, 문서 변환, 새 프로젝트 적용을 구현했다.

이전에 옮긴 같은 Jira 인스턴스의 같은 원본 프로젝트에서 새 업무를 추가할 수 있다. 대상 Teamspace 프로젝트의 저장된 상태·유형·필드에 매핑하고 새 업무에 다음 키를 부여한다. 이미 연결된 원본과 그 하위 기록은 영수증에 원문으로 보관한다. 새 업무의 부모와 업무 관계는 현재 살아 있는 기존 연결도 사용한다. 프로젝트 설정·새 키·원본 연결이 미리보기 뒤 바뀌면 다시 검토한다. 새 티켓·관계·첨부와 영수증을 같은 적용으로 보관한다.

패키지별 기본 주소를 지정하면 새 Jira 업무와 Confluence 페이지에 원래 업무 키와 페이지 ID로 링크를 만든다. 미리보기의 링크 예시와 연결·미연결 건수를 검토한 뒤 대상과 링크를 함께 저장한다. 영수증은 이관 당시 건수와 누락 사유를 보관한다. 이관 과정의 주소 계산은 오프라인으로 수행한다.

적용한 영수증의 **이관 결과 대조**에서 당시 원본과 현재 Teamspace 항목의 연결 상태를 확인한다. 원래 Jira 키·원본 ID·제목으로 찾고, 현재 업무·문서를 열거나 보존한 원본 기록을 읽는다. 첨부 버전은 이관할 때 기록한 크기와 SHA-256을 현재 파일 바이트와 비교한다.

**전체 이관 검증**은 영수증의 대상 상태를 집계하고 모든 원본 첨부 버전의 파일을 읽어 결과를 JSON으로 내보낸다. 파일럿 리허설에서는 서로 다른 원본 제품의 티켓·문서·링크를 한 프로젝트에 적용하고, 별도 물리 복원본에서 같은 검증을 실행한다.

새 이관 영수증은 패키지별 원본 수량, 첨부 버전 연결 수량, 보존 원본의 SHA-256 기준값을 적용과 함께 저장한다. 현재 검증에서 보존 원본 누락과 같은 건수의 원문·메타데이터 변경도 찾는다. 현재 티켓·문서의 편집이나 휴지통 이동은 원본 검증값과 별도로 대상 상태에 반영한다. 원래 제외한 객체와 함께 제외된 하위 원본도 이관 제외로 표시한다. 형식 33 자체 백업은 기준값과 제외 표시를 보존하며 기준과 다른 원본이 든 백업을 거절한다. 예전 영수증은 남아 있는 당시 수량을 사용한다.

주 입력은 Jira 관리자 XML 백업과 별도 첨부파일 묶음, Confluence Server 전체 공간 XML ZIP이다. Jira CSV의 반복 Comment/Attachment 헤더, 검색 XML과 REST/Importers JSON은 별도 형식으로 판별한다. CSV만으로 작성자·전체 이력·첨부 바이트가 보존된다고 판단하지 않는다. Jira 관리자 백업에도 첨부 바이트는 별도이며, JSON Importers 명세를 UI의 완전한 JSON 내보내기 명세로 취급하지 않는다.

원본 인스턴스·객체 종류·원본 ID를 기준으로 Teamspace ID를 매핑하고 원래 키·URL·시각·작성자·원문 해시를 보관한다. 이름만으로 팀원을 합치지 않는다. 이관 영수증과 원본 기록에 원본 신원·변경 이력·첨부 버전을 보존하고, 현재 업무·문서에서 원본을 찾아볼 수 있게 한다. Confluence Page/historicalVersions/BodyContent 관계를 따라 버전을 복원하고, 양쪽 ID를 확보한 뒤 문서/티켓/include 링크를 재작성한다. 모르는 매크로는 원문과 대체 표시·손실 항목으로 남기며 누락 첨부를 자동 다운로드하지 않는다. 제한된 문서/댓글을 팀 전체에 조용히 공개하지 않고 적용 차단 또는 명시적 제외로 보고한다.

Confluence 본문의 제목 참조는 원본 인스턴스와 명시한 공간 또는 현재 원본 문서의 공간에서 찾는다. 다른 페이지의 첨부 링크와 이미지는 본문이 지정한 소유 페이지에서 확인하며, 첨부 ID가 있으면 해당 버전을 사용한다. 후보가 없거나 원본에서 유일하지 않으면 원문과 변환 진단을 남긴다. 미리보기 진단에서 해당 패키지의 원본 객체를 바로 열어 확인할 수 있다. [Confluence 저장 형식의 리소스 식별자](https://confluence.atlassian.com/doc/confluence-storage-format-790796544.html#ConfluenceStorageFormat-Resourceidentifiers)

서버가 보관한 미리보기 계획에 패키지 해시·매핑 버전·대상 버전을 고정한다. 같은 패키지 재적용은 중복 생성하지 않고, 대상 변경은 충돌로 중단한다. 적용은 DB와 새 첨부 바이트를 복구 가능하게 묶으며 기존 업로드를 전체 교체하지 않는다. `origin:import`를 사용해 상태 자동화와 외부 발신 이벤트를 만들지 않는다. 완료 근거는 개수·원본 ID·작성자·이력·첨부 해시·양방향 링크 대조와 실패/재시작 복구다.

합성 자료로 분석·매핑·적용·복원을 검증한다. 실제 오프라인 패키지 리허설에서는 Jira 관리자 백업 및 별도 첨부파일의 구성, Confluence 6.9.1의 공간 내보내기 범위, 조직별 매크로와 권한, 누락된 자료를 확인해야 한다.

근거: [Jira 검색 내보내기](https://confluence.atlassian.com/jirasoftware/working-with-search-results-1528533257.html), [관리자 XML 백업과 첨부 범위](https://confluence.atlassian.com/adminjiraserver/backing-up-data-938847673.html), [Jira Importers JSON](https://confluence.atlassian.com/adminjiraserver100/importing-data-from-json-1442845835.html), [Confluence XML 객체/이력 구조](https://confluence.atlassian.com/confkb/use-space-site-xml-export-entities-xml-to-find-confluence-objects-1283686755.html), [Confluence 저장 형식](https://confluence.atlassian.com/doc/confluence-storage-format-790796544.html).


## Jira 작업 시간 이관

Jira 관리자 XML의 작업 기록과 REST·Importers JSON의 개별 작업 시간에서 이관할 업무, 작성자, 작업일, 초 단위 길이를 확인한다. 날짜는 기록에 명시된 현지 날짜를 유지한다. 팀원으로 명시적으로 매핑한 작성자의 기록을 업무의 작업 시간과 프로젝트 보고서에 함께 반영한다. 제한된 기록은 제외하기 전까지 적용을 차단한다. 매핑되지 않은 작성자나 기준이 불명확한 날짜·시간 단위는 원본에 보관하고 확인 항목에 표시한다. 부분 REST 페이지는 진단에 남긴다. [Jira Data Center 작업 기록 API](https://developer.atlassian.com/server/jira/platform/rest/v11003/api-group-issue/), [Jira JSON 작업 시간 예시](https://confluence.atlassian.com/servicedeskcloud/importing-data-from-json-1097176631.html#ImportingdatafromJSON-Worklogs).

적용 건수와 원본에만 보관한 건수를 미리보기와 영수증에 남긴다. 작업 시간과 보관 원본은 다른 업무 데이터와 같은 트랜잭션에 저장하며 원본 ID로 연결한다. 자체 백업은 원본과 정확한 초 단위를 함께 복원한다. 기존에 적용한 이관 영수증과 부분 데이터의 운영 리허설은 따로 검토한다.

## 보고서와 주간 문서 연결

프로젝트 개요는 현재 상태를 집계한다. 기간 보고서와 흐름 차트에는 업무 생성·삭제와 상태 전이를 구조화한 변경 기록이 필요하다. 업무 작업과 같은 트랜잭션에 이전·이후 상태, 당시 분류, 발생 시각, 출처를 기록한다. 수집 시작 전이나 원본 이력의 누락 구간은 보고서에 표시한다.

팀 보고서에 선택한 시간대의 날짜 경계, 완료 업무·완료 전이·재완료 구분, 관측 구간과 일별 상태를 구현했다. 주간 문서를 만들 때 기간·필터·기준 시각·집계·참조 업무를 다시 계산해 보관하고 양방향으로 연결한다. 실제 작업 시간은 티켓에 작성자와 작업일을 저장하고 별도 보고서에서 기간·작성자·업무를 기준으로 집계한다. 이후 결정 기록과 알림의 연결을 확장한다.

필드 집계는 전체 프로젝트 또는 저장된 보기의 현재 조건으로 업무를 선택해 필드 값으로 묶는다. 값이 비어 있는 업무와 필드 대상 유형에 속하지 않는 업무를 각각 표시한다. 숫자 통계와 그룹별 업무 이동을 제공한다. 그룹을 열 때 집계 이후 바뀐 데이터를 확인해 다시 조회할 수 있게 한다.

## 완료 판단

화면 시안이나 좁은 기능 검사만으로 제품 완성을 선언하지 않는다. 실제 실행 상태·저장 및 재시작·핵심 업무 흐름·브라우저 동작·데이터 이동을 검증하고 미구현 범위를 명시한다. 최초 개발 묶음은 제품 전체 완료와 구분한다.
