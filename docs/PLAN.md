# Teamspace 개발 계획

목표는 Jira·Confluence의 핵심 업무를 대체하고 Plane·Docmost의 빠른 입력·보기·문서 편집 방식을 반영한 독립적인 팀 프로젝트·지식 관리 제품이다. 초기 사용자는 20명 이하이다. 복잡한 보안, SSO, 기업용 계정 관리 기능은 현재 범위에서 제외한다. 기존 Jira/Confluence/Docmost/Plane 운영 데이터와 서비스는 변경하지 않는다.

## 제품 범위

- 팀 개요: 프로젝트·팀원·기준일 필터와 열린 업무 집계, 지표별 업무 목록과 간트 날짜 입력, 문서 검토 대기, 최근 GitLab 활동, 당일 시간 배정과 원래 항목 열기.
- 티켓: 기본 9개와 사용자 정의 유형, 요청자·담당자·협력자, 상태·전이, 우선순위, 프로젝트별 업무 순서, 계층·연관, 댓글·첨부, 실제 작업 시간 기록·집계, 사용자 정의 필드·유형별 필수 입력, 변경 이력, 검색·필드 조건·저장 보기.
- 계획: 목록·보드·간트에서 같은 티켓 사용, 인라인 일정 입력·수정, 스프레드시트에서 날짜와 선후행 연결 붙여넣기, FS·SS·FF·SF 연결과 근무일 간격, 저장된 일정 충돌·미정 확인과 날짜 편집, 다중 일정 이동·되돌리기, 마일스톤·달력·기준 계획, 팀원별 시간 배정과 프로젝트 간 겹침 검사.
- 지식: 문서 트리, 라벨·필터, 서식 편집·표·체크리스트·코드·이미지, 문서/티켓 참조, 템플릿, 버전 이력·복구, 댓글·검색, 공동 편집.
- GitLab: 저장소·브랜치·MR·커밋·파이프라인 연결, 업무 목록·보드의 상태 요약과 공유 보기 조건, 검증된 웹훅·재동기화, 환경별 배포 기록과 티켓 연결, 명시적 상태 자동화.
- API·자동화: 공개 API 계약, 개인/자동화용 API 키 발급·회수, 외부 웹훅과 도구 연결. 복잡한 계정 체계와 별도로 간단한 연동 수단을 제공한다.
- 데이터: 실제 서버 저장, 버전 충돌 검사, 문서·티켓·관계 내보내기, 기존 도구 이관, 백업·복원.
- 팀: 간단한 팀원 관리·작업자 기록, 담당자 배정·댓글·문서 검토 알림, 업무·문서·프로젝트 업무·문서 공간 구독. SSO와 복잡한 권한 엔진은 제외.

## 구현 원칙

하나의 저장소에서 웹 UI, 독립 API, 공통 타입을 관리한다. 초기 로컬 개발은 Node 24와 SQLite WAL을 사용하며 UI의 localStorage를 데이터 원본으로 사용하지 않는다. 저장 형식·API·일정 규칙은 참고 제품이나 화면 라이브러리에 종속시키지 않는다. 기존 설계의 PostgreSQL 도입은 규모·운영 요구 검증 후 판단한다.

새 업무의 요청자는 생성 작업자로 시작하며 등록된 팀원이나 미지정으로 저장할 수 있다. 업무 복제에도 새 업무의 기본값을 적용한다. 이전 데이터의 요청자 기록 유무를 보존하고 상세에서 변경할 때 업무 버전을 확인한다. 내 업무의 요청 범위는 담당·협력 여부와 독립적으로 적용하고, 전체 보기와 배지는 업무별로 한 번씩 센다. 형식 84 백업에 활성 및 휴지통 업무의 요청자를 보관한다.

티켓의 **변경 이력**은 상태·담당자·일정·계획 연결·사용자 정의 필드 등 실제로 바뀐 값과 작업자를 저장 버전별로 표시한다. 상세 편집·보드·간트·일괄 변경과 자동화는 같은 저장 경로에서 변경 기록을 함께 커밋한다. 이름과 선택지의 표시 값은 변경 시점에 기록하고 긴 텍스트의 일부는 발췌임을 표시한다. 현재의 활동 요약과 원본 Jira 상태 이력도 같은 탭에서 열 수 있다. 형식 88 자체 백업은 활성·휴지통 티켓의 필드 변경 기록을 복원한다.

프로젝트 공유 보기의 요청자 조건은 팀원 ID, 미지정, 기존 기록 없음으로 저장한다. 목록·보드·간트·문서 업무 블록·보고서는 같은 업무 판정 함수를 사용한다. 필드 교차 집계에서 요청자를 행이나 열에 두고, 조회 버전이 일치하는 그룹의 업무를 연다. 형식 85 백업은 공유 보기에 있는 요청자 조건을 보존한다.

프로젝트 업무 목록과 보드에서 여러 상태를 골라 하나라도 일치하는 티켓을 볼 수 있다. 공유 보기는 선택한 상태 ID를 보존하고 간트·문서 업무 블록·보고서에서 공통으로 사용한다. Jira `status IN`과 상태 조건만 포함하는 `OR`을 같은 범위로 옮기며, 프로젝트 범위 읽기 API와 형식 103 백업에도 상태 선택을 반영한다.

기존 업무와 문서는 어느 쪽에서도 같은 연결을 추가할 수 있다. 프로젝트 및 팀 공통 공간으로 좁히고 문서의 제목·상위 경로 또는 티켓의 업무 번호·제목으로 검색한다. 결과는 페이지로 탐색하며 정확한 업무 번호를 먼저 표시한다. 대상 확인 후 현재 업무나 문서의 초안을 보존한 채 저장한다. 업무·문서 쌍이 이미 있으면 같은 연결과 종류를 반환하며 새 이력을 남기지 않는다. 자동화 API는 양쪽 프로젝트를 확인하고 연결의 식별자와 종류를 조회한다. 결정 근거가 붙은 연결의 검토와 해제는 티켓 화면에서 수행한다.

문서의 **연결** 패널에서 이 워크스페이스의 일반 문서·절 링크와 저장 본문에서 들어오는 역참조를 찾는다. 절 링크는 현재 저장본에서 확인한 제목을 표시하고 문서의 현재 프로젝트에 있는 절로 이동한다. 절이 삭제됐으면 현재 문서를 열 수 있다. 페이지 링크와 같은 문서를 가리키는 참조 블록은 한 행으로 표시한다.

티켓에서 새 연결 문서를 만들 때 현재 프로젝트를 기본 공간으로 사용하며 다른 프로젝트 또는 팀 공통 공간, 같은 공간의 상위 문서, 기본 및 팀 템플릿을 선택할 수 있다. 티켓의 저장된 소속과 문서 위치를 확인한 뒤 문서·첫 이력·템플릿 첨부·연결·활동·알림을 한 번에 저장한다. 응답이 끊기면 같은 작업자와 요청으로 결과를 확인한다. 확정된 저장 뒤 목록을 불러오지 못하면 목록만 다시 요청한다. 티켓과 댓글 초안은 상세에 남고 양쪽에서 상대 항목을 열 수 있다. [티켓에서 새 연결 문서 만들기](API.md#티켓에서-새-연결-문서-만들기)

팀 문서 템플릿은 저장된 문서 본문과 그 버전의 제목·아이콘을 별도로 보관한다. 프로젝트 양식은 해당 프로젝트에, 팀 공통 양식은 모든 문서 공간에 적용한다. 같은 공간의 저장 문서로 본문을 교체하거나 이름 변경·보관·복원을 할 때 버전을 확인한다. 템플릿으로 만든 문서에는 독립된 첫 저장본을 기록하고 양식 안의 절 링크를 새 문서에 연결한다. 원본 문서가 소유하고 본문에 참조된 첨부는 정확한 버전을 양식에 복사한다. 새 문서의 파일과 주소는 새로 만들고 첨부·본문·첫 저장본과 요청 결과를 함께 저장한다. 팀 템플릿과 보관 상태는 자체 백업 형식 63에, 양식이 보관한 첨부와 무결성 정보는 형식 65에 포함한다.

업무 상세에서 현재 티켓을 상위 업무로 지정해 하위 업무를 만든다. 서버는 상위 업무의 저장 버전을 확인하고 같은 프로젝트의 기존 생성 규칙을 적용한다. 하위 티켓·업무 번호·변경 기록과 재시도 기록을 함께 저장한다. 목록·보드·간트는 표시 행의 필터와 별도로 현재 워크스페이스에 저장된 계층을 읽으므로, 상위 티켓 행이 가려져도 상위 업무를 열 수 있다.

업무 복제는 저장된 티켓의 입력을 같은 프로젝트의 새 업무 양식에 채운다. 현재 유형과 상태에서 사용할 수 있는 값을 표시하고, 초기 상태를 기본으로 선택한다. 날짜는 원할 때 복사해 수정하며 상위 업무와 계획 항목은 새 양식에서 지정한다. 원본이 수정되면 최신 저장 버전을 확인하면서 복제 양식의 입력을 유지한다. 업무 생성·이력·알림·원본과의 관련 업무 연결·요청 기록은 한 트랜잭션에 저장한다. 복제 후 원본의 작성 중인 초안을 이어 쓰거나 새 업무를 열 수 있다. [Jira 업무 복제](https://support.atlassian.com/jira-software-cloud/docs/clone-an-issue/) · [Plane 업무 생성과 복사](https://docs.plane.so/work-items/create-and-manage-work-items)

업무 목록·보드와 간트의 새 업무 입력은 저장 요청마다 작업자·입력·요청 ID를 고정한다. 서버는 같은 요청의 재시도에 이미 만든 업무를 반환하고 번호 배정·생성 이력·알림은 한 번만 저장한다. 응답을 받지 못했거나 생성 뒤 목록 갱신이 실패하면 같은 요청으로 업무가 있는지 다시 확인하고 목록을 읽는다. 현재 데이터 디렉터리의 재시작과 물리 백업은 요청 기록을 보존한다. 같은 워크스페이스를 이동용 JSON 백업으로 교체하면 이전 요청 ID를 다시 보낼 때 충돌을 반환한다.

프로젝트 설정에서 반복 업무의 제목·설명·유형·우선순위·라벨·사용자 정의 필드 기본값을 템플릿으로 저장한다. 직접 입력하거나 같은 프로젝트의 저장 티켓에서 기본값을 가져온다. 일반 새 업무 양식에서 선택해 적용하고 저장 전에 값을 편집할 수 있다. 업무 생성은 적용한 템플릿 버전과 현재 프로젝트의 워크플로를 검사한다. 형식 87 백업은 보관된 템플릿도 포함한다.

프로젝트 **반복 업무**는 업무 템플릿과 서울 기준 요일·시각에 따라 매주 티켓을 만든다. 등록한 작업자가 요청자로 남고 지정한 담당자는 일반 배정 알림을 받는다. 실행 때 현재 템플릿·업무 양식·초기 상태를 확인하며, 적용할 수 없는 회차는 다음 실행과 함께 사유를 기록한다. 티켓, 업무 번호, 알림, 실행 결과는 함께 저장한다. 서버가 여러 회차를 지나 재시작하면 가장 최근 회차를 실행한다. 형식 90 백업은 활성 상태·다음 회차와 최근 실행을 복원한다.

프로젝트 업무 목록에서는 TSV·CSV를 붙여넣고 신규 업무 최대 100개를 검토한다. 현재 업무 유형·상태·담당자를 확인하고 일반 생성과 같은 업무 양식과 일정 규칙을 적용한다. 행별 오류가 있으면 전체 적용을 막는다. 작업자별 미리보기는 30분간 유효하다. 적용 전 양식·워크플로와 결과 값을 다시 대조하고, 검토한 순서로 업무 번호·이력·알림·발신 이벤트와 적용 기록을 한 트랜잭션에 저장한다. 적용 기록은 7일 동안 같은 요청의 결과 확인에 사용한다.

같은 표의 새 업무는 임시 키로, 같은 프로젝트의 기존 선행 업무는 현재 업무 키로 연결한다. 한 행에 여러 선행 업무와 각 연결 유형·근무일 간격을 지정하고, 행 순서와 별개로 실제 선후행 그래프의 순환을 확인한다. 미리보기에는 대상과 달력을 기준으로 계산한 미정·충돌 경고가 표시된다. 적용 전에 기존 선행 업무와 달력 버전을 확인하고, 새 업무를 표 순서대로 만든 뒤 연결과 이력까지 같은 트랜잭션에서 저장한다. 연결은 간트와 티켓 상세의 기존 선후행 데이터를 사용한다.

티켓 사이의 관련·차단·중복은 각 업무에 표시하는 관계다. 여러 프로젝트의 업무를 연결할 수 있다. 관련은 한 쌍에 한 번 저장하고, 차단과 중복은 방향을 포함해 같은 연결을 재사용한다. 관계 변경과 양쪽 티켓 활동은 함께 저장한다. 범위 제한 키는 양쪽 프로젝트에 접근할 수 있어야 한다. 백업과 휴지통 복원은 해당 관계 ID를 유지하고 버전을 높인다.

열린 티켓은 원본 업무와 허용된 완료·취소 상태를 선택해 중복으로 닫는다. 서버는 양쪽 업무 버전과 워크플로 버전을 확인하고 기존 상태 변경 검증을 적용한다. 원본이 같은 관계는 재사용하며, 별도 원본이나 새 순환은 거절한다. 상태·중복 관계·활동 이력은 함께 저장한다. 화면은 저장한 상태를 갱신하며 다른 업무 항목과 댓글 초안을 보존한다.

같은 프로젝트의 차단 관계에서는 두 업무를 연 상태로 일정 연결을 검토한다. Jira REST에서는 관계의 한쪽에 표시할 설명을 링크 끝점과 유형 설정으로 정한다. 이관 관계를 일정에 쓸 때는 선행·후행을 지정한다. 적용 시 원래 관계의 버전과 업무 쌍을 확인하고 기존 의존성의 중복·순환 규칙을 적용한다. [Atlassian Jira 업무 연결 모델](https://developer.atlassian.com/cloud/jira/platform/issue-linking-model/)

간트의 **차단 관계로 일정 연결**에서 Teamspace 관계와 원본으로 방향을 검증한 Jira 관계를 한 번에 최대 100개 검토한다. 여러 프로젝트에서 고른 관계를 함께 처리하며, 각 관계의 양쪽 업무는 같은 프로젝트에 속해야 한다. 검색이나 공유 보기에서 가려진 업무도 포함하고 검토 창의 프로젝트·페이지를 바꿀 때 선택을 유지한다. 차단하는 업무를 선행으로 하고 새 일정 연결에 FS·0근무일을 적용한다. 이미 저장한 같은 방향의 연결은 기존 유형·간격을 유지한다. 프로젝트별 달력으로 미정·충돌을 표시하고 순환이 생기면 적용을 보류한다. 원래 관계의 방향과 버전, 업무 날짜·버전·소속, 관련 연결과 프로젝트 규칙을 저장 전에 대조한다. 연결 적용과 되돌리기는 기존 일정 변경 기록을 사용한다. [Jira 타임라인의 차단 관계](https://support.atlassian.com/jira-software-cloud/docs/manage-dependencies-between-epics-on-the-timeline/)

간트와 티켓 상세에서 같은 선후행 연결의 방향을 바꿀 수 있다. 기존 연결 ID를 유지하고, 조회한 버전과 순환 여부를 확인한 뒤 양쪽 티켓에 변경 이력을 기록한다. 프로젝트의 선후행 연결 조회와 추가·수정·해제, 차단 관계에서 연결 만들기는 자동화 API에서도 같은 규칙을 사용한다. API 키는 변경 대상 연결이나 차단 관계의 양쪽 업무에 접근할 수 있어야 하며, 연결 해제에는 조회한 버전이 필요하다.

간트의 **선후행 일괄 연결**은 같은 프로젝트에서 현재 보이는 선택 업무 최대 100개의 연결을 추가·수정·해제한다. 공통 선행·후행 업무는 보기 밖에서도 검색할 수 있다. **순서대로 연결**에서는 차트 행의 순서에서 시작해 편집한 순서의 인접 쌍을 처리한다. 새 연결 추가는 기존 연결을 유지하며, 수정은 연결 ID를 유지한 채 선택한 유형과 근무일 간격을 바꾼다. 수정·해제에서 이미 있는 방향의 쌍과 연결이 없는 쌍을 미리보기에서 확인한다. 관련 업무 버전과 연결 그래프를 확인해 전체를 적용하며, 응답 유실 시 저장 결과를 다시 확인하고 이번 변경을 한 번에 되돌릴 수 있다.

일괄 연결에서 선택한 행과 공통 기준 업무의 차트 날짜 초안을 함께 검토한다. 변경한 날짜 칸만 반영하고, 같은 칸의 최신 저장값이 달라진 경우에는 해당 초안의 반영 여부를 확인한다. 제안 날짜로 기존 및 추가 연결의 일정 경고를 계산한 뒤 날짜와 연결을 함께 저장하고 되돌린다. 포함하지 않은 초안은 차트에서 계속 편집한다.

일괄 연결의 **후행 일정 함께 검토**는 제안한 연결의 추가·수정·해제와 선택해 저장할 시작일·종료일을 반영한 상태로 같은 프로젝트의 후행 일정을 계산한다. 차트에서 입력해 포함한 날짜는 고정한다. 필터 밖 직접·간접 후행 업무는 각 업무의 기존 근무일 기간을 유지하며 충돌을 해소하는 데 필요한 만큼 늦춘다. 계산한 날짜와 연결을 함께 검토하고 한 번에 저장하거나 되돌린다. 저장하기 전에 계산 범위의 업무·연결·프로젝트 달력을 다시 확인한다. [간트 선후행 일괄 연결](SCHEDULING.md#여러-업무의-공통-선후행-연결)

프로젝트·전체 프로젝트 간트와 팀 보드의 업무 검색은 현재 티켓과 연결을 확인한 Jira 원래 키 및 이동 전 Teamspace 키를 포함한다. 업무를 연결하는 선택창은 현재 키·제목과 검색된 이전 키를 함께 표시한다. 같은 키가 여러 업무에 해당하면 프로젝트 범위에 맞는 후보를 각각 보여주고 선택한 현재 업무 ID로 미리보기와 연결을 수행한다.

전체 프로젝트 간트에서 담당자나 미배정, 시작일·종료일 입력 여부로 업무를 좁힌다. 프로젝트·담당자·일정 미정·업무 검색·GitLab 조건을 주소에서 복원하고, 선택한 업무의 실제 프로젝트에 날짜를 저장한다. 전체 프로젝트 보드에서 간트를 열 때 프로젝트·담당자·검색·GitLab 조건을 가져온다. 두 화면은 검색어를 프로젝트 이름·키, 업무 상태 이름과 티켓의 검색 대상에 같은 규칙으로 적용한다. 마지막 빈 날짜를 채워 필터에서 사라진 업무는 되돌리기로 다시 나타난다. 연결 점검은 업무가 속한 프로젝트의 기존 작업 달력과 선후행 관계를 사용한다.

선후행 연결이 있는 일정 미정 업무의 날짜 제안은 프로젝트 달력과 현재 또는 편집 중인 직접 연결에 저장된 양쪽 업무의 날짜를 사용한다. 사용자가 입력한 근무일 수에 맞춰 한쪽 날짜만 있으면 그 값을 보존하고, 양쪽이 비어 있으면 오늘 이후의 가장 이른 범위를 찾는다. 날짜가 비어 점검할 수 없는 연결, 충족할 수 없는 조건을 표시한다. 제안은 편집기의 빈 칸에만 반영하고, 실제 저장에는 일정과 연결의 기존 미리보기·버전 검사·되돌리기를 사용한다. [날짜 미정 업무 입력](SCHEDULING.md#날짜-미정-업무-입력)

다른 프로젝트의 열린 차단 업무도 직접 연결의 날짜 제안에 반영한다. 확인된 Jira 이관 관계를 포함해 선행 종료일부터 후행 프로젝트 달력의 완료 후 시작(FS)·0근무일 조건을 계산한다. 필터 밖 선행 업무도 근거 목록에서 확인할 수 있다. 제안을 적용하기 전에 서버가 현재 조건을 다시 계산하고, 미리보기 이후 열린 선행 업무나 관계가 바뀌면 최신 업무를 읽고 다시 검토한다. 다시 계산할 때는 직접 입력한 날짜와 근무일 수를 보존하고 제안으로 채운 칸을 다시 계산한다.

간트의 선후행 흐름은 기존 연결에서 기준 업무의 모든 선행과 후행을 각각 찾아 표시한다. 같은 프로젝트의 업무 순서를 유지하며 단계는 가장 짧은 연결 경로를 기준으로 표시한다. 이전 보기에 가려진 날짜 미정·완료 업무도 해당 경로에서 확인하고 편집할 수 있다. 보기 전환과 일정 변경은 별도로 처리하며, 일괄 편집 대상을 새로 포함하려면 직접 선택한다. [Jira 타임라인에서 업무의 의존성 보기](https://support.atlassian.com/jira-software-cloud/docs/view-all-of-an-issues-dependencies-on-your-timeline/)

간트의 **하위 업무 일정**은 같은 프로젝트의 상위 관계를 따라 직접·간접 하위 티켓을 가지 순서로 표시한다. 평소 보기에서 가려진 티켓도 날짜와 선후행 연결을 편집할 수 있다. 시작일과 종료일을 모두 저장한 하위 티켓의 날짜로 전체 계획 범위를 계산하고, 완료·취소는 프로젝트 상태 분류를 사용한다. 집계 범위와 각 티켓의 입력 날짜를 차트에서 바로 비교한다. [하위 업무 일정 보기](SCHEDULING.md#하위-업무-일정-보기)

상위·하위 일정 함께 이동은 같은 프로젝트의 기준 업무와 직접·간접 하위 업무를 서버에서 다시 찾는다. 상위·하위 업무의 날짜 전후와 완료·취소·일정 미정 제외, 선후행 경고를 검토한다. 적용 전에 범위 전체의 업무와 상위 연결, 관련 일정과 프로젝트 규칙을 대조한다. 일수와 근무일 여부를 다시 검토에 사용하며, 날짜 저장·되돌리기·적용 재확인을 기존 수동 일정 변경과 같이 처리한다. [상위·하위 일정 함께 이동](SCHEDULING.md#상위하위-일정-함께-이동)

선택 업무나 상위·하위 업무의 상대 이동에서 **후행 업무도 함께 조정**을 선택할 수 있다. 이동해 계산한 날짜는 고정하고 프로젝트별 근무일과 선후행 조건으로 직접·간접 후행 변경을 검토한다. 공통 후행과 필터 밖 업무도 계산하며, 상위·하위 범위 밖의 후행은 미리보기에서 표시한다. 함께 검토한 날짜는 한 번의 적용과 되돌리기에 포함한다. [수동 일정 변경](SCHEDULING.md#수동-일정-변경-검토와-되돌리기)

공유 보기에 저장한 계획·일정 조건은 목록·보드·간트·문서 업무 블록·필드 보고서에서 같은 판정 함수를 사용한다. 사이클·모듈·릴리스는 ID 또는 미지정 여부로 비교한다. 기간 겹침과 목표 마감일 조회는 입력한 날짜 경계를 포함한다. 계획을 보관하면 ID를 유지하고 저장된 보기에서 참조 중인 계획은 삭제를 거절한다. 백업 형식 47은 가져올 프로젝트의 계획에 각 보기의 ID를 대조한다.

프로젝트 업무 목록·보드, 전체 프로젝트 보드와 간트에서 화면에 보이는 업무를 열 때 당시 필터와 표시 순서의 업무 ID 목록을 현재 브라우저 세션에 유지한다. 보드는 표시된 담당자 행과 상태 열, 간트는 업무 행 순서를 따른다. 저장으로 현재 업무가 필터에서 빠져도 이전·다음 검토를 이어 갈 수 있다. 최신 데이터에서 삭제되었거나 검토 프로젝트 범위에서 이동한 대상은 건너뛴다. 기존 변경 확인과 저장 완료 확인을 적용하며, 브라우저 뒤로 가기로 검토를 시작한 보기에 돌아온다.

프로젝트 업무 목록과 보드는 브라우저에 표시되는 동안 업무·워크플로·GitLab 링크·계획·저장 보기의 변경을 조건부로 확인한다. 검색어와 필터, 공유 보기 주소를 유지한다. 상세·생성·붙여넣기·일괄 편집, 우선순위·라벨·계획·사용자 정의 필드의 필터 편집, 카드 끌기와 저장 중에는 자동 응답을 화면에 적용하지 않는다. **업무 새로고침**으로 최신 정보를 직접 확인할 수 있다.

공유 보기의 우선순위와 라벨 조건도 같은 업무 판정 함수로 계산한다. Jira 이관 업무를 포함해 저장된 라벨의 대소문자와 공백을 그대로 비교한다. 한 보기에서 우선순위, 라벨 포함·제외 및 유무, 기존 검색·계획·필드 조건을 함께 쓸 수 있다. 참조한 라벨을 현재 쓰는 업무가 없어도 보기의 조건을 보존한다. 백업 형식 68에 조건을 기록하고 프로젝트 범위 읽기 API에서도 같은 값 비교를 사용한다.

파일럿은 빌드한 정적 웹, SQLite API와 공동 편집을 단일 루프백 주소로 실행한다. 팀 접속은 HTTPS 프록시 뒤에서 공용 키로 브라우저 세션을 열고, 각 작업자는 앱에서 선택한다. GitLab 웹훅과 개인 API 키는 각각의 자격 증명으로 요청한다. 물리 백업은 파일럿과 같은 데이터 잠금을 사용해 식별 키, 첨부, 이관 원본과 저장소를 함께 보관한다. 백업과 복원에서는 SQLite가 참조하는 활성·휴지통 첨부와 보존 원본의 크기 및 해시를 복사본과 대조한다. 실제 팀 접속 경로 및 운영 데이터 적용은 환경이 정해진 뒤 검증한다.

20명 합성 리허설은 Jira 관리자 백업과 Confluence 공간 ZIP을 이관한 뒤 시작한다. 각 브라우저에서 HTTPS로 로그인해 이관 문서를 공동 편집하는 동안 연결된 Jira 티켓의 상태·간트 일정과 서명된 모의 GitLab 웹훅을 검증한다. 기존 Jira 키를 검색과 웹훅 연결에 사용한다. 같은 편집 세대로의 재접속, 이전 세대 편집의 사본 저장, 재시작과 별도 복원 뒤 문서·일정·GitLab 자동 전이와 이관 원본·첨부파일의 일치를 검증한다.

업무와 문서의 첨부는 고정 ID를 유지하고 각 파일 버전의 바이트를 따로 보관한다. 목록에서 최신 파일을 선택하고 이력에서 당시 파일을 내려받는다. 문서에 삽입한 이미지는 저장 당시 파일 ID를 참조한다. 버전 추가는 확인한 최신 ID가 여전히 일치할 때 진행하며, 파일과 메타데이터는 장애 후 복구할 수 있도록 함께 반영한다. 자체 JSON과 파일럿 전체 백업에 이력을 포함한다.

업무와 문서를 휴지통으로 보내면 일반 조회·검색에서 사라지고 댓글·첨부 버전·연결과 문서 이력을 함께 보관한다. 복원은 원래 ID와 업무 키를 유지하며 편집 버전과 공동 편집 세대를 갱신한다. 상위 항목을 먼저 복원하고, 상대가 아직 휴지통에 있는 연결은 두 항목이 모두 돌아올 때 복원을 시도한다. 새 생성과 복원을 보고서에서 구분한다. 보관본은 전체 백업에 포함하며 휴지통에서 별도로 영구 삭제할 수 있다.

작성자는 개별 댓글을 휴지통에 보낼 수 있다. 댓글은 본문·작성자·작성 시각과 원래 ID를 보존하며 복원 후 작성 시각순으로 표시한다. 첨부파일은 최신 버전을 확인한 뒤 원본 및 모든 버전의 메타데이터와 바이트를 보존한다. 파일 복원 전에 각 버전의 크기와 SHA-256을 검사한다. 원래 업무·문서를 먼저 복원하고 개별 항목을 이어서 복원한다. 상위 항목을 영구 삭제하면 개별 휴지통 항목까지 지우며, 중단된 파일 정리는 재시작 후 이어진다. 자체 백업 형식 31과 전체 데이터 백업은 개별 휴지통을 포함한다.

공동 편집 문서는 Yjs 상태를 원본으로 삼고 JSON·검색용 평문을 같은 트랜잭션에서 생성한다. 복구·가져오기는 편집 세대를 바꾸어 오래된 오프라인 편집을 분리한다. 문서 참조는 ID를 유지하고 최신 원문을 가리키는 포함 본문은 읽기 전용으로 표시한다. 최신 원문 포함 관계의 순환은 저장·복원·가져오기·공동 편집에서 같은 규칙으로 거절한다. 이력 비교는 제목·본문과 서식·속성·블록 구조를 보존하며, 대규모 비교도 유한한 계산량으로 수행한다.

수동·공동 편집의 슬래시 메뉴에서 참조·포함·업무 목록과 현황·안내 상자·상태 배지 대화상자를 열면 입력한 명령을 확정할 때까지 유지한다. 공동 편집에서는 Yjs 상대 위치로 입력 범위를 추적하고 원래 문단과 앞뒤 블록을 대조한다. 다른 문단의 본문을 편집해 위치가 이동해도 원래 명령을 확인해 블록을 넣는다. 입력이 바뀌었거나 같은 위치를 확인하기 어려우면 대화상자에서 위치를 다시 선택하도록 안내한다. 명령을 지우고 블록을 넣는 변경은 한 편집으로 저장한다.

같은 팀원으로 문서를 여러 탭에서 편집할 때 각 탭은 미전송 편집을 별도 기록한다. 다시 열면 현재 세대의 기록을 Yjs로 합치고 해당 편집의 서버 저장 확인 후 확인한 기록을 정리한다. 다른 세대·이전 문서 형식·읽을 수 없는 원본은 별도로 복구한다. 복구 화면에서 표시된 편집만 버리거나 사본으로 보관하며, 나머지 보관 편집은 이어서 확인할 수 있다.

문서 속성은 편집을 시작한 저장본을 기준으로 제목·작성 상태·상위 문서·라벨을 각각 비교한다. 서로 다른 속성의 변경은 합치고, 같은 속성의 값이 갈리면 최신 저장값과 입력을 보며 하나를 선택한다. 선택은 초안에 반영하고 저장 때 변경된 속성만 현재 버전과 함께 보낸다. 저장 응답이 늦으면 응답을 기다리며 입력한 값과 이후 도착한 동료의 변경도 보존한다. 프로젝트가 이동하면 이전 상위 문서 초안을 그대로 적용하지 않는다. 수동 본문이 최신 저장본보다 오래됐거나 이전 형식 가져오기로 공동 편집이 해제된 경우에는 기존 사본·버리기 복구를 사용한다.

문서 표는 마우스, 키보드, 모바일의 두 단계 선택으로 셀 범위를 정하고 병합하거나 나눌 수 있다. 첫 행·첫 열·현재 셀의 헤더를 편집하며 Confluence에서 온 병합 구조도 같은 도구를 사용한다. 병합 내용은 왼쪽 위 셀에 모으고, 분할 시에도 해당 셀에 남긴다. 새 병합 범위는 한 축에 100셀까지다. 수동·공동 편집은 같은 표 노드를 저장하고, Markdown 다운로드에는 행·열 병합과 혼합 헤더를 HTML 표로 기록한다.

문서 라벨은 현재 문서 속성으로 저장한다. 프로젝트와 팀 공통 문서 목록에서 문서 검색과 한 라벨을 함께 적용하며, 주소로 필터를 공유할 수 있다. 통합 검색에서 다른 프로젝트의 문서도 라벨로 찾는다. 첫 이관과 새 문서 추가에서는 원본 페이지 관계와 소유 정보로 확인한 Confluence 전역 라벨을 옮긴다. 이후 원본 변경분은 현재 라벨과 이전 이관 기준을 비교해 반영한다. [Confluence 전역 라벨의 소유 정보](https://support.atlassian.com/confluence/kb/labels-arent-retrieving-owners-when-using-remote-api/)

통합 검색의 **전체 검색 결과**는 현재 불러온 워크스페이스에서 업무와 문서의 저장된 내용을 찾아 20건씩 보여준다. 정확한 업무 번호, 일치하는 제목, 제목 일부, 라벨, 본문·상태·사용자 정의 필드 등으로 순위를 정한다. 업무·문서 유형, 프로젝트·팀 공통 공간과 문서 라벨로 좁힌다. 문서는 같은 제목도 공간과 상위 경로로 구분하며 저장된 본문 발췌를 표시한다. 검색 조건과 페이지는 주소로 복원하고, 다른 프로젝트의 업무 상세를 닫거나 문서에서 뒤로 가면 같은 결과를 열 수 있다.

빠른 검색과 전체 검색에서 본문 일치 위치가 한 절로 확인되면 저장한 제목 ID로 해당 절을 연다. 접힌 구역에 있는 절도 펼쳐 보여주고 현재 문서 주소에 절을 보관한다. 문서 제목·라벨·원본 주소로 찾은 결과, 첫 제목 앞의 본문이나 여러 절에서 일치한 결과는 문서 자체를 연다. 전체 검색의 발췌에는 확인한 구역의 일치 문장을 표시한다.

빠른 검색과 전체 검색은 이관 원본의 실제 Jira 키와 연결을 대조하고 프로젝트 이동 이력에서 이전 키를 읽는다. 현재 키가 정확히 일치한 티켓을 먼저 보여주고, 같은 이전 키를 가리키는 활성 티켓을 모두 후보로 둔다. 현재 프로젝트와 키, 일치한 이전 키를 확인하고 현재 티켓을 연다. 자동화의 정확 조회도 현재 프로젝트 범위를 적용한다. 별칭은 현재 자료와 이력에서 다시 계산하므로 자체 백업 복원 뒤에도 같은 기준을 사용한다.

문서 연결 패널과 본문의 업무 참조, 티켓의 관계 추가와 중복 처리에서도 Jira 원래 키와 이동 전 키로 후보를 찾는다. 정확한 현재 키가 먼저 표시된다. 같은 키가 여러 업무를 가리키면 현재 키·프로젝트·제목과 일치한 이전 키를 확인한다. 현재 프로젝트 이름이나 키를 함께 입력해 후보를 좁힐 수 있다. 연결과 본문 참조에는 선택한 업무 ID를 기록한다.

Jira·Confluence 원본 주소는 빠른 검색과 전체 검색에서 현재 저장된 연결을 읽는다. HTTP(S) 원본과 설치 경로를 같게 맞추고 Jira 키, Confluence 페이지 ID 또는 제목 주소의 공간·제목을 대조한다. Confluence의 두 페이지 ID 형식은 같은 원본 페이지로 처리한다. 저장된 연결을 활성 업무·문서별로 합치며 결과를 현재 프로젝트나 라벨로 좁힐 수 있다. 페이지 주소의 검색 요청과 공유 주소에는 필요한 `pageId`를 남기고 프래그먼트를 제거한다. 연결 조회는 Teamspace 저장소 안에서 수행한다.

Confluence의 예전 제목 주소는 원본 페이지가 연결된 활성 문서, 영수증에 적힌 설치 경로와 같은 패키지에서 보관한 원본 페이지 제목·공간으로 찾는다. Teamspace에서 문서 제목을 수정한 뒤에도 원래 제목을 검색하며, 확인된 대상이 여럿이면 모두 표시한다. [Confluence 주소 형식](https://support.atlassian.com/confluence/kb/the-differences-between-various-url-formats-for-a-confluence-page/)

Confluence 댓글 주소를 빠른 검색이나 전체 검색에 붙여넣으면 원본 서버·설치 경로·페이지와 댓글의 이관 기록을 대조한다. `focusedCommentId` 또는 `#comment-`의 원본 번호를 읽고 현재 문서의 일반 댓글, 문장 댓글이나 답글에 바로 초점을 맞춘다. 두 번호가 함께 있으면 일치해야 한다. 문서가 이동하면 현재 프로젝트에서 열고, 휴지통의 댓글이나 원본을 하나로 확인할 수 없는 댓글 주소에는 결과를 표시하지 않는다. 공유 검색 주소에는 검증에 필요한 번호를 보존한다. [Confluence 댓글 링크 형식](https://confluence.atlassian.com/spaces/CONF90/pages/1425052105/Links#Links-Linktoacomment)

빠른 업무 검색과 전체 검색은 저장된 GitLab 활동 주소·저장소 한정 MR 번호·브랜치 이름·전체 커밋 SHA에서 연결된 티켓을 찾는다. URL은 서버와 저장소 경로, 활동 종류와 식별자를 대조한다. 현재·이전 티켓 키 다음에 GitLab에서 일치한 업무를 배치하며, 화면에 저장소와 참조를 표시한다. 결과는 현재 저장된 연결과 활성 티켓을 사용한다. 검색 주소에는 GitLab URL의 사용자 정보·쿼리·프래그먼트를 제외한 참조를 저장한다.

새 문서 화면에서 UTF-8 기준 512KiB까지 Markdown 파일을 선택하거나 붙여넣고, 새 초안의 공간과 상위 문서를 선택한다. 제목, 표, 인용·체크리스트, 코드와 일반 링크를 편집 가능한 본문으로 변환한다. 같은 파일의 확인된 제목 링크는 저장한 문서의 절 링크에 연결한다. 원본 파일 URL을 입력하면 상대 링크를 그 주소 기준으로 계산한다. HTML은 텍스트로 표시하고 이미지는 대체 텍스트와 확인 가능한 주소를 링크로 보존한다. 브라우저의 미리보기에서 바뀌는 요소를 확인한 뒤 저장한다. [GitLab Markdown 제목 링크](https://docs.gitlab.com/user/markdown/#heading-anchors)

문서 트리 순서는 최상위 문서에서 공간별로, 하위 문서에서 상위 문서별로 저장한다. 탐색 트리는 각 형제의 실제 순서를 표시한다. 편집 대화상자는 검색·라벨 필터에 관계없이 그 위치의 전체 문서를 읽고 순서·구성 버전을 함께 확인한다. 새 문서와 위치가 바뀐 문서는 도착 그룹 끝에 추가되며, 트리 이동과 복제는 내부 형제 순서를 적용한다. 순서 변경은 별도 저장 이력을 남기고 형식 82 백업에 사용자 지정 순서를 보관한다.

문서 복제는 서버의 저장본과 활성 하위 트리를 미리 검토하고 선택한 프로젝트 또는 팀 공통 공간에 새 초안으로 저장한다. 같은 트리의 현재 문서 참조·포함·절 링크를 새 ID로 연결하고 고정 포함은 그 저장본을 참조한다. 현재 첨부의 최신 파일과 본문에 고정된 내부 첨부를 후속 편집 가능한 새 파일로 복사한다. 문서 버전과 계층·대상·첨부의 변경을 적용 전에 검사하며, 같은 요청 결과와 모든 문서·파일을 함께 저장한다.

문서 공간이나 하위 트리의 서버 저장본을 ZIP으로 내려받는다. 최신 저장본에는 문서별 현재 첨부와 본문이 고정한 파일을, 승인·발행본에는 승인 당시 본문과 그 본문이 참조한 정확한 파일만 담는다. `README.md`에 문서 트리를 기록하고 `manifest.json`에 문서 버전·계층, 파일의 SHA-256, 패키지 밖 참조와 동적 블록의 진단을 담는다. 패키지 내부의 문서·절·파일 링크는 상대 경로로 바꾸고 모든 첨부를 검증한 뒤 전송한다. [Docmost 문서와 공간 내보내기](https://github.com/docmost/docs/blob/main/docs/user-guide/import-export.md#exporting-pages)

Markdown ZIP 가져오기는 Teamspace·Docmost 메타데이터 또는 일반 Markdown 폴더의 구조를 읽고 프로젝트·팀 공통 공간의 상위 문서를 선택해 적용한다. 검토한 바이트와 대상 위치를 다시 확인하며 새 초안, 최초 이력, 활동, 첨부와 결과 기록을 한 번에 저장한다. 묶음 안에서 확인한 문서·절·첨부 주소를 새 문서에 연결하고 본문 변환이나 해결되지 않은 경로를 미리보기에 표시한다. [가져오기 계약](API.md#문서-트리-markdown-zip-가져오기)

Markdown ZIP 안의 표를 편집 가능한 본문으로 복원할 때는 병합된 셀이 격자 전체를 빈칸이나 겹침 없이 덮는지 검사한다. 머리글·셀 정렬과 셀 안의 제목·본문·지원 서식은 문서 노드로 옮기고, 묶음 안에서 확인한 문서·절·첨부는 새 주소로 연결한다. 지원 범위를 벗어난 표는 미리보기 안내와 텍스트 원문을 제공한다. [HTML 표 모델](https://html.spec.whatwg.org/multipage/tables.html#table-model)

라벨별 문서 목록은 정확한 프로젝트 또는 팀 공통 공간과 라벨·일치 방식·정렬을 본문에 저장한다. 최신 편집본과 읽기 화면은 현재 문서 집합으로 목록을 계산하고, 이력·검토본·발행본·Markdown은 저장한 조건을 보여준다. 본문 형식과 공동 편집 프로토콜 9는 목록 블록을 지원하며, 서버는 이전 공동 편집 상태를 업그레이드한다. Confluence **라벨별 내용** 매크로는 문서 유형과 원본 공간의 범위를 이관 프로젝트로 표현할 수 있는 경우 변환한다. 복합 쿼리, 발췌문, 확인하기 어려운 범위는 원문과 진단으로 보존한다. [Confluence 라벨별 내용 매크로](https://confluence.atlassian.com/doc/content-by-label-macro-145566.html)

문서 속성은 그룹과 이름·텍스트 값의 행을 본문에서 편집한다. 속성 보고서는 하나의 프로젝트 또는 팀 공통 공간에서 라벨과 그룹이 맞는 현재 문서의 속성을 열 순서대로 표시한다. 숨긴 속성도 보고서에 사용하고 표에서 원문을 연다. 이력·검토·발행본은 보고서의 당시 조건을 보존한다. 두 블록은 문서 JSON 형식 13과 자체 백업 형식 96부터 지원한다. Confluence 속성 표와 보고서는 원본의 표 구조·라벨·공간을 정확히 표현할 수 있는 경우 변환하고, 다른 조건과 서식은 진단과 원본에서 확인한다. [Confluence 페이지 속성](https://confluence.atlassian.com/conf100/page-properties-macro-1627457216.html) · [페이지 속성 보고서](https://confluence.atlassian.com/doc/page-properties-report-macro-186089616.html)

공간을 생략한 구형 Confluence 보고서는 원본의 현재 공간으로 해석한다. CQL 보고서는 문서 유형과 단일 공간이 쿼리에서 확인돼야 한다. 그 공간의 문서만 담긴 이관 프로젝트를 대조한 뒤 보고서를 만든다. 이관한 보고서는 최대 200행을 표시하며 원본의 페이지 나누기와 차이는 진단에 남긴다. [구형 보고서의 공간 매개변수](https://confluence.atlassian.com/spaces/CONF57/pages/701435053/Page%2BProperties%2BReport%2BMacro)

하위 문서 목록은 현재 문서나 지정한 문서·공간에서 서버에 저장된 문서 트리를 조회한다. 현재 문서 기준은 템플릿에서 새 문서를 만들거나 최신 본문을 포함할 때 해당 본문의 문서에 적용한다. 첫 단계의 최대 문서 수와 하위 단계 범위를 구분하고, 형제 문서마다 저장된 정렬 조건을 적용한다. 역사 기록에는 조건을 표시한다. Confluence **하위 페이지 표시**에서 부모·공간을 확인할 수 있으면 지원 조건을 옮긴다. 전체 공간을 표시하는 설정은 이관 대상 공간이 분리된 경우에 변환한다. 발췌와 확인할 수 없는 설정은 원본 XML과 진단으로 보존한다. 정렬 기준을 생략한 원본은 사용자가 지정한 형제 순서를 적용하고, 저장된 순서가 없는 그룹은 제목순으로 표시한다. 동일 버전의 후속 이관은 예전 제목순 변환본과 현재 본문·원본이 모두 일치할 때 이 조건을 미리보기에서 갱신할 수 있다. [Confluence 하위 페이지 표시 매크로](https://confluence.atlassian.com/doc/children-display-macro-139501.html)

문서 발췌는 원본의 일부 블록을 서식과 함께 다른 문서에서 재사용한다. 읽기 화면에서 정의를 숨겨도 포함한 문서에는 그 구역을 표시한다. 포함 내부의 상대 블록은 원본 문서의 범위를 사용한다. 참조 새로고침, 순환·표시 한도와 저장본 표기는 일반 문서 포함과 같은 규칙을 적용한다. Confluence의 블록형 `excerpt`와 `excerpt-include`는 내용·원본 숨김·원본 안내 설정을 보존한다. 확인할 수 없는 대상이나 인라인 방식은 원본 XML과 진단에 남긴다. 이전에 이관한 문서는 더 새로운 원본 버전을 검토할 때 현재 본문이 이전 이관 기준과 일치하는 경우 새 변환을 적용할 수 있다. [Confluence 발췌](https://confluence.atlassian.com/conf59/excerpt-macro-792499102.html), [발췌 포함](https://confluence.atlassian.com/conf59/excerpt-include-macro-792499101.html)

문서 도구막대에서 프로젝트 또는 팀 공통 공간과 새 상위 문서를 고르고 이동 범위를 검토한다. 다른 공간으로 옮길 때는 활성 하위 문서와 복원 가능한 휴지통 하위 문서를 함께 옮긴다. 본문·문서 ID·절 ID·고정 저장본·업무 링크와 작성자가 블록에 지정한 조회 범위를 보존한다. 서버는 적용할 때 미리보기의 문서 버전과 계층, 도착 위치를 다시 확인하고 함께 저장한다. 이전 절 링크는 현재 공간의 같은 절을 연다. 현재 문서를 열어 둔 상태에서 주소가 갱신되면 댓글 초안을 유지한다.

문서 목차는 편집기의 현재 본문 또는 읽기 화면에서 선택한 저장본의 제목을 순서대로 나열한다. 반복된 제목은 순서로 구별하고, 접힌 블록의 제목은 그 절의 상위 블록을 열어 이동한다. 포함 문서의 제목은 해당 원문 목차의 범위다. 목차 이동과 펼치기는 현재 브라우저에서만 적용한다.

문서 본문 찾기는 수동·공동 편집기의 현재 본문에서 일반 문자열을 찾는다. 한 문단에서 서식으로 나뉜 텍스트를 이어 찾고, 표 셀·접기·코드·다단 속의 본문을 검색하며 결과로 이동할 때 접힌 상위를 펼친다. 포함한 원문과 다른 동적 블록은 현재 문서 검색 범위에서 제외한다. 검색 결과 최대 1,000개를 현재 브라우저에 강조하고, 결과가 더 많으면 모두 바꾸기를 보류한다. 바꾸기는 최신 편집기 본문의 위치를 확인해 같은 범위에 공통으로 적용된 서식을 유지하고 한 번의 편집으로 기록한다. 배치와 문서의 바이트 한도를 적용한다. 검색·강조·이동은 문서 내용이나 이력을 변경하지 않는다.

편집기와 가져오기는 제목 단계 1~6을 보존한다. 본문 목차 블록은 제목 범위와 세로·가로 목록 설정을 저장하며 새 블록의 기본 범위는 1~3이다. 링크는 현재 편집본이나 선택한 저장본의 제목에서 만들고, Markdown에 파일 안의 절 링크로 내보낸다. Confluence 목차의 기본 최대 단계 7은 HTML 제목의 최대 단계인 6으로 옮긴다. 정규식 필터나 사용자 지정 서식은 원문과 진단으로 보존한다. 이전 이관 문서의 제목 깊이는 원본 전체와 이전 변환으로 저장한 현재 본문이 각각 일치할 때 같은 원본 버전에서 검토해 복원할 수 있다. [Confluence 목차 매크로 설정](https://confluence.atlassian.com/conf85/table-of-contents-macro-1283360361.html)

공유할 절에는 제목 블록의 `sectionId`를 기록한다. 저장 또는 공동 편집 동기화가 끝나면 문서 ID와 절 ID가 들어간 주소를 복사한다. 편집기는 제목 변경과 제목 블록 이동에서 ID를 보존하고, 같은 문서에 붙인 사본에는 별도 ID를 만들 수 있다. 검토·발행본 링크에는 당시 저장본 ID도 기록한다. 현재 문서에서 절 링크로 이동할 때 편집 초안을 유지한다.

결정 기록과 설계 검토에서는 포함할 원본의 이력 ID를 지정한다. 편집기·이력·검토본·발행본에서 해당 저장본을 펼칠 수 있다. 저장본 안의 동적 블록은 당시 저장한 이름을 표시한다. 전체 백업 형식 26에 고정 포함 ID와 원본의 활성·휴지통 이력을 보존한다. [Confluence의 페이지 이력과 버전 비교](https://confluence.atlassian.com/doc/page-history-and-page-comparison-views-139379.html)

안내 상자는 종류와 선택 제목, 여러 본문 블록을 보관한다. 상태 배지는 문장 안에 이름과 색을 보관한다. Confluence의 지원 패널과 상태 매크로는 같은 편집 가능한 노드로 이관한다. 문서 이력·검토본·발행본과 자체 백업에도 같은 구조를 저장한다. 본문 목차를 지원하는 공동 편집 프로토콜 8은 기존 형식 1~7의 Yjs 데이터를 보존한 채 편집 세대를 갱신한다.

문서의 다단 구역은 한 줄에 1~3개 단과 상대 너비, 테두리 설정을 저장한다. 각 단은 제목·목록·표와 기존 참조를 포함할 수 있다. 좁은 화면은 저장된 순서대로 단을 쌓고, Markdown 내보내기는 동일한 읽기 순서로 본문을 이어서 기록한다. Confluence의 여섯 표준 페이지 배치를 동일한 구조로 가져오며, 지원 범위가 확인되지 않는 원본은 이관 진단과 함께 확인할 수 있게 보존한다. [Confluence 저장 형식](https://confluence.atlassian.com/doc/confluence-storage-format-790796544.html#ConfluenceStorageFormat-Pagelayouts)

공동 편집의 커서와 텍스트 선택은 Yjs 상대 위치로 공유하고, 같은 문서와 편집 세대의 수신자가 화면에 표시한다. 서버가 접속자 정보를 제공하고 브라우저가 그 위치를 현재 편집기에 연결한다. 본문 저장과 커서 통신은 별도로 처리하며, 본문 변경을 저장한 뒤 새 위치를 보내고 연결 종료나 유효 시간 만료 시 표시를 지운다.

문서 업무 목록은 프로젝트와 선택한 공유 보기의 ID를 저장한다. 편집 화면에서는 보기의 필터를 적용한 현재 업무와 상태·담당자를 최대 20개까지 보여주며 원래 업무를 열 수 있다. 이력과 검토·발행본에는 당시 저장된 목록 설정을 보존한다. 공유 보기가 삭제되면 그 설정의 이름과 오류를 표시한다.

문서 업무 현황은 같은 공유 보기 조건으로 업무를 상태·담당자·우선순위 중 하나로 묶는다. 편집 화면에서 개수와 비율을 읽고 그룹을 펼쳐 실제 티켓을 연다. 현재 수치는 업무 데이터를 갱신할 때 다시 계산한다. 이력과 검토·발행본에는 저장한 범위와 집계 기준을 보존한다.

회의록과 결정 문서의 연결 화면에서 후속 업무를 만든다. 프로젝트 문서는 현재 프로젝트에 연결하고 공통 문서는 사용자가 프로젝트를 선택한다. 기존 업무 양식과 필수 속성을 적용한다. 문서 버전을 확인한 뒤 업무와 연결을 한 번에 저장하며, 응답 유실 시 요청 ID로 같은 결과를 다시 확인한다. 작성 중인 문서에서는 본문과 댓글 초안을 유지한다.

문서의 연결 업무 목록은 직접 연결한 티켓과 저장 본문에서 직접 참조한 티켓을 한 행씩 보여준다. 프로젝트별 상태·담당자와 목표 마감일 또는 계획 종료일, 해당 문서의 본문 참조 횟수를 표시한다. 미완료 업무를 먼저 놓고 같은 그룹에서는 날짜가 빠른 순으로 보여준다. 미완료와 종료 건수로 범위를 좁히며, 직접 연결에 저장된 결정 근거에서 발췌와 고정 원문을 열 수 있다. 아직 저장하지 않았거나 대상을 열 수 없는 참조는 문서 정보에서 따로 확인한다. 업무 값은 새로고침으로 갱신하고 고정 원문은 선택한 버전을 읽는다. 연결이나 본문 참조에서 업무를 열면 문서의 프로젝트·문서·절 주소와 편집 상태를 유지한 채 티켓 상세를 표시한다. 저장하지 않은 티켓 편집과 문서를 벗어나는 이동은 각 입력의 확인 절차를 사용한다.

프로젝트 보고서의 결정 후속 업무는 여러 문서에 분산된 근거를 티켓의 프로젝트 기준으로 모은다. 현재 업무의 상태·담당자·기한과 원문 저장 당시 제목을 함께 표시한다. 미완료·종료 상태와 담당자, 현재 업무 키·제목, Jira 원래 키, 프로젝트 이동 전 업무 키와 현재·고정 문서 제목으로 범위를 좁힌다. 문서에서 기존 업무에 근거를 붙일 때도 이전 키를 검색할 수 있으며, 현재 키가 정확히 일치하는 후보를 먼저 보여준다. 업무와 원본 문서가 활성 상태일 때 연결당 한 행을 표시하고, 기한·원문 저장 시각·연결 ID 순으로 페이지를 나눈다. 근거를 열면 고정 버전 뷰어에서 저장한 발췌 위치를 강조한다. 티켓 상세는 최신 저장값을 확인하고 연다. 보고서 주소에는 적용한 조건과 페이지를 기록한다.

**팀 결정 후속 업무**는 팀 공통 문서와 여러 프로젝트의 문서에 연결된 현재 업무를 함께 조회한다. 업무 프로젝트와 문서 공간을 구분해 표시하고, 현재 프로젝트·전체 프로젝트 또는 지정 프로젝트로 조회를 좁힌다. 각 업무의 실제 워크플로에서 상태를 판정하고 모든 결과를 공통 마감일 순서로 정렬한 뒤 페이지를 나눈다. 티켓 상세와 고정 발췌는 각 항목의 실제 프로젝트·문서 ID로 연다. 적용한 프로젝트 범위도 주소에 보관한다. 범위 제한 API 키의 합계와 목록에는 양쪽 프로젝트가 허용된 근거만 포함한다.

보고서의 문서 제목은 현재 문서로 연결한다. 같은 탭에서 열 때는 이동한 문서의 현재 공간을 확인한다. 뒤로 가면 보고서의 프로젝트 범위·필터·페이지가 복원되고, 편집 중인 문서에는 기존 저장 확인을 적용한다. 같은 행에서 당시의 고정 발췌도 열 수 있다.

보고서와 문서의 연결 업무 목록에서는 기한과 계획 기간을 각각 표시한다. 보고서의 **일정 미정만**을 켜면 계획 시작일이나 종료일이 비어 있는 업무를 볼 수 있다. 두 화면에서 업무의 현재 프로젝트 간트로 이동해 해당 행을 열며, 날짜가 비어 있으면 시작일과 종료일 순서로 첫 입력란에 초점을 둔다. 뒤로 가면 보고서의 조건과 페이지 또는 이전 문서가 복원된다.

회의 초안은 팀·프로젝트 보고서에서 사용자가 읽은 페이지와 조회 버전을 서버에서 다시 확인한다. 선택한 프로젝트 또는 팀 공통 공간에 검증한 고정 발췌와 티켓 상태·담당자·기한·계획 기간을 기록한다. 원본 문서와 고유 티켓 참조, 일정 미정 조건과 페이지를 다시 여는 보고서 링크도 보관한다. 문서·첫 버전·업무 연결·생성 요청 기록은 한 트랜잭션으로 저장한다. 조회 버전이 바뀌면 입력한 제목과 문서 공간을 유지한 채 다시 검토하고, 적용 응답이 끊기면 같은 요청으로 저장 결과를 확인한다.

티켓에서는 직접 연결했거나 본문에서 티켓을 참조한 문서의 현재 저장본과 목차를 미리보기로 연다. 주소에 문서 ID를 기록하고 티켓과 문서의 연결 또는 참조를 대조한다. 미리보기만 여닫을 때는 티켓·댓글과 배경 문서의 편집을 유지한다. 문서 공간으로 이동할 때는 기존 저장 확인을 따르며, 당시의 결정 근거는 고정 원문 저장본에서 읽는다.

현재 저장된 본문에 직접 삽입된 업무 참조를 티켓 ID로 역조회한다. 참조한 문서는 참조 횟수와 함께 티켓에 한 번 표시한다. 이미 직접 연결된 문서는 연결 행에 횟수를 표시한다. 미리보기에서는 해당 문서의 참조 블록으로 본문 순서에 따라 이동한다.

저장되거나 동기화된 문서의 특정 문장에서 댓글을 시작할 수 있다. 서버가 문서 버전과 선택 범위를 대조하고, 당시 원문 저장본·댓글·알림·재시도 기록을 한 트랜잭션에 저장한다. 댓글 패널에서 발췌와 고정 원문을 열 수 있다. 본문이 먼저 바뀌면 입력한 의견을 유지하며 최신 본문에서 다시 선택한다. 자체 백업 형식 50은 활성 댓글과 휴지통 댓글의 원문 저장본 및 발췌를 대조한다.

댓글 패널의 **댓글에서 후속 업무 만들기**는 문장 댓글의 본문을 수정 가능한 업무 설명에 채우고 댓글이 달린 당시 문장과 저장본을 결정 근거로 연결한다. 현재 문서가 바뀐 뒤에도 당시 발췌를 사용한다. 신규 요청에는 현재 문서 버전과 댓글의 원문 저장본을 대조하며, 저장한 업무와 근거는 문서의 연결 목록 또는 결정 후속 업무 보고서에서 연다. 댓글 편집과 해결은 댓글 패널에서 관리한다. [문서에서 후속 업무 만들기](API.md#문서에서-후속-업무-만들기)

이미 있는 티켓에는 문장 댓글의 **댓글을 기존 업무에 연결**에서 당시 발췌를 결정 근거로 붙인다. 연결 전에 현재 문서 버전과 댓글에 고정된 원문을 확인한다. 일반 문서 연결이 있으면 기존 연결을 사용하고, 당시 발췌는 티켓과 결정 후속 업무 보고서에서 읽는다. 결과를 받지 못했을 때는 같은 요청을 다시 확인한다. 문서와 댓글에 작성 중인 내용은 계속 편집할 수 있다. [기존 업무에 문서 결정 근거 연결](API.md#기존-업무에-문서-결정-근거-연결)

문서 체크리스트 항목에 커서를 두면 **후속 업무 만들기**와 **기존 업무에 연결**을 사용할 수 있다. 커서를 둔 항목의 첫 문단을 해당 저장본에 고정하고, 새 업무의 수정 가능한 제목에 채운다. 하위 항목은 따로 선택한다. 문서를 먼저 편집한 사람이 있으면 최신 저장본에서 근거를 다시 고르며 작성한 업무 제목·설명·담당자·마감일을 유지한다. 문서 연결 목록과 결정 후속 업무 보고서에서 연결한 업무의 현재 상태·담당자·마감일을 확인한다. [문서에서 후속 업무 만들기](API.md#문서에서-후속-업무-만들기)

체크리스트 항목을 다시 고르면 **연결된 체크리스트 업무**에서 현재 상태·담당자·기한을 보고 티켓을 연다. 편집기가 저장한 항목 ID로 같은 문구의 항목을 구별하고, 문구나 위치가 바뀌어도 같은 항목의 티켓을 표시한다. 당시 결정 근거와 원문은 연결을 만든 저장본에서 연다. 항목 ID가 없는 예전 연결은 연속 저장본에서 같은 항목임을 확인할 수 있을 때 이어진다. 확인할 수 없거나 항목을 삭제했다면 **문서에 연결된 업무 보기**에서 기존 티켓을 확인한다.

문장 댓글은 열린 상태에서 시작한다. 팀원이 해결하거나 다시 열면 처리한 팀원과 시각을 기록한다. 댓글 패널에서 전체·미해결·해결됨을 열고, 알림과 공유 링크는 현재 상태에 맞게 해당 댓글과 원래 발췌를 표시한다. 문서 본문·고정 저장본과 작성 중인 초안은 그대로 사용한다. 다른 팀원이 먼저 상태를 바꾸면 최신 댓글을 읽고 다시 선택할 수 있다. 자체 백업 형식 73은 활성 상태와 휴지통에 보관한 문장 댓글의 처리 내역을 보존한다. 문장 댓글에 한 단계 답글을 단다. 각 답글은 같은 문서의 원래 댓글을 참조하며 대화는 원래 발췌·해결 상태를 공유한다. 새 답글을 등록할 때 원래 댓글이 열린 상태인지, 마지막으로 확인한 해결 버전과 일치하는지 검증한다. 답글·이력·알림·요청 기록을 함께 저장하며, 응답이 끊긴 경우 대화 상태가 바뀐 뒤에도 이미 등록된 답글을 같은 요청으로 확인할 수 있다. 원래 댓글의 작성자와 대화 참여자는 해당 답글로 이동하는 알림을 받고 멘션과 같은 알림을 중복해서 받지 않는다. 원래 댓글의 휴지통 항목과 문서 백업은 함께 보관된 답글을 복원한다. 티켓 댓글, 일반 문서 댓글, 문장 댓글과 답글은 작성자가 제자리에서 수정한다. 기존 주소·원문 위치·해결 상태를 사용하고 수정 시각을 함께 표시한다. 다른 탭에서 먼저 저장했다면 현재 본문을 읽으면서 편집 입력을 보존한다. 새 멘션 알림·변경 이력·요청 재확인 정보는 본문과 같은 트랜잭션에 기록한다. 백업 형식 89는 활성·휴지통 댓글의 수정 정보를 보존한다.

업무 댓글의 HTTP(S) 주소는 읽기 화면과 수정 충돌에서 비교하는 현재 본문에서 열 수 있다. 주소가 멘션과 겹치면 멘션과 일반 텍스트로 표시한다. 주소와 멘션의 저장 형식은 일반 텍스트와 기존 범위 기록을 사용한다.

저장되거나 동기화된 본문의 문장을 새 티켓이나 기존 티켓의 결정 근거로 연결한다. 서버는 문서 버전과 선택 범위를 대조해 당시 저장본 ID를 연결에 기록한다. 이미 문서와 티켓이 연결돼 있으면 그 연결 ID와 관계 유형을 유지하며, 다른 발췌가 이미 고정돼 있으면 새 저장을 거절한다. 공동 편집에서 해당 버전의 이력이 필요하면 연결과 같은 트랜잭션에 기록한다. 티켓에서 발췌와 당시 저장본을 열고, 자체 백업 형식 48은 기존 업무의 활성·휴지통 연결에도 발췌와 원문을 대조해 복원한다.

프로젝트 범위 쓰기 키로 문서에서 후속 업무를 만들거나 기존 티켓에 결정 근거를 붙일 수 있다. 저장할 문서와 업무의 프로젝트 및 발췌 원문의 참조 범위를 확인한다. 같은 요청의 재시도는 현재 업무의 프로젝트와 이미 고정한 저장본의 범위를 다시 확인한다. [후속 업무 생성 API](API.md#문서에서-후속-업무-만들기)

티켓과 연결 업무의 결정 근거, 문장 댓글은 당시 저장본에서 기록된 본문 위치와 발췌를 다시 대조한다. 일치하는 텍스트 범위와 상태 배지를 강조하고 첫 위치로 이동한다. 같은 문장이 반복될 때도 저장된 위치를 사용한다. 읽기 중 다시 이동하거나 Esc로 접을 수 있다. 본문을 읽어 오는 동안 작업자가 다른 곳으로 이동하면 포커스를 유지하며, 위치를 대조할 수 없는 저장본은 당시 본문과 안내를 표시한다.

티켓에서 결정 근거가 붙은 문서 연결을 해제할 때는 확인한 저장본과 발췌 범위를 현재 값과 대조한다. 다른 팀원이 일반 연결에 근거를 추가하면 이전 화면의 해제 요청을 거절한다. 연결 목록을 다시 읽어도 작성 중인 업무와 댓글을 유지한다. 해제는 티켓과 문서의 연결에 적용되며 당시에 저장한 문서 버전은 문서 이력에 남는다.

문서 검토는 요청 당시 서버 저장본을 이력 ID로 고정한다. 한 명 또는 여러 팀원을 지정하며, 모든 검토자가 승인하면 마지막 승인이 해당 저장본을 발행한다. 대기 중인 검토자의 수정 요청은 그 회차의 검토를 종료하고 기존 승인과 의견을 보존한다. 요청자는 요청을 철회할 수 있다. 편집기는 이후 초안을 계속 저장할 수 있고, 형식 91 백업은 승인 저장본과 검토자별 결정 메모를 보존한다. 작업자별 검토함에는 자신의 미처리 요청을 표시하고, 요청함과 팀 개요에서는 승인 진행률을 확인한다. 상단 배지는 현재 작업자의 미처리 요청을 한 문서당 한 건으로 센다.

문서 검토함의 탭과 조회 범위·프로젝트·고정 제목 검색·페이지를 목록 주소에 보관한다. 검토본이나 발행본에서 뒤로 돌아오면 같은 작업자와 목록에서 열었던 버전의 행에 초점을 돌린다. 행이 빠지면 목록 제목을 선택하고, 처리 이후 페이지가 사라졌으면 남아 있는 마지막 페이지를 조회한다. 공유 주소의 개인 탭은 현재 접속한 작업자로 조회한다.

재검토에서 마지막 발행본과 요청 당시 검토본의 제목·본문 구조를 검토 화면에서 비교한다. 서버는 검토 상태 버전과 복원 세대, 두 저장본 ID를 같은 조회에서 대조한다. 보는 동안 검토 결과 메모를 보존하고, 비교를 닫으면 비교를 열었던 버튼으로 돌아간다. 승인·수정 요청 전에는 개별 검토본을 열어 전체 내용을 확인한다.

팀 알림은 변경과 같은 트랜잭션에 수신자별로 저장한다. 담당자 변경, 업무·문서 댓글과 문서 검토·수정 요청·발행·철회를 알린다. 사용자 본인과 중복 수신자는 제외한다. 알림에서 대상에 이동하고 읽음 여부를 저장한다. 모두 읽음은 목록의 첫 알림까지 적용하여 이후 도착한 알림을 보존한다. 자체 JSON 백업의 15번 형식부터 알림과 읽음 시각을 포함한다.

업무 요청자에게 다른 작업자의 상태 변경과 새 댓글을 알린다. 상태와 요청자를 동시에 바꾸면 저장된 요청자를 사용한다. 상태 변경 당시의 전후 상태명과 일반 업무 댓글의 ID를 알림에 기록하며 업무·프로젝트 구독과 중복되는 수신자를 합친다. 멘션된 수신자에게는 멘션 알림을 기록한다. 형식 86 백업에 상세와 댓글 위치를 저장한다.

열린 업무에 팀에서 관리하는 차단 관계가 생기거나 원인 하나가 해소되면 해당 업무의 담당자·협력자·개별 구독자·프로젝트 구독자에게 원인 업무를 표시한다. 관계 변경과 원인 업무의 완료·취소·재개를 감지한다. 목표 마감일을 우선해 이전과 이후의 유효 마감을 계산하고, 변경 후 열린 업무에서 두 날짜가 모두 있으며 더 늦어진 경우 같은 수신자에게 두 날짜를 표시한다. 자체 백업 형식 62에 알림 내용과 읽음 상태를 보존한다.

팀원별 마감 알림은 기본값을 모두 끈 상태로 시작한다. 마감 전 1~14일 범위, 당일, 초과를 선택하며 서울 날짜로 현재 열린 담당 업무의 유효 마감일을 비교한다. 저장 직후, 서버 시작 시, 실행 중에는 60초마다 현재 해당하는 알림을 평가한다. 종류·팀원·업무·유효 마감일이 같은 알림은 한 건만 생성한다. 자체 백업 형식 70은 설정·발송 기록·읽음 상태를 보존한다. [Jira의 날짜 기반 예약 자동화](https://support.atlassian.com/automation/kb/trigger-an-automation-rule-based-on-due-date-field/)

개인 구독은 업무의 상태 변경·댓글과 문서의 저장·이력 복구·발행·댓글을 앱 알림으로 전달한다. 실시간 공동 편집은 새 버전 기록을 만들 때 구독자에게 알린다. 구독은 작업자·대상별로 관리하며, 휴지통에서 대상을 복원하면 다시 적용한다. 자체 JSON 백업의 25번 형식에 구독과 새 알림을 보존한다. [Jira 업무 구독](https://support.atlassian.com/jira-software-cloud/docs/watch-share-and-comment-on-a-work-item/), [Confluence 페이지 구독](https://confluence.atlassian.com/doc/watch-pages-spaces-and-blogs-139579.html)

프로젝트 업무 구독은 새 업무·상태 변경·댓글을 전달한다. 프로젝트 문서 공간과 팀 공통 문서 공간은 따로 구독하며 새 문서·저장·버전 복구·발행·댓글을 전달한다. 업무나 문서의 개별 구독과 범위 구독이 겹쳐도 같은 이벤트는 한 번 받는다. 각 범위 구독은 기존 자료와 이관 대상의 소급 알림 없이 켤 수 있다. 문서를 다른 공간으로 옮긴 뒤에는 도착 공간의 구독을 적용한다. 자체 백업 형식 29에 범위 구독과 생성 알림을 저장한다.

티켓과 문서의 개인 즐겨찾기는 작업자, 항목 유형, 고정 ID로 저장한다. 여러 프로젝트와 팀 공통 문서를 한 목록에서 열며 저장 당시의 ID로 현재 제목과 위치를 찾는다. 항목을 휴지통에 넣으면 표시를 유지하면서 목록에서 숨기고, 영구 삭제할 때 제거한다. 자체 백업 형식 94는 활성·휴지통 항목의 팀원별 기록과 처음 표시한 시각을 복원한다.

프로젝트 워크플로는 상태 ID와 집계 분류를 구분하고 모든 업무 수정·일정 API에서 같은 규칙을 적용한다. 공유 보기도 서버에서 버전 충돌을 검사한다.

전이별로 열린 차단 업무를 먼저 해결하도록 설정할 수 있다. Teamspace 관계와 이관 원본에서 연결 대상과 방향을 확인한 Jira 관계를 사용한다. 각 원인 업무의 프로젝트에서 완료·취소 여부를 판단한다. 상세·보드·업무 API·일괄 편집·GitLab 자동화의 상태 변경과 미리보기에 같은 규칙을 사용한다. 일괄 적용은 저장 전에 다시 검사한다. 업무 상세에서 차단 사유와 원인 업무를 찾고, 형식 81 백업에서 전이 설정을 복원한다. 관리용 상태 일괄 변경은 자체 상태 매핑 규칙을 따른다.

담당자별 보드는 현재 필터에 맞는 업무를 담당자와 상태별로 배치한다. 빈 담당자 줄을 펼치고 미지정 줄을 열어 재배정할 수 있다. 개별 줄 안의 카드는 프로젝트 순서를 따른다. 다른 담당자 줄로 옮기면 도착 담당자를 명시적으로 적용하고 상태·순서·이력과 함께 저장한다. 같은 줄에서 상태를 바꾸면 프로젝트 자동 배정 규칙을 적용한다. 이동 요청은 프로젝트 순서와 출발 업무의 버전, 기준 카드의 현재 상태·담당자를 확인한다. 공유 보기와 자체 백업 형식 76에 보드 표시 설정을 저장하고, 보기를 사용하는 간트·문서·보고서는 같은 업무 필터를 적용한다.

프로젝트 업무 목록의 상태 칸과 프로젝트 보드 카드의 **상태 변경**은 터치와 키보드로 열 수 있다. 업무 유형과 워크플로가 허용하는 상태를 보여 주고 업무·워크플로 버전을 확인한다. 전체 프로젝트 보드에서도 같은 창에서 담당자를 직접 지정하거나 해제하고 상태와 함께 저장할 수 있다. 자동 배정 규칙을 선택하면 서버의 배정 규칙이 적용된다. 최종 담당자와 다른 필수 값, 미해결 차단 업무를 검증한다. 적용 뒤 검색과 공유 보기, 업무 순서를 유지하고 남아 있는 행이나 이동한 카드로 포커스를 돌린다. 저장 응답이 끊기면 최신 업무의 상태와 명시한 담당자를 확인한다.

상태 변경 창의 **인수인계 댓글**에 메모나 팀원 멘션을 남길 수 있다. 상태·담당자·자동 목표 마감일과 티켓 댓글은 한 트랜잭션에서 기록한다. 서버가 돌려준 변경 기록의 요청 ID와 댓글 ID로 재시도를 확인하며, 다른 작업자가 같은 상태에 먼저 도달한 경우에는 업무를 다시 읽고 현재 초안으로 다음 전이를 검토한다. [상태 변경과 댓글 API](API.md#상태-변경과-인수인계-댓글)

**전체 프로젝트 보드**는 각 프로젝트의 실제 상태를 공통 상태 분류의 열에 배치한다. 카드는 실제 상태 이름·색상과 프로젝트를 표시하고 프로젝트 안에서 저장된 업무 순서를 따른다. 카드의 상태 변경 메뉴에는 업무 유형과 프로젝트에 허용된 실제 상태를 표시한다. 열로 끌어 이동하면 해당 열에 속한 상태 중에서 고른다. 업무 버전과 해당 프로젝트의 워크플로 버전을 상태 변경 트랜잭션에서 확인하고 기존 필수 입력, 차단 관계, 자동 배정 규칙을 적용한다. `teamboard` 주소는 프로젝트·담당자·검색과 GitLab 조건을 보관하며 다른 프로젝트의 업무를 열고 닫아도 유지된다.

팀 보드의 GitLab 조건은 프로젝트 업무 보기와 같은 판정과 카드 배지의 집계를 적용한다. 열린 MR과 그중 병합 확인이 필요한 MR을 보거나, 같은 참조와 실행 유형의 최신 파이프라인을 실패·진행 중·수동 실행 대기 조건으로 확인한다. 연결 활동 없음은 커밋·브랜치·MR·파이프라인 등 저장된 연결이 하나도 없는 경우에 표시한다. 새 저장본을 읽으면 현재 조건에 맞는 카드와 열별 건수를 다시 계산한다.

**보드 일괄 편집**에서 표시된 카드 최대 100개를 고르고 우선순위·담당자·마감일·라벨을 함께 바꿀 수 있다. 상태는 선택된 업무의 각 프로젝트에서 실제 도착 상태를 따로 지정한다. 필터가 바뀌면 가려진 업무를 선택에서 빼고, 선택 업무가 남지 않은 프로젝트의 상태 입력을 지운다. 공통 입력은 유지한다. 미리보기와 적용에서 프로젝트별 상태·워크플로·업무 버전을 확인한다. 전이·필수 값·배정 규칙을 통과하면 여러 프로젝트의 업무·변경 이력·알림을 함께 저장한다. 적용 응답이 끊기면 같은 미리보기로 결과를 조회한다. [업무 일괄 편집 API](API.md#업무-일괄-편집)

보드가 보이는 동안에는 약 15초 간격으로 저장 버전을 확인한다. 카드 데이터가 달라질 수 있는 SQLite 변경과 버전을 같은 트랜잭션에서 보관한다. 같은 버전은 상태 코드로 확인하고, 다른 버전은 업무 상세와 다른 화면에서도 사용하는 워크스페이스를 함께 갱신한다. 업무 상세·상태 선택·드래그·일괄 편집 중에는 확인을 멈춘다. 이전 화면이나 이전 요청의 응답을 무시해 현재 입력과 보기 주소를 보존한다. 수동 새로고침은 최신 워크스페이스를 요청한다. 12초 안에 응답하지 않은 요청은 중단하고 현재 화면에서 다시 시도할 수 있다. 자동 요청이 실패하면 다음 확인 간격을 최대 60초까지 늘린다.

보드 업무 한도는 프로젝트 워크플로의 상태 ID별로 저장한다. 해당 상태의 프로젝트 업무 수에 하위 업무를 포함하고 휴지통의 업무를 제외한다. 검색·저장 보기와 관계없이 한도에 도달하거나 초과한 상태를 표시한다. 해당 상태의 전체 티켓은 필터를 유지한 채 별도 목록에서 열 수 있다. 상태 이동은 기존 워크플로의 전이 검사를 따른다. [Jira의 보드 열 한도](https://support.atlassian.com/jira-software-cloud/docs/configure-columns/)

상태별 자동 목표 마감일은 실제 전이 시 날짜가 비어 있는 티켓에 적용한다. 도착 상태에 저장한 근무일 수를 서울 기준 변경일 다음부터 프로젝트 달력으로 센다. 기존 목표 마감일과 직접 지정한 값이 우선한다. 필수 입력을 검사하기 전에 날짜를 계산하고 상태·마감일·이력을 한 번에 저장한다. 일괄 편집은 계산한 날짜를 보여주고 적용 전에 달력과 결과를 다시 대조한다. 자체 백업 형식 93에 설정을 보존한다.

사용 중인 상태의 활성 티켓은 워크플로의 상태 일괄 변경에서 다른 기존 상태로 옮긴다. 출발 상태의 전체 업무를 조회해 도착 상태·업무 양식의 필수 입력과 자동 배정을 미리 확인한다. 관리 작업의 상태 매핑은 개별 전이의 방향·조건과 별도로 처리한다. 검토 후 출발 업무의 구성·버전과 설정을 다시 확인하고 상태·이력·알림·발신 이벤트를 함께 저장한다. 워크플로 정의와 휴지통의 원래 상태를 보존한다.

내 업무는 선택한 작업자가 담당하거나 협력하는 업무를 프로젝트 전체에서 읽는다. 기본 마감 묶기는 브라우저의 현지 날짜와 `목표 마감일 → 계획 종료일` 순서로 계산한다. 각 프로젝트 워크플로의 분류를 적용해 상태별로 묶거나 완료·취소 업무를 포함할 수 있다. 프로젝트와 참여 범위 필터는 티켓 상세를 여는 경로와 독립적으로 유지한다.

팀 개요는 서울 시간의 기준일과 프로젝트·팀원 조건을 주소로 보관한다. 열린 업무의 마감 초과·7일 이내·일정 미정·미배정 수를 집계하고, 문서 검토의 고정 저장본과 최근 7일간 저장된 GitLab 연결 및 당일 확정 시간 배정을 같은 읽기 트랜잭션에서 조회한다. 팀원 조건은 업무·GitLab의 담당자 또는 협력자, 문서 검토자, 배정된 팀원으로 적용한다. 열린 티켓과 고정 검토본으로 이동하고, 프로젝트 개요·간트·개발 화면에서 브라우저 뒤로 가기로 같은 범위에 돌아올 수 있다.

업무 현황 지표를 선택하면 같은 집계 조건에 속한 업무를 연다. 날짜가 있는 업무는 유효 마감일순으로 표시하고 마감일이 같거나 미정이면 우선순위와 업무 키를 사용한다. 미정인 시작일이나 종료일은 해당 간트 입력 칸으로 이동한다. 선택한 지표와 업무 페이지를 주소에 보관한다.

프로젝트의 수동 업무 순서는 목록, 보드, 문서 안의 업무 목록과 현황에 공통으로 적용한다. 필터를 사용한 순서 변경은 선택한 이웃의 앞이나 뒤에 배치하며 다른 업무끼리의 상대 순서를 보존한다. 다른 상태 열의 카드에 놓는 경우 상태 전이와 순서를 같은 트랜잭션에서 검사하고 저장한다. 자체 백업은 프로젝트별 활성 티켓의 순서를 보존한다.

**백로그 · 사이클**에서는 사이클 미지정 업무와 선택한 계획·진행 중 사이클의 업무를 함께 본다. 프로젝트 순서에서 각 그룹의 업무를 골라 표시한다. 업무를 끌거나 위·아래 이동과 사이클 선택을 사용하면 다른 업무의 상대 순서를 보존하면서 배정·순서·이력을 함께 저장한다. 기준 카드가 있으면 그 업무의 앞이나 뒤에 넣고, 그룹 끝으로 이동할 때는 필터 밖 업무까지 포함한다. 빈 그룹에 넣으면 이동한 업무의 프로젝트 순위를 유지한다. 버전 충돌에는 최신 업무를 확인한 뒤 다시 이동한다. 적용 응답을 잃으면 같은 요청으로 결과를 확인한다. [Jira 백로그 순위](https://support.atlassian.com/jira-software-cloud/docs/rank-an-issue/) · [Plane 사이클 계획](https://docs.plane.so/introduction/tutorials/plan-and-create-cycles)

백로그와 선택한 사이클의 각 그룹에서 같은 프로젝트의 새 업무를 바로 만든다. 일반 생성 양식·템플릿과 필수 필드 검사를 사용한다. 서버에서 사이클의 현재 버전과 계획·진행 중 상태를 확인하고 티켓 번호·배정·프로젝트 순서·이력과 요청 결과를 함께 저장한다. 검토 중 사이클이 바뀌면 입력을 보존하고 대상을 다시 확인한다. 응답이 끊기면 원래 요청으로 결과를 확인한다. [백로그 또는 사이클 업무 생성](API.md#백로그-또는-사이클에서-업무-생성)

업무 상세의 프로젝트 이동은 티켓 UUID와 관계를 유지하고 대상 프로젝트 순서의 끝에 발급된 업무 키를 배치한다. 연결된 업무를 함께 선택하면 상하위·선후행 연결을 따라 같은 프로젝트에서 이동할 범위를 미리 보여준다. 대상 유형과 상태, 보존 가능한 사용자 정의 값과 선택한 계획을 검증하고, 달력 차이와 계획 연결 해제를 적용 전에 표시한다. 원래 프로젝트에 묶인 역사 기록은 이동을 막는 이유와 함께 표시한다. 출발·도착의 관측 이력을 형식 83에 저장하고 이전 키로 수신한 GitLab 이벤트를 같은 업무에 연결한다.

작업 시간의 보고서 귀속은 티켓의 현재 프로젝트를 따른다. 프로젝트 이동 미리보기에서는 활성 기록 건수를 표시한다. 적용 전에 작업 시간의 버전·존재 여부를 대조하고, 이동과 함께 활성·삭제 기록의 프로젝트 및 업무 키를 갱신한다. ID·작성자·시간·메모·버전과 삭제 상태는 보존한다. Jira 작업 시간은 원본 연결과 초 단위 값을 유지한다.

Jira 이관 티켓은 원본 Jira 키, 이관 당시의 영수증·보관 기록, 상태 이력과 원본 차단 관계를 함께 유지한다. 상태와 관계의 이관 당시 근거는 출발·도착 쌍을 검증한 이동 이력에서 확인하며, 현재 일정과 보고서의 접근 범위는 이동한 프로젝트로 평가한다. 출발 프로젝트로 후속 이관을 적용하는 경우 원본 ID·키와 이동 근거를 대조해 해당 기록을 보관하고 같은 패키지의 신규 업무를 처리한다. 이동한 업무의 현재 값은 보존한다. [프로젝트 이동 API](API.md#업무-프로젝트-이동)

티켓 설명은 원문 문자열과 선택한 Markdown 서식 설정을 저장한다. 새 업무·상세·복제 양식에서 제목·목록·표·코드와 링크를 편집하고 미리 본다. 읽기 화면은 HTML을 입력한 문자로 표시하고 원격 이미지는 자동으로 읽지 않는다. Jira Wiki·ADF·검색 XML의 지원 서식은 Markdown으로 옮기고, 새로운 원본 변경분을 적용할 때 설명과 서식의 비교 기준을 함께 검사해 팀 편집을 보존한다. [Plane의 업무 설명](https://docs.plane.so/work-items/work-item-details) · [Atlassian Document Format](https://developer.atlassian.com/cloud/jira/platform/apis/document/structure/)

목록·보드·간트에서 같은 프로젝트의 공유 보기를 열 수 있다. 목록·보드의 **보기 링크 복사**로 저장된 레이아웃과 조건을 공유한다. 주소에 보기 ID를 보관해 직접 열기와 업무 상세 이동 이후에도 같은 보기를 사용한다. 선택한 보기의 저장된 조건으로 목록·보드와 간트를 오갈 수 있다. 삭제됐거나 다른 프로젝트의 보기를 가리키면 안내와 함께 업무를 숨기고 사용자가 범위를 다시 고를 수 있게 한다. 보기 편집은 처음 연 대상의 ID와 버전에 적용한다. 이름을 바꾼 뒤 이동하려면 확인을 받는다.

공유 보기의 정렬은 목표 마감일·우선순위·계획 시작일과 종료일·등록일·수정일·업무 키·제목을 여러 기준으로 저장한다. 빈 날짜는 마지막에 표시하며 정렬 값이 모두 같으면 프로젝트 순서를 사용한다. 목록의 업무 검토와 CSV, 보드의 각 그룹, 간트와 일정 내보내기, 문서의 최신 업무 목록과 업무 현황이 같은 규칙을 적용한다. 보드에서는 필드로 정렬하는 동안 상태나 담당자를 바꿀 수 있다. 프로젝트 순서를 사용하면 업무의 수동 위치를 바꿀 수 있다. [공유 보기 정렬](API.md#공유-보기의-정렬)

**Jira 필터 옮기기**는 붙여넣은 검색식을 해당 프로젝트의 일반 공유 보기 조건으로 변환한다. 원본 프로젝트를 이관 기록과 대조하고 상태·유형·팀원을 현재 ID에 연결한다. 라벨 비교는 대소문자와 값이 빈 경우의 의미를 유지한다. 명시한 마감일·등록일·수정일 정렬은 현재 Teamspace 값으로 검토해 저장한다. `Rank`, 우선순위 등 지원하지 않는 정렬은 프로젝트 순서 적용을 확인한 뒤 저장한다. 검토한 조건과 결과를 저장 시 같은 트랜잭션에서 다시 대조한다. [Jira 고급 검색](https://confluence.atlassian.com/jiracoreserver/advanced-searching-939937709.html)

원본 Jira 프로젝트를 하나로 확인할 수 있으면 현재 프로젝트의 이관 업무와 적용 영수증을 대조해 원래 상태·유형명과 ID 및 담당자·요청자 계정을 변환한다. 후속 이관 자료는 실제 반영한 값을 사용한다. 변환은 현재 프로젝트에서 고유하게 확인된 매핑을 사용하고, 미리보기에서는 이름 변경을 반영한다.

Jira `due` 날짜 비교는 목표 마감일이 있는 업무의 날짜 범위로 옮긴다. REST 자료에서 새 업무를 이관할 때도 원본 `duedate`를 저장한다. 현재 업무에 저장된 목표 마감일로 미리보기를 계산하고, 저장된 보기는 목록·보드·간트·문서 업무 목록의 공통 일정 필터를 사용한다. [Atlassian JQL 마감일](https://confluence.atlassian.com/jirasoftwareserver101/advanced-searching-fields-reference-1455427012.html#Advancedsearching-fieldsreference-Due)

Jira `priority` 조건의 이름과 ID는 하나로 확인된 원본 프로젝트의 이관 업무와 영수증에서 읽는다. 확인한 원본 값이 현재 Teamspace 우선순위 하나에 여러 개 대응하면 조건의 교집합이 그 전체를 포함할 때 변환한다. 같은 Jira ID의 이름이 바뀌어 기존 이관 수준을 유지한 경우 반영 기록으로 연결을 확인한다. 미리보기와 저장에서 팀의 편집 및 근거가 불명확한 업무가 결과를 바꾸는지 확인한다. 저장한 보기와 Confluence에서 복원한 업무 목록은 현재 Teamspace 티켓의 우선순위를 조회한다.

Jira `component` 조건은 하나로 확인된 원본 프로젝트와 이관 영수증에서 컴포넌트 이름·ID를 읽어 다중 선택 필드의 현재 선택지에 연결한다. 현재 표시 이름을 변경해도 기존 검색식을 옮길 수 있다. 여러 값을 모두 포함하는 조건과 하나 이상 포함하는 조건은 기존 사용자 정의 필드 필터로 저장한다. 원본 대응이 모호하거나 필터를 같은 결과로 표현할 수 없으면 미리보기에서 오류를 표시한다. 저장한 공유 보기와 복원한 Confluence 목록은 현재 티켓의 선택지 값을 사용한다. [Atlassian JQL 컴포넌트](https://confluence.atlassian.com/jiracoreserver/advanced-searching-fields-reference-939937719.html#Advancedsearching-fieldsreference-Component)

Confluence 문서에서 JQL 목록 매크로를 보관한 코드 블록을 선택해 일반 문서 업무 목록으로 바꿀 수 있다. 대상 프로젝트와 일치 업무, 공유 보기 저장을 검토한 뒤 원래 코드 위치에 목록을 적용한다. 문서 편집 중 다른 사용자가 선택한 원문을 변경하면 교체를 보류한다. 저장한 보기와 문서 블록은 기존의 업무·문서 저장과 복원 규칙을 사용한다.

간트에서는 공유 보기에 업무 검색·완료 숨기기·계획 연결 조건을 함께 적용할 수 있다. 선후행 계산에는 전체 프로젝트의 연결을 사용한다.

팀 메뉴의 **전체 프로젝트 간트**는 프로젝트별 업무를 공통 날짜축에 배치한다. 필터와 티켓 상세는 팀 보기 주소에 보관한다. 단일 프로젝트가 표시되면 비근무일을 표시하고, 여러 프로젝트를 표시할 때는 날짜축을 공통으로 사용한다. 일정 충돌과 근무일 이동을 각 업무의 프로젝트 달력으로 계산한다. 행의 날짜와 선후행 연결은 실제 업무에 저장한다. 여러 프로젝트의 선택 업무를 함께 이동하거나 날짜를 일괄 지정하고, 업무량 미리보기에서 이동 대상 프로젝트를 바꿔 확인한다.

프로젝트 간트와 전체 프로젝트 간트는 보드와 같은 방식으로 보이는 탭에서 저장된 버전을 확인한다. 간트에는 달력·계획·저장 보기·마일스톤·기준선·작업량·시간 예약·차단 관계의 버전도 적용한다. 날짜 입력·드래그·미리보기·상세 또는 저장이 진행 중이면 요청을 멈추며 늦게 도착한 응답에도 같은 조건을 확인한다. 수동 버튼은 날짜 입력의 포커스를 보호한다. 적용할 때 현재 보기와 확대 수준을 유지하고 시작 날짜가 이동한 기본 기간에서는 같은 날짜가 보이도록 가로 위치를 보정한다.

팀 간트의 프로젝트 간 차단 화면은 차트 업무 한쪽과 방향이 연결된 열린 업무를 조회한다. 반대편 업무가 검색이나 프로젝트 필터 밖에 있어도 소속과 제목을 표시해 티켓을 열 수 있게 한다. 두 프로젝트의 업무를 골라 기존 차단 관계를 저장한다. 어느 한쪽이 완료·취소되거나 연결이 해제되면 현재 차단에서 빠지고, 관계 수정·보관·복원은 티켓의 업무 관계와 같은 저장 흐름을 사용한다.

전체 간트의 **차트에서 연결**에서 서로 다른 프로젝트의 열린 업무를 원인·대상 순서로 고르면 두 업무를 채운 차단 관계 검토를 연다. 날짜가 미정인 업무도 행 이름으로 고른다. 막대에서 고를 때는 선행 종료일과 후행 시작일을 사용한다. 날짜 초안이 있으면 저장값과 입력을 비교해 포함할 행과 새 차단을 함께 검토한다. 대상 달력과 관련 연결의 경고를 보여주고, 최신 값이 바뀌면 두 업무와 입력을 유지한 채 다시 검토한다. 저장과 되돌리기는 날짜·관계·적용 결과를 같이 처리한다.

팀 간트의 차단 화면과 원인 티켓에서 다른 프로젝트에 새 차단 대상 업무를 만든다. 대상 프로젝트의 달력에서 원인 종료일 다음 근무일을 선택적으로 입력하고, 대상 업무 양식으로 저장한다. 원인 업무와 대상 달력의 버전을 확인해 티켓·차단·생성 요청 결과를 같이 저장한다. 적용과 재확인 후 원인 티켓의 초안과 간트 필터를 유지한다.

**프로젝트 간 후행 일정 검토**는 같은 선행 업무의 열린 차단 관계 최대 100개를 골라 저장된 선행 종료일에서 시작할 수 있다. 열린 프로젝트 간 차단은 후행 프로젝트 달력의 완료 후 시작으로 계산하고, 프로젝트 내부 일정 연결의 유형과 간격을 함께 적용한다. 선택한 대상에서 이어진 후행과 범위 밖 고정 선행을 확인하고 갈래가 모이는 업무는 한 번 계산한다. 날짜 이동은 조건을 위반한 업무만 대상으로 하고 각 업무의 근무일 기간을 보존한다. 순환·미정 날짜·고정 일정 충돌은 적용을 막으며 목표 마감일 초과는 검토에 표시한다. 연결·업무·프로젝트 규칙을 다시 확인해 결과와 되돌리기를 한 번에 저장한다.

이미 검토 범위에 들어온 업무에는 방향을 확인한 다른 Jira 차단의 선행 조건도 적용한다. 그 선행 업무가 범위 밖에 있으면 저장한 날짜를 사용한다. Jira 차단으로 검토 대상을 늘릴 때는 해당 관계를 선택한다.

프로젝트·전체 프로젝트 간트의 행 입력과 한 업무의 차트 변경 미리보기에서 입력한 선행 날짜를 **프로젝트 간 일정 검토**로 넘긴다. 열린 관계가 여러 개면 차트 필터 밖을 포함한 다른 프로젝트 업무를 선택한다. 먼저 저장된 날짜가 바뀌면 최신 값과 사용자가 고친 칸을 대조한다. 취소 때는 원래 날짜 입력과 포커스를 유지하며, 적용과 되돌리기는 선행과 후행 업무의 변경을 함께 처리한다. [프로젝트 간 후행 일정 검토](SCHEDULING.md#프로젝트-간-후행-일정-검토)

원인 티켓에서도 같은 후행 선택과 일정 검토를 연다. 시작일과 종료일을 편집한 경우 기존 저장 버전과 입력을 검토에 넘기고, 저장본이 달라지면 편집하지 않은 날짜에 최신 값을 사용한다. 적용과 결과 재확인 후 다른 속성·댓글의 초안을 유지하며, 원인 날짜가 그대로인 경우까지 원인 티켓에서 이번 일정을 함께 되돌릴 수 있다.

검토에서 선행 업무 날짜를 변경하면 해당 업무로 들어오는 조건을 확인한 뒤 새 날짜를 고정한다. 선행 업무에서 갈라지거나 다시 모이는 모든 프로젝트 내부 연결과 열린 Teamspace 차단 및 검토한 Jira 관계를 따라 계산한다. 변경된 선행·후행 업무와 적용 결과·되돌리기 기록은 한 트랜잭션으로 저장한다. 선행 업무 버전이 바뀌면 최신 날짜를 보여주고, 수정한 값은 유지한 상태로 새 버전에서 다시 검토할 수 있다.

프로젝트 간 차단 목록은 원본 방향과 양쪽 티켓이 확인된 Jira 차단 관계도 보여준다. 같은 방향의 Teamspace 차단이 이미 있으면 기존 관계를 사용한다. 선택한 Jira 관계를 현재 검토에 포함하고, 적용 전에 원본과 두 업무를 다시 확인한다. 적용과 되돌리기는 검토한 업무의 날짜를 처리하며, 티켓 상태 전이는 기존 워크플로를 따른다.

간트 HTML 보고서는 현재 차트의 날짜 범위와 순서, 표시된 업무·계획·마일스톤·기준선 기록, 표시된 업무 사이의 연결을 저장한다. 차트의 현재 조건과 저장된 날짜를 사용하며 보고서는 오프라인에서 읽고 인쇄할 수 있다. 차트 막대는 날짜 범위까지 그리며, 원래 날짜 값은 행에 그대로 표시한다.

티켓 상세에서 간트 위치를 열면 업무 행을 찾는다. 일반 프로젝트에서는 해당 프로젝트의 전체 일정, 전체 프로젝트 보드에서는 기존 필터를 유지한 팀 간트를 연다. `focusIssue`가 들어간 주소로 다시 열 수 있으며 업무 상세를 열고 닫는 동안 그 위치를 유지한다. 일정 막대가 있는 업무는 저장된 날짜로 이동하고, 날짜가 비어 있는 업무는 같은 행의 첫 빈 날짜를 입력할 수 있게 한다. 새로 읽은 업무가 사라졌으면 안내를 표시한다.

업무 목록의 CSV 내보내기는 렌더링에 사용한 검색·필터 결과와 프로젝트 순서를 그대로 사용한다. 일괄 편집에서는 현재 목록에서 선택한 행만 내보낼 수 있다. 상태·유형·담당자·계획은 표시 이름으로 기록하고, 시작일·종료일·목표 마감일은 별도 열에 둔다. CSV는 UTF-8 BOM으로 한글을 읽을 수 있게 하고, 따옴표·쉼표·줄바꿈을 이스케이프하며 수식으로 해석될 수 있는 텍스트의 시작에 작은따옴표를 붙인다. [CSV 레코드 형식](https://www.rfc-editor.org/rfc/rfc4180#section-2) · [Excel의 UTF-8 CSV 읽기](https://support.microsoft.com/en-us/excel/opening-csv-utf-8-files-correctly-in-excel) · [스프레드시트의 수식 해석](https://community.owasp.org/attacks/CSV_Injection)

업무 목록의 일괄 편집은 검색·필터로 표시된 티켓을 최대 100개 선택해 상태·우선순위·담당자·마감일·라벨을 바꾼다. 마감일은 지정하거나 해제한다. 라벨을 제거할 때는 선택한 업무에 있는 이름을 고르고, 추가한 이름은 기존 순서 뒤에 넣는다. 개별 업무와 같은 워크플로·필수 필드·담당자 배정 규칙으로 각 업무의 변경 전후와 차단 이유를 계산한다. 일괄 편집에서 담당자를 직접 선택하거나 해제하면 그 입력을 적용한다. 적용할 때 티켓과 설정 버전을 검사하고 변경·이력·알림·발신 이벤트를 한 트랜잭션에서 저장한다. 같은 미리보기 ID로 적용을 재시도하면 이미 저장된 결과를 반환한다. [Jira의 업무 일괄 변경](https://support.atlassian.com/jira-software-cloud/docs/edit-multiple-issues-at-the-same-time/)

필드 집계에서는 한 행 또는 교차표 한 셀의 업무를 페이지를 넘겨 최대 100개 선택한다. 각 페이지에서 집계의 조회 버전과 실제 업무 버전·라벨을 같은 기준으로 읽는다. 미리보기와 적용에서 저장된 보기의 조건, 집계 버전, 행과 열에 대한 선택 업무의 소속을 확인한다. 충돌하면 최신 집계에서 대상을 다시 선택한다. 저장이 완료되면 새 집계에서 변경된 상태·배정·라벨을 읽으며 응답 유실 시 같은 미리보기 ID로 적용 결과를 확인한다.

프로젝트 업무 목록과 필드 집계에서 고른 티켓에 공통 상위 업무를 지정하거나 각 티켓의 상위 연결을 해제할 수 있다. 후보는 같은 프로젝트의 현재 업무에서 검색하고, 현재 키·Jira 원래 키·이동 전 키·제목을 지원한다. 변경 전후의 상위 키와 제목을 비교하고 같은 업무, 타 프로젝트, 순환 계층이 포함되면 적용을 보류한다. 적용 직전에 선택한 상위와 상위 경로를 확인하고 기존 일괄 편집 트랜잭션과 재시도 기록을 사용한다.

프로젝트 업무 목록과 필드 집계에서 사이클·모듈·릴리스 연결을 각각 유지·지정·해제한다. 상태나 다른 속성과 함께 변경할 때 최종 업무를 기존 규칙으로 검증하고, 이전과 새 계획의 이름을 티켓별로 표시한다. 보관된 계획의 기존 연결은 해제할 수 있으며, 새 배정은 해당 계획의 소속과 종류를 확인한다. 표시한 계획의 버전이 달라지면 새 미리보기를 요청한다. 적용은 기존 일괄 편집 트랜잭션과 결과 재확인 경로를 사용하고, 계획·간트·보고서가 같은 업무 연결을 읽는다.

업무 목록과 필드 집계의 일괄 편집에서 사용자 정의 속성을 여러 개 지정하거나 지운다. 선택하지 않은 필드의 입력을 보존한다. 상태와 조건에 쓰이는 필드를 함께 바꿀 때는 변경 후 업무 양식과 워크플로로 값을 검증한다. 대상 업무의 유형에 적용되지 않거나 현재 보관된 필드, 워크플로에서 요구하지 않는 숨겨진 필드를 변경하려 하면 업무별 이유를 표시하고 적용을 막는다. 여러 선택의 순서만 같은 값으로 바꾼 경우는 변경 없음으로 처리한다.

프로젝트·전체 프로젝트 간트의 날짜 일괄 편집은 화면에 표시된 선택 업무 최대 100개를 대상으로 한다. 업무 ID와 버전을 검토에 보내고 시작일·종료일·목표 마감일의 유지·지정·비우기를 독립 적용한다. 서버는 업무의 실제 소속을 확인하며 미리보기는 각 업무의 프로젝트·전후 값·오류와 해당 달력의 선후행 경고를 표시한다. 적용 때 관련 업무·연결과 대상 프로젝트별 달력·워크플로·양식 버전을 대조한다. 모든 날짜와 되돌리기 기록, 적용 결과는 한 트랜잭션에 남기며 응답 유실 시 같은 결과를 확인한다. [Jira 계획의 날짜 일괄 편집](https://support.atlassian.com/jira-software-cloud/docs/edit-multiple-issues-in-bulk-on-your-timeline/)

날짜 일괄 편집은 선택한 행의 날짜 초안을 같은 검토로 가져온다. 포함한 초안은 해당 업무의 입력한 날짜 칸에서 공통 값을 덮어쓴다. 동료가 같은 날짜를 수정한 경우 현재 저장값을 비교하고 초안을 계속 적용할지 확인한다. 검토에서 제외한 초안은 간트에 남는다. 후행 조정을 켜면 각 프로젝트에서 영향을 받는 직접·간접 후행 업무를 검토하고, 선택한 변경과 후행 변경을 함께 적용하거나 되돌린다. 필터 밖 후행 업무도 해당 달력과 현재 근무일 기간으로 계산한다.

한 업무의 일정·연결 편집과 간트 및 새 업무 양식에서 시작일과 근무일 수로 종료일을 계산하거나, 종료일부터 거꾸로 시작일을 계산한다. 업무가 속하거나 생성될 프로젝트의 근무 요일과 예외를 적용한다. 기준일이 휴무일이어도 보존하고 근무일 수에서 제외한다. **날짜에 반영**은 현재 양식의 날짜를 채우며 행 편집은 기존 미리보기·저장·되돌리기를 사용한다.

계획 작업 시간은 업무별 정수 분으로 저장한다. 프로젝트의 근무일과 팀원별 가용 시간을 사용해 간트의 표시 기간에 대한 계획 작업량을 계산한다. 가용 시간 설정은 프로젝트 기본값, 팀원별 기본값, 날짜 예외를 지원한다. 일정 변경 미리보기에서 초과 날짜를 비교하며 초과 여부로 업무 날짜를 자동으로 바꾸지 않는다.

프로젝트 간트에서는 담당자 작업량의 초과를 줄일 일정 변경을 계산해 검토 후 적용한다. 표시 기간과 선택한 담당자를 기준으로 우선순위가 낮은 업무부터 뒤로 옮길 후보를 찾고, 근무일 수·마감일·선후행 연결을 지킨다. 변경 전후 초과 시간과 프로젝트 계획 종료일, 남는 초과 날짜를 함께 표시한다. 같은 미리보기를 재시도하면 적용 결과를 돌려주며, 업무·연결·가용 시간·달력·워크플로 설정이 바뀌면 다시 계산한다. [Microsoft Project의 자원 초과 조정 방식](https://support.microsoft.com/en-us/project/distribute-project-work-evenly-level-resource-assignments)

프로젝트 간 작업량은 각 프로젝트의 달력에 따라 배분한 계획 시간을 팀원의 날짜별 합계로 보여준다. 비교 기준으로 팀 근무일과 개인 예외를 적용한 하루 가용 시간을 한 번 사용한다. 기본·팀원별·날짜별 가용 시간과 공통 달력 예외를 자체 백업에 보존한다. 날짜별 배분에서 원래 업무를 바로 연다.

프로젝트와 프로젝트 간 작업량 화면은 해당 조회 범위에서 초과한 날짜·담당자를 초과 시간순으로 보여준다. 항목을 선택하면 표의 날짜와 원인 업무를 표시한다. 상세에서 일정 조정을 열면 해당 담당자와 현재 기간이 선택된다. 프로젝트 간 화면은 이동 대상으로 고른 프로젝트도 사용한다.

시간 배정은 티켓 ID와 팀원 ID에 연결한다. 팀 일정은 서울 시간의 날짜별로 조회하고, 서버는 분 단위 UTC 시각과 편집 버전을 저장한다. 모든 프로젝트에서 같은 팀원의 시작·종료 구간이 겹치는지를 같은 저장 트랜잭션에서 검사한다. 날짜 단위 계획 작업량과 업무 시간 기록은 각자 기존 방식으로 계산한다. 휴지통의 배정은 시간을 점유하지 않으며, 충돌하는 기간에 업무를 복원하면 편집할 수 있는 재검토 상태로 돌려준다. 자체 백업 형식 30은 배정 ID·버전·재검토 상태를 보존한다.

프로젝트 간 과부하 조정은 모든 프로젝트의 업무를 같은 팀 가용 시간에 합산한다. 사용자가 고른 프로젝트의 업무만 이동 대상으로 삼고, 각 업무의 기간·마감과 해당 프로젝트 근무일·선후행 조건을 보존한다. 조정 전후의 과부하와 변경된 각 프로젝트의 계획 종료일을 검토하고 적용한다. 작업량을 제공한 모든 프로젝트의 업무·달력·워크플로와 팀 가용 시간의 변경을 적용 전에 확인한다. 적용과 전체 되돌리기는 기존 일정 변경 기록을 사용한다.

사이클·모듈·릴리스는 프로젝트별 독립 항목으로 관리하고 업무에는 ID를 저장한다. 이름은 참조에서 생성하며, 이름 변경과 일괄 업무 연결도 버전 충돌을 검사한다. API 키는 자동화 경로의 작업자·읽기/쓰기·프로젝트 범위를 고정한다. 복잡한 로그인·SSO 계정 체계는 추가하지 않는다.

진행 중 사이클을 완료할 때 연결된 업무를 프로젝트의 워크플로 분류로 나눈다. 완료·취소 업무는 이전 사이클에 남기고, 미완료 업무는 같은 프로젝트의 계획·진행 중 사이클 또는 사이클 미지정인 백로그로 넘긴다. 휴지통 업무는 이월 대상에서 제외한다. 티켓 날짜·상태·계층·순서와 선후행 연결을 보존한다. 미리보기는 티켓별 이월 대상과 필수 속성 오류를 보여준다. 적용 전 작업자와 계획 버전·업무 구성 및 버전·워크플로·양식 설정을 확인하고 완료·연결 변경·이력·적용 결과를 함께 저장한다. [Jira 스프린트 완료 방식](https://support.atlassian.com/jira-software-cloud/docs/enable-sprints/)

완료 트랜잭션은 당시 사이클 일정, 작업자·시각, 완료·취소·이월 업무의 제목·상태·담당자와 이월 대상도 보관한다. 같은 완료 요청은 같은 기록을 반환하고 다시 연 사이클을 완료하면 별도 기록을 남긴다. 계획 상세와 프로젝트 전체에서 기록을 조회한다. 이후 원래 계획이나 업무가 삭제돼도 저장한 값을 유지하며, 실제 완료 기록이 있는 시점부터 조회한다. [Jira 스프린트 보고서](https://support.atlassian.com/jira-software-cloud/docs/view-and-understand-the-sprint-report) · [Plane 사이클 관리](https://docs.plane.so/core-concepts/cycles)

사이클 진행 추이는 보고 이력의 사이클 연결·추정치·상태 전이를 서울 날짜별로 재구성한다. 초기 관측과 복원 당시 업무 상태는 범위의 출발점으로 사용한다. 범위 추가·제외, 완료·취소·재개, 추정치 변경과 워크플로 상태 분류 변경에는 당시 업무 키와 제목을 남긴다. 업무 수와 스토리 포인트를 전환하고 날짜별 변경 근거를 연다. 관측 시작 이전과 복원 사이에 수집하지 않은 기간은 부분 관측 또는 미관측으로 표시한다. [Jira 번다운 차트](https://support.atlassian.com/jira-software-cloud/docs/view-and-understand-the-burndown-chart/)

간트에서 계획 기간·목표일·업무 연결을 확인하고, 연결된 업무만 보거나 업무를 선택해 연결을 변경할 수 있다. 업무와 계획의 날짜는 각각 저장하며, 목록의 기간 밖 집계로 차이를 확인한다. 계획 일정 저장은 계획 버전을 검사하고 연결 일괄 적용은 계획과 각 업무의 버전을 함께 검사한다. 계획 상세와 간트는 같은 항목 ID로 이동한다.

계획 상세에서 고른 항목은 주소에 기록하므로 간트·릴리스 준비 점검을 연 뒤 같은 선택으로 돌아간다. 연결 업무와 사이클·백로그 카드는 저장한 시작일·종료일을 표시한다. 업무별 간트 바로가기는 첫 빈 날짜 또는 저장 일정 행을 찾는다. 연결 업무에서 열면 해당 계획에 연결된 업무를 표시하고, 사이클 보드로 돌아갈 때 선택한 사이클과 업무 검색을 복원한다.

계획 일정 함께 이동은 지정한 달력일·근무일 수로 계획 날짜와 해당 업무 날짜의 미리보기를 만든다. 업무를 함께 이동할 때 계획 버전, 연결된 업무와 선후행 조건, 관련 설정을 고정한다. 계획·업무 날짜와 이력·되돌리기 기록을 같은 트랜잭션에서 저장하며 원래 미리보기 ID로 적용 결과를 다시 확인할 수 있다.

업무 유형·사용자 정의 필드·선택지는 프로젝트별 고유 ID로 참조한다. 이름 변경은 값을 바꾸지 않으며 사용 중인 항목을 제거해 자료를 잃지 않는다. 입력 종류와 범위·필수 규칙은 서버에서 검사하고 목록·상세·간트·API·백업이 같은 설정을 사용한다. 공유 보기는 형식에 맞는 필드 조건과 결합 방식을 저장한다. 목록·보드와 프로젝트 범위 자동화 조회는 같은 비교 규칙을 적용한다. 저장된 조건이 사용하는 필드·선택지는 보기에서 참조를 해제한 뒤 삭제할 수 있다.

사용자 정의 필드는 표시할 상태와 기준 체크 또는 단일 선택 값으로 티켓 양식에 표시할 수 있다. 기준 필드가 표시되고 입력한 값까지 일치해야 하며, 연결된 조건은 순환 없이 평가한다. 표시 중인 필드의 필수 입력과 별개로 워크플로의 상태·전이별 필수 규칙을 적용한다. 숨겨진 값은 보존한다. 표시 조건에 쓰는 상태·필드·선택지는 활성 참조가 해제되면 제거할 수 있다. 자체 백업 형식 34에 표시 조건을 보존한다.

일정은 프로젝트 달력의 근무일로 계산하며 변경은 미리 검토한다. 자동 제안은 업무·달력·의존성·워크플로의 버전을 고정하고, 같은 트랜잭션 안에서 날짜·이력·되돌리기·적용 기록을 저장한다. 스프레드시트 붙여넣기는 같은 프로젝트의 업무 키로 날짜와 선후행 연결을 찾는다. 변경 전후와 연결 경고를 검토하고, 제안된 연결을 모두 반영한 그래프의 순환 여부를 검사한 뒤 날짜와 연결을 함께 적용한다. 기준 계획은 당시 날짜와 달력을 변경하지 않고 보존하며 현재 계획과 비교한다. 마일스톤의 현재 업무 연결과 과거 캡처 기록을 구분한다.

프로젝트 간트의 이정표는 연결 업무가 저장된 현재 계획으로 목표일에 맞춰져 있는지 표시한다. 워크플로에서 완료·취소에 속한 업무를 먼저 분류하고, 나머지를 계획 종료일 기준으로 미정·이내·이후로 표시한다. 확인할 수 없는 연결은 건수만 표시한다. 화면의 검색이나 공유 보기 밖에 있는 업무도 세고, 해당 티켓이나 간트 종료일로 이동할 수 있다. 티켓에서 이정표 주소를 다시 열 수 있다. 달성 여부는 이정표에 수동으로 저장한 값을 사용한다. [이정표 연결 업무](SCHEDULING.md#이정표-연결-업무-확인)

이정표 편집에서는 같은 프로젝트 업무를 현재 키·제목과 확인된 이전 키로 검색한다. 검색과 페이지를 바꿔도 선택한 현재 업무 ID를 유지한다. 같은 차트에서 후보 티켓을 열고 이전·다음으로 검토하거나 닫으면, 이정표 입력과 연결 선택 및 간트 행의 날짜 초안을 유지한다. 저장 대상이 이동하거나 삭제되면 최신 목록에서 연결할 수 없는 선택만 해제할 수 있다. 다른 화면 또는 작업자로 이동할 때는 작성 중인 입력을 확인한다.

일정 붙여넣기에서 한 후행 업무의 여러 선행 연결은 연결마다 한 행씩 입력한다. 같은 업무의 시작일·종료일·목표 마감일을 모아 범위·필수 필드를 한 번 검증한다. 중복 연결과 같은 날짜 열의 충돌은 원본 행 번호를 표시한다. 검토 후 날짜와 연결의 추가·변경·해제를 한 번에 적용하고 되돌린다. [일정 붙여넣기](SCHEDULING.md#스프레드시트에서-날짜와-업무-연결-붙여넣기)

스프레드시트 붙여넣기에서 후행 검토를 선택하면 최종 선후행 연결과 프로젝트별 달력으로 숨겨진 후행 업무까지 계산한다. 바꾼 시작·종료일을 고정하고 조정한 업무의 기존 근무일 기간과 입력한 마감일을 유지한다. 관련 업무와 연결이 달라지면 미리보기를 다시 계산한다. 직접 입력, 연결 변경, 후행 조정은 한 번의 적용과 되돌리기로 처리한다.

간트 편집용 TSV는 저장된 시작일·종료일·목표 마감일과 선행 업무의 키·연결 유형·근무일 간격을 붙여넣기 형식으로 구성한다. 현재 표시된 선택 업무를 우선 사용하며, 선택이 없으면 표시된 업무를 사용한다. 선행 업무가 표시 범위 밖에 있어도 연결 정보에 포함한다. 전체 프로젝트 간트에서는 프로젝트 필터에 따라 한 프로젝트 또는 여러 프로젝트의 일정을 내려받고 편집한다. 미리보기는 현재 키를 우선하고 유일하게 확인된 이전 키를 같은 범위에서 연결한다. 키 선택 근거와 현재 업무를 함께 표시하고 적용 직전에 다시 대조한다. 같은 프로젝트 안에서 선후행 연결을 검토하고, 모든 프로젝트의 날짜와 연결을 한 번에 적용·되돌린다.

간트의 기존 업무 행과 티켓 상세에서 시작일·종료일·목표 마감일과 여러 선후행 연결을 같은 양식으로 검토한다. 같은 프로젝트의 업무는 현재 보기의 필터에서 가려져 있어도 검색할 수 있다. 새 연결의 방향을 지정하고 기존 연결의 유형·간격을 수정하거나 해제할 수 있다. 연결마다 입력 순서, 변경 전후와 달력에 따른 선후행 경고를 확인한다. 같은 방향의 중복 입력과 변경을 모두 반영한 연결의 순환 여부를 검사한다. 관련 업무·연결과 프로젝트 설정을 다시 검사하고 날짜와 연결을 함께 적용하거나 되돌린다. 응답을 잃으면 같은 미리보기 ID로 적용 결과를 확인한다.

간트에서 행 날짜를 입력한 뒤 **선택 업무에서 연결**이나 **차트에서 연결**을 열면 기준 업무의 입력과 연결을 같은 양식에 전달한다. 차트에서 같은 프로젝트의 두 행을 골랐고 양쪽에 날짜 입력이 있으면 두 업무의 날짜와 연결을 한 번에 적용하거나 되돌린다. 함께 저장하는 두 업무의 날짜를 고정해 후행 일정을 제안한다. 선행 업무의 초안을 간트에 둘 때는 현재 저장 날짜를 계산에 사용한다. 관련 업무가 먼저 바뀌면 최신 저장 날짜를 다시 읽고 입력을 유지해 검토한다.

간트 행의 시작일·종료일 입력은 같은 브라우저 탭에서 새로고침해도 보존한다. 작업자와 간트 범위별로 원래 프로젝트·업무 버전·저장 날짜·입력 날짜만 보관하고, 현재 보기에서 가려진 업무의 초안도 검토할 수 있게 표시한다. 바꾼 날짜가 새로 읽은 저장본에 모두 반영된 경우 초안을 정리한다. 다른 값이 저장된 경우 입력을 유지하고 최신 일정과 비교해 검토한다. 백업 가져오기는 새 워크스페이스 세대를 설정해 이전 초안을 다시 읽지 않게 한다.

같은 프로젝트 또는 전체 프로젝트 간트에서 티켓 상세를 열고 이전·다음으로 이동하거나 닫아도 각 행의 날짜 초안을 유지한다. 상세 날짜를 바꾸지 않았다면 일정과 연결 편집에서 해당 행의 수정 칸과 입력 시작 버전을 가져온다. 적용 결과에서 해당 행의 모든 입력값이 저장됐을 때만 간트 초안을 정리한다. 다른 행의 초안과 상세의 제목·댓글 입력은 이어서 편집할 수 있다.

날짜 입력으로 여는 간트 주소는 초안 복구가 끝난 뒤 해당 날짜 칸에 초점을 둔다. 저장으로 일정 막대가 생겨도 바로가기의 초점 이동은 다시 실행하지 않는다.

티켓 상세에서 편집기를 열 때 직접 바꾼 날짜 칸과 시작 버전을 전달한다. 양쪽에서 같은 날짜를 다르게 변경하면 현재 저장값을 입력 칸 옆에서 확인하고 그 값으로 바꿀 수 있다. 창을 닫으면 기존 상세 입력을 유지한다. 적용한 일정과 연결을 새로 읽은 저장 버전과 대조한 뒤 상세에 반영한다. 동료가 쓴 다른 필드는 최신 값을 유지하고 사용자가 별도로 작성한 필드와 댓글을 이어서 편집할 수 있다. 날짜 외 같은 필드를 양쪽에서 다르게 바꾼 경우에는 이전 편집 버전으로 충돌을 유지한다. 상세에서 마지막 적용을 되돌릴 때는 그 뒤에 입력한 날짜 초안도 유지한다. 원래 티켓과 배경 보기는 계속 열린 상태로 유지한다.

티켓 상세의 일반 저장에서 세 날짜가 달라지면 서버가 간트와 같은 선후행 및 프로젝트 간 차단 경고를 계산한다. 날짜 전후와 다른 업무에 필요한 날짜를 검토한 뒤 일반 저장으로 제목·상태 등과 함께 적용한다. 저장 직전에 업무와 관련 일정·연결·달력 버전을 대조하고, 근거가 바뀌면 입력을 유지해 다시 검토한다. 경고가 없으면 같은 저장 흐름으로 바로 적용한다. [티켓 저장 전 일정 검토](SCHEDULING.md#티켓-저장-전-일정-검토)

선후행 연결은 관계 유형에 따라 각 업무의 시작일 또는 종료일을 사용한다. 티켓 상세에서 같은 프로젝트의 업무를 키나 제목으로 찾아 연결하고 방향·유형·간격을 수정하거나 해제한다. 연결 방향을 바꿀 때 같은 ID를 유지하며 전체 의존성의 순환 여부를 검사한다. 간트에서 선행·후행 업무의 끝점이나 행을 선택하면 연결 검토 창에 두 업무와 유형이 채워진다. 같은 방향의 기존 연결은 간격을 불러와 수정한다. 간트에서 기준 업무를 하나 선택하면 현재 보기에서 가려진 같은 프로젝트 업무도 키나 제목으로 찾아 연결할 수 있다. 자동 일정은 시작·종료 조건을 함께 만족하면서 근무일 기간을 유지한다. 연결 변경은 버전을 검사하며 이미 만든 일정 제안은 새로 계산한다. 자체 백업 형식 21에 연결 유형과 버전을 보존한다.

차트의 날짜 선택은 일정 미정 업무에 필요한 날짜를 입력하고 이미 일정이 있는 업무의 기간을 교체한다. 한쪽 날짜만 있으면 그 값을 기준으로 빈 날짜를 고른다. 양쪽 날짜를 고를 때는 선택 순서를 정렬하고 현재 일정과 같은 범위는 저장하지 않는다. [차트에서 날짜 선택](SCHEDULING.md#차트에서-날짜-선택)

날짜를 직접 저장하거나 이동·일괄 편집·붙여넣기·행 편집에서 바꿀 때는 열린 프로젝트 간 차단 관계도 확인한다. 선행 종료일 또는 후행 시작일이 바뀌면 후행 프로젝트의 달력으로 충돌과 미정 날짜를 계산한다. 양쪽을 한꺼번에 바꾸면 두 제안 날짜를 사용한다. 직접 입력에서 경고가 생기면 적용 전에 미리보기를 표시하고, 창을 닫으면 입력을 유지한다. 검토 뒤 관계가 추가되거나 관련 업무·달력이 바뀌면 최신 조건으로 다시 확인한다. [수동 일정 변경](SCHEDULING.md#수동-일정-변경-검토와-되돌리기)

수동 막대 이동·기간 조정·일괄 이동·날짜 선택과 날짜 칸 직접 저장은 서버가 만든 제안을 적용한다. 선택 업무, 직접 연결된 선행·후행과 각 프로젝트의 달력·워크플로·양식이 바뀌면 같은 입력을 최신 상태로 다시 검토한다. 날짜 저장과 되돌리기, 작업자별 적용 결과를 함께 기록한다. 응답을 받지 못하면 같은 미리보기 ID로 결과를 확인한다. [수동 일정 변경](SCHEDULING.md#수동-일정-변경-검토와-되돌리기)

프로젝트 간트와 전체 프로젝트 간트 및 티켓 일정·연결 편집은 적용을 시작한 화면과 작업자를 기준으로 마지막 변경을 다시 찾는다. 화면을 다시 열어도 서버에 저장한 최근 7일의 기록을 사용한다. 최신 대상 버전이 일치할 때 날짜·연결·계획을 한 번에 복원한다. 응답 유실 뒤 같은 되돌리기 ID를 다시 보내면 완료 여부와 결과를 확인할 수 있다.

간트 날짜 칸의 입력은 행별로 유지한다. 행의 저장 버튼이나 Enter로 해당 날짜의 저장을 요청한다. 처음 검토하거나 적용할 때 업무 버전이 바뀌었으면 입력을 유지한 상태에서 검토를 다시 열 수 있다. 행 입력, 막대 한쪽 조정 또는 차트에서 빈 날짜 하나를 고르는 경우 미편집 날짜는 최신 저장값을 사용한다. 같은 행의 **일정과 연결 편집**은 변경한 날짜 칸을 가져와 저장된 업무와 비교한다. 창에서 적용하면 반영한 행의 입력을 정리하고, 닫으면 행에서 입력하던 날짜를 이어서 편집할 수 있다.

프로젝트와 전체 프로젝트 간트의 **입력한 날짜 N건 검토**는 서로 다른 날짜를 입력한 행마다 기존 일정과 일치하는 버전을 확인한다. 다시 검토할 때 변경한 칸만 입력값을 사용한다. 새로고침 뒤 현재 보기의 조건에서 빠진 업무는 날짜 입력을 유지하는 동안 표시한다. 서버는 각 프로젝트의 선후행 일정 경고를 만들고, 검토한 날짜 전체를 한 번에 적용하거나 되돌린다.

여러 행 날짜 미리보기에서 **후행 일정 함께 검토**를 선택하면 입력한 날짜 쌍을 고정하고, 각 프로젝트의 연결과 달력으로 후행 업무 전체를 계산한다. 공통 후행은 모든 선행 조건을 함께 검토하고 현재 날짜가 조건을 충족하면 유지한다. 변경하는 후행은 같은 표에 표시한다. 입력 날짜와 고정 일정의 충돌을 보류하고, 검토한 업무·연결·프로젝트 규칙을 적용 전에 확인한다. 입력과 후행 변경은 같은 적용 요청과 되돌리기 기록으로 저장한다. [여러 행 날짜 미리보기](SCHEDULING.md#수동-일정-변경-검토와-되돌리기)

간트 차트는 업무의 계획 기간과 목표 마감일을 별도로 표시한다. 마감일 검토는 현재 표시된 업무를 계획 종료일과 목표 마감일의 차이 및 종료일 입력 여부로 분류한다. 표시 범위 밖 마감일로 이동하면서 날짜 초안을 보존한다. 마감일 입력을 열면 같은 행의 시작일·종료일 초안을 가져오고 일반 행 편집의 미리보기·동시 변경 검사·되돌리기를 적용한다. 다른 행의 날짜 입력은 유지한다. [목표 마감일 검토](SCHEDULING.md#목표-마감일-검토)

간트에서 한 업무의 날짜를 직접 입력하거나 막대·차트 날짜를 조정하면 같은 변경 흐름에서 후행 일정을 검토할 수 있다. 기준 업무의 입력 날짜를 보존하고 전체 프로젝트 연결에서 필요한 만큼 후행 날짜를 계산한다. 버전·선후행 조건·업무 양식 검사를 통과하면 기준과 후행 날짜를 한 트랜잭션으로 저장한다. 결과가 끊기면 같은 제안을 조회하며 변경한 날짜 전체를 한 번에 되돌린다. [후행 일정 검토](SCHEDULING.md#날짜와-후행-업무-함께-변경)

간트 행과 티켓 상세의 **일정과 연결 편집**에서는 같은 검토에 직접·간접 후행 일정을 넣을 수 있다. 서버는 편집 중인 연결을 모두 반영한 그래프와 기준 업무의 입력 날짜로 계산한다. 이미 제약을 충족하는 일정은 보존하고, 변경할 후행 업무만 작업 기간을 유지해 필요한 만큼 늦춘다. 계산에 영향을 준 업무와 연결이 바뀌면 검토를 다시 요청하며, 확인한 날짜·연결·되돌리기 기록과 적용 결과를 함께 저장한다. [일정과 연결 편집](SCHEDULING.md#한-업무의-날짜와-연결-함께-편집)

간트에서 선택한 업무나 티켓 상세를 출발점으로 새 선행·후행 업무를 만든다. 프로젝트 달력의 네 연결 유형과 간격을 적용해 기존 후행 업무가 유지되는 가장 늦은 선행 업무 날짜 또는 새 후행 업무의 가장 이른 날짜를 제안한다. 날짜는 직접 입력하거나 미정으로 둘 수 있다. 기존 업무와 달력의 버전을 확인한 뒤 일반 업무 생성의 번호·양식·이력·알림과 선후행 연결을 같은 트랜잭션에 저장한다. 같은 작업자의 동일한 요청을 재전송하면 기존 생성 결과를 돌려준다. [새 선행 업무 만들기](SCHEDULING.md#새-선행-업무-만들기) · [새 후행 업무 만들기](SCHEDULING.md#새-후행-업무-만들기)

간트 일정 여유 분석은 저장 일정과 프로젝트 근무일을 기준으로 연결 조건을 충족하는 가장 이른 전체 완료일을 계산한다. 각 업무를 그 완료일 안에서 늦출 수 있는 근무일 수와 여유 0일 연결을 표시한다. 날짜가 부족한 연결 일정을 제외한 경우 계산 범위를 알려준다. 간트와 프로젝트 범위 API는 같은 읽기 전용 계산을 사용한다.

GitLab 상태 자동화는 명시적으로 활성화한 규칙과 현재 워크플로의 검증을 함께 적용한다. 수신 이벤트·상태 변경·이력·외부 웹훅 대기는 같은 트랜잭션에서 저장한다. 배포 성공 규칙은 저장소와 대소문자를 구분하는 환경 이름을 지정한다. 인증된 성공 웹훅의 발생 시각과 같은 저장소의 자동 연결 근거를 함께 검증한다. 배포 ID별 처리 기록은 당시 대상 업무가 없어도 저장해 재전송으로 추가 실행되는 일을 막는다. 같은 환경의 이미 알려진 더 최근 성공 또는 같은 시각의 다른 성공이 있으면 상태 변경을 생략한다. 실행에는 배포 ID와 환경을 보관한다. 외부 전송은 서명과 영속 재시도를 사용하며 수신 측은 이벤트 ID로 중복을 처리한다. 자체 백업 형식 75로 복원한 배포 규칙도 비활성 상태로 시작한다. [GitLab 배포 웹훅](https://docs.gitlab.com/user/project/integrations/webhook_events/#deployment-events)

파이프라인 성공·실패 규칙은 참조 이름 패턴에 푸시·MR·예약 등의 실행 유형과 브랜치·태그 조건을 더할 수 있다. 실행 유형은 선택 목록 중 하나와 일치해야 하며, 참조 유형까지 지정하면 두 조건을 함께 만족해야 한다. 비워 둔 조건은 모두 허용한다. 인증 수신 시 확인한 값으로 실행을 평가하고, 티켓의 GitLab 단건 조회에서도 같은 규칙으로 상태를 제안한다. 저장 전 미리보기에서는 두 값을 각각 지정하거나 미확인으로 두어 평가 이유를 확인한다. 적용하거나 기록된 실행에는 확인한 유형을 표시하며, 자체 백업 형식 112에서 규칙과 실행 근거를 보존한다. 복원한 규칙은 비활성으로 시작한다. [GitLab 실행 유형](https://docs.gitlab.com/ci/jobs/job_rules/#ci_pipeline_source-predefined-variable) · [GitLab 파이프라인 웹훅](https://docs.gitlab.com/user/project/integrations/webhook_events/#pipeline-events)

티켓 상세에서 자동화 실행과 차단 이유를 조회한다. 새 실행에는 당시 규칙 이름·저장소·객체·브랜치와 상태 이름을 보관한다. 현재 상태와 버전·전이가 맞는 최근 차단 결과는 기존 티켓 편집기에 목표 상태를 제안한다. 팀원은 작성 중인 다른 필드를 유지하며 일반 저장으로 변경한다. 실행 기록과 순서는 자체 백업 형식 64에서 복원한다.

상태별 담당자 배정은 상세 편집·보드 이동·업무 API·인증된 GitLab 자동화의 실제 상태 전이에 적용한다. 출발·도착 상태와 업무 유형이 맞는 활성 규칙을 우선순위 숫자와 ID 순으로 평가해 첫 규칙을 사용한다. 같은 저장에서 담당자를 직접 바꾸거나 비우면 그 값을 우선하며, 미배정에만 적용하는 규칙은 기존 담당자를 유지한다. 제안된 담당자를 포함해 워크플로를 검증한 뒤 티켓 버전·배정 결과·활동 이력·알림·발신 이벤트를 한 트랜잭션에서 저장한다. 미리보기는 입력한 한 규칙의 결과와 전이 차단 이유를 조회한다. 형식 32 자체 백업의 복원은 규칙을 비활성 상태로 시작하며, 전체 데이터 백업은 실행 기록도 보존한다.

GitLab 저장소는 연결 설정 화면에서 이름·그룹으로 페이지를 넘겨 찾거나 하위 그룹을 포함한 전체 경로로 조회한다. 확인한 저장소 ID를 입력 중인 연결 설정에 추가하고, 기존 미리보기와 명시적 저장 절차로 연결한다. 주소나 읽기 토큰이 바뀌면 이전 검색을 취소한다. 저장한 토큰은 같은 서비스 주소에서만 재사용한다. [GitLab Projects API](https://docs.gitlab.com/api/projects/#list-all-projects)

GitLab 연결 미리보기는 현재 입력한 주소·저장소·읽기 토큰으로 저장소별 조회 가능 여부와 티켓 연결을 계산한다. 설정·연결·업무를 읽기 전용으로 확인한다. 실제 수동 동기화에서도 같은 연결 계산을 쓰고, 파이프라인이 MR에서 티켓 키를 가져올 때는 브랜치와 head SHA가 함께 일치해야 한다. 조회가 완료된 저장소는 하나의 저장 트랜잭션에 반영한다. 실패한 저장소와 사유를 별도로 알리고, 같은 연결 설정에서 실패한 저장소를 다시 조회할 수 있다.

저장한 연결의 활동·배포 동기화 결과는 종류별로 저장소당 한 건을 유지한다. 화면을 다시 열어도 최근 완료 결과와 마지막 성공 시각을 확인할 수 있다. 실패한 활동 저장소는 시도 당시의 브랜치·커밋 이력 옵션으로 다시 실행한다. 결과 확인은 Teamspace에 저장된 요약을 읽는다. 연결 주소·읽기 토큰·저장소 범위나 Jira 매핑이 바뀌면 영향받는 요약을 초기화한다.

웹훅 수신 확인은 저장소마다 마지막 인증 수신과 Push·MR·Pipeline·배포 각각의 중복을 제외한 최근 처리 요약을 보관한다. 이벤트가 업무와 연결되지 않아도 수신 사실을 확인할 수 있다. 재전송은 마지막 수신에 기록하고 이전 업무 연결·배포 반영 건수는 이벤트별로 확인할 수 있다. 주소·웹훅 자격 증명을 바꾸면 다시 수신을 확인하며, 저장소 범위와 Jira 매핑 변경은 영향받은 저장소의 요약을 초기화한다. 브라우저에서 수신 상태를 조회하는 동안 설정 입력과 펼친 저장소를 유지한다.

프로젝트 웹훅 설정은 배포 시 검증한 Teamspace HTTPS 수신 주소와 저장한 GitLab 연결을 사용한다. 저장소의 웹훅 목록을 끝까지 읽고 같은 경로의 등록과 이벤트·TLS·브랜치 필터·전송 상태를 표시한다. 누락을 확인한 저장소는 같은 작업자와 설정 버전으로 등록한다. 등록 직전 목록을 다시 읽고 관리 토큰과 다시 입력한 인증 값을 해당 GitLab 액세스에만 사용한다. 외부 쓰기 결과를 확인할 수 없으면 재시작 후에도 미확인 시도를 기억하고 목록으로 확인한다. 등록과 인증된 이벤트 수신은 각각 확인한다. [GitLab 프로젝트 웹훅 API](https://docs.gitlab.com/api/project_webhooks/)

프로젝트 웹훅의 **최근 전송 확인**은 저장한 저장소에서 현재 수신 주소에 정확히 일치하는 훅을 대조한다. 요청하면 GitLab 전송 이력을 읽고 이벤트·HTTP 상태·시각·소요 시간을 표시한다. 안정적인 메시지 ID의 해시를 같은 연결·저장소·이벤트·수신 주소에서 인증한 기록과 대조한다. 같은 메시지의 재전송은 같은 수신 요약에 연결된다. 저장소 전체의 마지막 수신도 함께 표시한다. 조회 도중 연결 설정이 바뀌면 이전 결과를 폐기한다. [GitLab 프로젝트 웹훅 전송 이력 API](https://docs.gitlab.com/api/project_webhooks/#list-project-webhook-events) · [GitLab 전송 헤더](https://docs.gitlab.com/user/project/integrations/webhooks/#delivery-headers)

배포 기록은 GitLab 인스턴스·저장소·배포 ID와 발생 시각을 기준으로 저장한다. 인증된 배포가 먼저 들어오면 저장소 이력에 나타난다. 이후 연결된 커밋·파이프라인의 전체 SHA 또는 대상 저장소가 확인된 병합 MR의 병합·스쿼시 SHA가 일치하면 티켓에도 표시된다. 배포 화면은 환경·상태·시각과 GitLab 작업 또는 커밋 주소를 표시한다. GitLab 19 이전의 시간대가 포함된 웹훅 발생 시각은 ISO 8601로 정규화한다. [GitLab 19 웹훅 변경](https://docs.gitlab.com/update/versions/gitlab_19_changes/#webhook-payload-timestamps-changed-to-iso-8601-format)

**배포 조회 미리보기**는 GitLab 연결 초안의 주소·읽기 토큰·선택 저장소로 최근 배포와 성공한 배포의 포함 MR을 읽는다. 조회 집계와 빈 목록, 일부 조회와 권한·요청 한도 문제를 표시한다. 배포와 동기화 이력은 실제 동기화 실행 때 기록한다. 확인 중 입력이나 저장된 연결 버전이 바뀌면 이전 결과를 폐기한다. [GitLab 환경별 배포](API.md#gitlab-환경별-배포)

저장소별 배포 이력 동기화는 GitLab에서 최근 배포 50건과 성공한 배포의 포함 MR을 읽는다. MR의 숫자 ID·IID·대상 저장소가 기존 티켓 연결과 일치하면 같은 배포를 함께 표시한다. 조회 권한·한도·일시 오류로 전체 관계를 읽지 못하면 확인한 관계를 보존하고 누락 가능성을 안내한다. 동기화 중 갱신한 웹훅 상태와 연결 설정 버전을 저장 직전에 확인한다. 자체 백업 형식 74는 배포 상태의 동기화 출처와 포함 MR을 보존한다. [GitLab의 배포별 MR 추적](https://docs.gitlab.com/ci/environments/deployments/#track-newly-included-merge-requests-per-deployment)

티켓에 연결된 배포는 **이 배포로 상태 검토**에서 한 건을 다시 확인한다. GitLab 저장소·배포 ID·환경·전체 SHA를 대조하고 같은 환경의 최신 성공과 실제 작업 완료 시각을 확인한다. 현재 티켓의 자동 연결이 같은 SHA 또는 직접 조회한 포함 MR에 해당하면 성공 배포 규칙으로 상태 변경을 제안한다. 최신 성공 여부와 완료 시각을 확인할 수 없으면 현재 배포 상태를 표시한다. 작업자는 일반 티켓 편집에서 제안을 저장하며 그때 배포와 연결을 다시 대조한다. [GitLab 배포 API](https://docs.gitlab.com/api/deployments/)

기존 브랜치·커밋·MR·파이프라인을 티켓 상세에서 주소로 직접 연결할 수 있다. GitLab 읽기 API에서 저장소 ID와 브랜치 이름, 전체 커밋 SHA 또는 해당 항목 ID를 검증하고 정규 주소를 저장한다. 웹훅과 동기화는 같은 링크의 상태를 갱신한다. 직접 연결한 브랜치도 인증된 푸시에 따라 최신 확인 SHA와 삭제 상태를 표시한다. 상태 자동화는 티켓 키로 확인한 연결에 대해 기존 규칙을 평가한다. 같은 연결이 나중에 티켓 키로 확인되면 같은 행에 자동 연결을 기록한다. 백업과 휴지통 복원은 연결을 보존하고 해제 확인용 식별자를 새로 발급한다. [GitLab 브랜치 조회](https://docs.gitlab.com/api/branches/#retrieve-a-repository-branch) · [GitLab 커밋 조회](https://docs.gitlab.com/api/commits/#retrieve-a-commit)

티켓 상세의 **GitLab에서 상태 확인**은 이미 연결된 MR·파이프라인·브랜치 중 최근 20건을 저장한 읽기 자격 증명으로 조회한다. 저장소 ID와 원본 ID 또는 정확한 브랜치 이름을 대조한다. 성공한 브랜치 조회는 기존 연결에 HEAD를 기록하고 그 SHA를 후속 푸시의 기준으로 삼는다. 조회 중 같은 브랜치의 더 최신 관측이 반영되면 최신 값을 보존하고 재확인을 안내한다. GitLab이 브랜치를 찾지 못하거나 읽기를 거부하면 기존 관측을 보존한다. 상태 자동화는 인증된 이벤트를 계속 사용한다. **GitLab 활동 새로고침**은 Teamspace에 저장한 활동을 불러온다. [티켓 상태 확인 API](API.md#티켓에서-gitlab-상태-다시-확인)

티켓 상세나 개발 활동 목록에서 MR·파이프라인·활성 브랜치 옆의 **상태 확인**을 누르면 원하는 연결의 저장 상태를 바로 갱신한다. 최근 20건보다 오래된 연결도 확인할 수 있다. 개발 화면에서는 검색과 보기 조건을 유지하고, 갱신한 활동이 조건에서 벗어나면 목록에서 제외한다. [연결된 활동 한 건 확인 API](API.md#연결된-gitlab-활동-한-건-확인)

티켓의 GitLab 직접 조회로 확인한 MR 병합·닫기와 파이프라인 성공·실패는 활성 규칙에 맞는 상태 변경을 제안할 수 있다. 저장소·참조·커밋과 완료 시각을 확인한다. 웹훅 자동화와 직접 조회의 제안은 참조·실행 유형·태그 여부가 일치하는 그룹의 최신 인증 파이프라인 ID를 대조한다. 오래된 기록이나 일부 이벤트에 유형·태그 근거가 비어 있으면 확인된 범위에서 같은 그룹일 수 있는 실행도 대조한다. 전체 활동의 검토는 MR·파이프라인 연결 일부를 확인할 수 없으면 제안을 보류한다. 여러 결과가 서로 다른 목표에 해당하면 작업자가 결정한다. 제안은 일반 티켓 편집을 열며, 저장할 때 확인한 업무·워크플로·규칙·연결을 대조하고 현재 작업자로 기록한다. [티켓에서 GitLab 상태 변경 검토](PILOT.md#티켓에서-gitlab-상태-변경-검토) · [GitLab 파이프라인 웹훅](https://docs.gitlab.com/user/project/integrations/webhook_events/#pipeline-events)

티켓 상세의 **이 활동으로 상태 검토**는 최근 조회 범위 밖에서도 선택한 MR 또는 파이프라인 한 건을 GitLab에서 확인한다. 제안에 선택한 활동을 근거로 사용했음을 표시한다. 해당 파이프라인보다 더 큰 원본 ID의 활동 중 같은 실행 계열일 수 있는 현재 티켓 연결과 인증 수신 기록을 대조한다. 선택한 활동에 해당하는 규칙이 다른 목표를 요구하면 제안을 보류한다. 작업자는 일반 티켓 편집에서 입력을 확인하고 저장한다. [선택한 활동의 상태 검토 API](API.md#선택한-gitlab-활동으로-상태-변경-검토)

저장소 동기화와 인증된 웹훅은 이미 자동 연결한 파이프라인의 원본 저장소와 숫자 ID를 대조해 상태를 갱신한다. 양쪽에 있는 브랜치나 SHA가 다르면 해당 연결의 갱신을 보류한다. 티켓이나 저장소 조회에서 확인한 최신 상태는 해당 파이프라인의 발생 시각과 함께 저장한다. 이후 더 오래된 이벤트와 같은 시각에 다른 상태를 보고한 이벤트는 링크와 티켓 자동화에 적용하지 않는다. 같은 시각·상태의 첫 인증 웹훅은 기존 규칙대로 평가한다. 업무 키가 생략돼도 같은 링크를 갱신하며, 티켓 자동 전이 대상은 인증 이벤트가 확인한 업무 키로 정한다. [GitLab 파이프라인 이벤트](https://docs.gitlab.com/user/project/integrations/webhook_events/#pipeline-events) · [파이프라인 API](https://docs.gitlab.com/api/pipelines/)

티켓과 **개발 · GitLab**에서 연결된 파이프라인의 일반 CI 작업을 직접 확인한다. 실패와 수동 실행 대기 작업의 단계, 실패 사유, 실패 허용 여부와 원본 작업 링크를 제공한다. 서버는 저장소·파이프라인의 실제 ID를 대조하고 조회 전후 파이프라인과 현재 업무의 연결 상태를 확인한다. 열린 화면에서 저장된 파이프라인 상태·시각·브랜치·SHA가 달라지면 이전 CI 결과를 지우고 진행 중인 조회를 취소한다. 사용자가 다시 확인을 선택하면 새로운 조회를 시작한다. 조회 결과는 화면에서 사용하며, 파이프라인 설정 오류는 여부를 표시한다. [GitLab Jobs API](https://docs.gitlab.com/api/jobs/#list-all-jobs-by-pipeline)

같은 **CI 작업 확인**에서 트리거 작업의 상태와 GitLab이 제공한 다운스트림 파이프라인 상태를 함께 읽는다. 트리거가 성공한 경우에도 다운스트림 실패를 볼 수 있다. 다른 저장소를 가리킬 때도 연결된 GitLab 주소와 파이프라인 번호를 확인한 링크를 연다. 트리거 조회가 불가능해도 일반 CI 작업은 표시하고, 확인한 빈 목록은 별도로 안내한다. [GitLab 트리거 작업 API](https://docs.gitlab.com/api/jobs/#list-all-trigger-jobs-by-pipeline)

연결된 파이프라인의 **테스트 결과 확인**에서 GitLab이 집계한 성공·실패·건너뜀·오류 수와 처음 50개 스위트의 결과를 본다. 보고서 처리 오류는 여부로 표시하고 빈 결과 및 조회 실패와 구분한다. 저장한 연결로 요청할 때 읽고 조회 전후 파이프라인의 상태와 업무 연결을 대조한다. 업데이트가 감지되면 다시 확인을 안내하며, 전체 보고서는 원래 GitLab 파이프라인에서 열 수 있다. [GitLab 테스트 결과 요약 API](https://docs.gitlab.com/api/pipelines/#retrieve-a-test-report-summary-for-a-pipeline)

같은 화면의 **실패 테스트 확인**에서 결과가 실패·오류인 테스트의 이름과 스위트, GitLab이 제공한 클래스를 최대 50개까지 확인한다. 상세 조회는 버튼을 눌렀을 때 시작하고, 연결된 저장소·파이프라인을 다시 대조한다. 한도에 도달했거나 집계만 확인한 실패가 남아 있으면 전체 보고서로 이어서 확인할 수 있다. 스택 추적과 출력 및 첨부는 GitLab 화면에서 읽는다. [GitLab 상세 테스트 결과 API](https://docs.gitlab.com/api/pipelines/#retrieve-a-test-report-for-a-pipeline)

티켓에서 새 브랜치를 만들 때 저장한 GitLab 저장소와 대문자 티켓 키를 기본 이름에 사용한다. 미리보기는 저장소·브랜치와 기준 참조를 전체 커밋 SHA로 확인한다. 같은 작업자와 설정·티켓 위치를 다시 대조한 뒤 사용자가 한 번 입력한 쓰기 토큰으로 검토한 SHA에서 생성한다. 같은 이름을 발견하면 기존 브랜치 주소를 표시한다. 생성 요청 결과가 불명확하면 SQLite의 시도 기록과 GitLab의 현재 SHA를 조회해 확인하며 추가 생성은 보류한다. 티켓이 이동한 뒤에는 같은 활성 티켓 ID에서 팀원이 명시적으로 확인한 경우에 연결한다. 생성은 개발 활동으로 기록하고 자동 전이는 기존의 인증된 이벤트에서 평가한다. [GitLab 브랜치 생성](https://docs.gitlab.com/api/branches/#create-repository-branch)

티켓과 개발 화면의 연결 브랜치에서 같은 저장소의 열린 MR을 확인하고 GitLab에서 연다. 확인을 끝낸 뒤 열린 MR이 없으면 기본 또는 직접 입력한 대상 브랜치를 확인하고, 두 브랜치의 커밋이 다를 때 GitLab 생성 화면을 연다. 저장한 티켓 키와 제목을 복사해 MR 제목에 붙일 수 있다. 작성과 최종 제출은 GitLab 화면에서 한다. [GitLab MR 생성](https://docs.gitlab.com/user/project/merge_requests/creating_merge_requests/)

티켓에서 찾은 열린 MR은 같은 검토 화면에서 수동 연결한다. 실제 MR의 ID·저장소·출발 및 대상 브랜치와 현재 티켓의 브랜치 연결을 다시 확인한다. 연결 뒤에는 티켓의 MR 목록에서 상태와 검토자를 확인한다. 이미 연결한 MR은 같은 행으로 표시한다. 응답이 끊기면 저장된 GitLab 활동을 다시 읽으며 티켓과 댓글 초안은 유지한다. 티켓 상태 전이는 이후 인증 이벤트에서 업무 식별과 규칙 조건이 확인될 때 평가한다.

업무 목록과 보드는 열린 MR과 실패·진행 중·수동 실행 대기 파이프라인을 티켓별로 표시한다. 같은 티켓의 GitLab 인스턴스·저장소·참조 이름에서 푸시·MR·예약 등의 실행 유형별로 최신 파이프라인을 사용하고 확인된 태그 실행을 따로 집계한다. 티켓과 개발 화면은 각 실행의 유형과 상태를 표시한다. 유형을 확인하지 못한 기존 연결은 같은 참조의 미확인 그룹으로 집계한다. 이 상태를 기준으로 업무를 좁혀 공유 보기에 저장할 수 있다. 간트, 문서 업무 목록·현황, 필드 집계와 진행 차단 보고서도 같은 보기 조건을 사용한다. [GitLab 파이프라인 실행 유형](https://docs.gitlab.com/ci/jobs/job_rules/#ci_pipeline_source-predefined-variable)

**개발 · GitLab → 연결된 개발 활동**에서는 현재 프로젝트의 저장된 활동을 업무 키·제목, 확인된 이전 키, 저장소·참조 또는 GitLab 활동 주소로 검색한다. 실패와 수동 실행 대기는 업무 보기와 같은 기준으로 각 실행 그룹의 최신 파이프라인을 고른 뒤 상태와 검색 조건을 적용한다. 병합 확인이 필요한 MR은 확인된 차단 상태로 좁힌다. 조건과 유형별 페이지는 주소에 저장한다. 활동에서 업무를 열면 현재 결과의 업무를 순서대로 검토하고 원래 목록과 버튼으로 돌아온다. 필터와 티켓 검토는 Teamspace에 저장된 자료를 사용한다.

열린 MR에는 GitLab 조회나 인증된 이벤트에서 확인한 병합 상태와 기준 시각을 저장한다. 승인 대기, 수정 요청, 충돌, 미해결 토론, 파이프라인 조건처럼 확인된 사유를 업무 상세와 개발 화면에 표시한다. 병합 확인이 필요한 MR을 기준으로 공유 보기를 만들 수 있다. 미확인·검사 중인 MR은 별도 상태로 표시한다. [GitLab 병합 상태](https://docs.gitlab.com/api/merge_requests/#merge-status)

티켓과 **개발 · GitLab**에서 연결된 열린 MR의 **MR 검토 확인**을 선택하면 검토자별 수정 요청·검토 진행·승인 상태와 현재 승인자를 본다. 배정만 읽을 수 있으면 검토자 명단과 상태 미확인을 함께 표시하고, GitLab이 승인 규칙의 필요·남은 수를 제공할 때 두 값을 표시한다. 열린 화면에서 링크가 갱신되면 이전 결과를 지우고 사용자가 재조회한다. 이 화면에는 요청 당시 확인한 정보가 표시되며 승인·병합은 GitLab에서 수행한다. [MR 검토 확인 API](API.md#연결된-mr-검토-확인)

**MR 최신 파이프라인 확인**은 티켓과 개발 화면에서 연결된 MR을 조회해 GitLab이 `head_pipeline`으로 지정한 실행의 상태와 원본 주소를 보여준다. MR의 현재 소스 HEAD와 파이프라인의 커밋은 각각 검증하므로 병합 결과를 검증하는 파이프라인도 확인할 수 있다. **CI 작업 확인**을 요청하면 해당 실행의 실패·수동 대기·트리거 작업을 읽는다. 파이프라인을 별도 링크로 연결하지 않은 티켓에서도 사용할 수 있다. [MR 파이프라인 조회 API](API.md#연결된-mr-최신-파이프라인), [GitLab 병합 결과 파이프라인](https://docs.gitlab.com/ci/pipelines/merged_results_pipelines/)

같은 화면의 **미해결 토론 확인**은 사용자가 요청할 때 토론별 발췌와 확인 가능한 파일·줄을 불러온다. 일부 조회와 빈 목록, 조회 불가를 각각 표시한다. 검토 화면을 닫거나 연결이 바뀌면 진행 중인 조회를 취소하고, 원문 링크는 GitLab의 해당 댓글을 연다. [MR 토론 조회 API](API.md#연결된-mr-미해결-토론-확인)

Jira 이관 뒤 기존 개발 이력을 연결할 때 저장소별로 Teamspace 프로젝트와 Jira 원본을 지정한다. 현재 키와 원래 키는 그 프로젝트에서 찾으며, 두 업무에 해당하는 키는 미리보기에 표시하고 연결을 보류한다. 원래 키로 만든 링크에는 이관 키를 기록한다. 매핑을 변경하면 해당 저장소의 활성 상태 자동화 규칙을 비활성화하고 다시 검토할 수 있게 한다.

기존 개발 이력을 포함하는 미리보기와 수동 동기화는 브랜치 이름과 최근 커밋 메시지의 명시적인 업무 키로 링크를 만든다. 같은 저장소·SHA·업무의 커밋 링크를 재사용한다. 저장소 목록에서 표본으로 읽은 값, 티켓에서 단건 조회한 HEAD, 인증된 푸시 관측을 구분한다. 저장소의 목록 동기화에서는 단건 조회나 푸시로 확인한 브랜치 상태를 보존한다.

Push 웹훅은 브랜치 이름과 커밋 메시지의 티켓 키로 MR 전 개발 기록을 연결한다. 브랜치의 마지막 확인 SHA와 삭제 상태를 저장하며 푸시의 `before`와 `after`로 이어지는 변경을 반영한다. 티켓과 개발 화면에서 브랜치·커밋·MR·파이프라인을 구분해 표시하고, 프로젝트 범위 API 키는 티켓의 GitLab 활동을 조회할 수 있다.

현재 구현 다음에는 계획·업무 보기, 문서의 고급 매크로, 시간대별 일정, 알림·보고와 기존 도구 이관을 확장한다. 실제 구현과 검사 결과는 [개발 상태](STATUS.md)에 기록한다.

## 기존 도구 원본 이관

Confluence ZIP 대조 파일에 ZIP 전체의 현재 페이지, 원본과 연결한 페이지, 제한 상태가 확인된 페이지와 확인 범위 밖의 페이지를 집계한다. 리허설의 매핑과 미리보기는 같은 패키지에 연결된 각 검토의 집계를 표시한다. 형식 1 파일의 확인 범위는 미기록으로 표시하며 공간 권한은 계속 수동 검토한다. 검증 보고서에는 저장한 대조 근거와 전체 페이지 확인을 증명할 수 없는 패키지 수를 남긴다. [Confluence ZIP 사전 대조](PILOT.md#confluence-공간-xml과-현재-페이지-대조)

새 리허설은 준비 기록과 Confluence 검토 파일을 워크스페이스 데이터와 함께 백업한다. 복원본에서도 같은 매핑과 제한 확인 근거를 불러오며 검증 명령은 복원본의 준비 기록과 원본 해시를 대조한다. 리허설로 표시된 작업 공간은 루프백 검토 모드에서 열고 자동 작업을 중지한다. 이전에 준비한 리허설은 기존 디렉터리에서 계속 연다. [리허설 복원](PILOT.md#오프라인-원본-이관-리허설)

Jira 요청자는 원본에서 요청자 필드를 식별하고 팀원 매핑을 확인한 경우 업무에 기록한다. 명시적으로 비어 있는 원본 요청자는 미지정으로 이관한다. 이후 원본 변경분은 마지막 이관 기준값과 현재 값을 비교해 팀이 수정한 요청자를 지킨다. 이전 분석 자료에서 요청자 근거가 부족하면 원본을 다시 분석할 수 있다.

Jira Data Center REST 수집은 프로젝트 또는 명시한 업무 키를 기준으로 Jira에서 읽을 수 있는 원본을 전용 ZIP으로 저장한다. 검색과 활동 페이지의 업무·ID·범위를 대조하고, 첨부는 지정한 Jira 서비스에서 원본 ID가 일치하는 바이트를 읽는다. 확보한 범위와 생략 항목을 기록한다. 생성한 ZIP은 기존의 오프라인 미리보기, 검토 적용과 물리 복원 절차를 사용한다. [Jira REST 수집과 리허설](PILOT.md#jira-data-center에서-rest-자료-수집)

큰 Jira 프로젝트는 검색 결과 두 번의 업무 ID와 현재 키, 순서가 일치할 때 최대 10,000개 업무의 분할 수집 계획을 저장한다. 각 묶음은 같은 Jira 주소·프로젝트·첨부 설정에서 숫자 ID로 업무를 읽고 현재 키와 프로젝트를 재확인한다. ZIP별로 계획의 해시를 기록하고 실패한 묶음을 재시도할 수 있다. 같은 원본 인스턴스와 대상 프로젝트를 사용하는 묶음은 기존 이관 미리보기에서 함께 검토한다. [분할 수집 절차](PILOT.md#jira-프로젝트-분할-수집)

Confluence Server에서는 이관 전 현재 계정이 읽을 수 있는 페이지의 ID·버전·상위 관계와 직접 제한 및 상속된 읽기 제한을 확인한다. 실제 공간 XML을 제공하면 같은 공간의 현재 페이지와 대조하고 ZIP에서 확인한 본문·첨부 근거와 진단을 집계한다. 공간의 전체 열람 범위와 이관 대상은 별도 검토한다. 원문과 버전·첨부의 이관 입력은 공간 XML을 사용한다. [Confluence 공간 XML 대조](PILOT.md#confluence-공간-xml과-현재-페이지-대조)

Confluence 체크리스트는 항목 순서와 완료 여부를 편집 가능한 목록으로 옮긴다. 항목의 원본 담당자와 기한은 본문 텍스트로 보존한다. 일부 항목의 원본 구조를 변환할 수 없으면 해당 구조의 위치에 원문을 남긴다. 이전 이관에서 체크리스트가 포함된 본문 전체를 원문 코드 블록에 보관한 문서는 같은 원본 버전으로도 변경분 미리보기에서 복구를 검토할 수 있다. 저장 본문과 보관 원본을 비교해 팀 편집을 보존한다. [Confluence 체크리스트와 사용자 참조 형식](https://confluence.atlassian.com/doc/confluence-storage-format-790796544.html)

Confluence 문장 댓글의 위치 표식과 표시 텍스트·서식·링크를 보존한다. 처음 옮기거나 변경분에서 새로 추가하는 댓글은 같은 XML 패키지의 댓글 속성, 원래 페이지, 하나로 확인된 위치 표식을 대조한다. 발췌 범위가 적용할 Teamspace 본문과 일치하면 문장 댓글의 원문 저장본을 고정한다. 같은 문장이 반복돼도 표식 범위에서 열고, 문서 편집 뒤에도 내보낸 원문의 위치를 읽는다. 표식이 없거나 중복된 경우, 팀에서 편집한 본문과 일치하지 않는 경우에는 일반 댓글로 보존하고 미리보기에서 확인한다. [Confluence 문장 댓글 속성](https://docs.atlassian.com/ConfluenceServer/javadoc/6.9.1/constant-values.html#com.atlassian.confluence.pages.Comment.MARKER_REF_PROP) · [Confluence 원문 위치 표식](https://support.atlassian.com/confluence/kb/keep-inline-comments-while-editing-confluence-pages/)

Confluence XML에 소유 페이지와 직접 상위 댓글이 확인된 답글은 원문을 고정한 문장 댓글 아래에 옮긴다. 추가 이관에는 상위 댓글 객체가 빠져 있어도 같은 인스턴스와 페이지의 이관 기록에서 확인한 현재 문장 댓글을 찾을 수 있다. 과거 답글을 추가할 때는 팀에서 처리한 해결 상태를 보존한다. 여러 단계의 답글이나 직접 상위 댓글을 확인할 수 없는 답글은 일반 문서 댓글로 남기고, 최초 관계를 원본 기록에서 읽는다. [Confluence 6.9.1 댓글 관계](https://docs.atlassian.com/ConfluenceServer/javadoc/6.9.1/serialized-form.html#com.atlassian.confluence.pages.Comment)

병행 기간에는 업무와 문서에 Jira 티켓 및 Confluence 페이지 주소를 연결한다. 조회 버튼을 누르면 설정한 각 서버의 읽기 API에서 제목·상태·식별자와 수정 시각을 가져온다. 팀에서 사용할 연결의 자격 증명은 서버의 별도 파일에 둔다. 연결 주소는 전체 백업에서 보존하며, 원본 조회는 GET 요청으로 처리한다. [Jira 이슈 읽기 API](https://developer.atlassian.com/server/jira/platform/rest/v11000/api-group-issue/), [Confluence Server 6.9.1 REST API](https://docs.atlassian.com/ConfluenceServer/rest/6.9.1/)

기존 `/api/import`는 자체 백업으로 워크스페이스를 교체하는 기능이다. Jira·Confluence 이관은 별도 흐름으로 구현하며, 기본값은 새 프로젝트/문서 영역에 추가한다. 패키지 분석 → 작성자·상태·유형·필드 매핑 → 변환 샘플과 손실 미리보기 → 명시적 적용 순서다. 오프라인 분석과 원문 보관에 이어 작성자·상태·유형·필드 매핑, 문서 변환, 새 프로젝트 적용을 구현했다.

**사용자 매핑 → 이메일 일치 후보 검토**에서 아직 매핑되지 않은 원본 계정과 현재 팀원을 대조한다. Jira REST·관리자 XML의 계정 이메일과 Confluence XML의 사용자 이메일을 사용한다. Confluence 프로필의 이메일은 원본에서 사용자 키로 유일하게 연결되고 관련 주소가 일치할 때 사용한다. 주소의 앞뒤 공백과 대소문자를 정리해 비교한다. 한 원본 계정의 주소 근거가 충돌하거나 하나의 주소가 같은 원본 인스턴스에서 여러 계정으로 확인되면 해당 후보를 보류한다. 기존 팀원 지정은 유지한다. 반영 직전에 최신 팀원을 다시 대조하고, 사용자가 선택한 매핑으로 새 미리보기를 만든다. [이관 리허설](PILOT.md#오프라인-원본-이관-리허설)

**작성자 매핑 미리보기**는 실제로 생성할 문서·댓글·원본 문서 버전·첨부 버전·작업 시간과 기존 Confluence 문서의 변경분을 센다. 원본 작성자를 매핑한 팀원, 매핑 또는 원본 작성자 정보가 없어 이관 작업자로 기록할 항목, 기존 작성자를 유지할 문서를 패키지별로 검토한다. 적용할 때 원본의 정확한 대상과 예상 작성자를 같이 기록한다. 이후 작성자 검증에서 현재·휴지통의 대상을 대조하고 원본으로 이동한다. 형식 111 자체 백업은 작성자 비교 기록을 보존한다.

새 Jira 프로젝트의 워크플로는 대상 프로젝트 키를 기준으로 초기 상태와 허용 전이를 직접 지정할 수 있다. 여러 원본 컨테이너를 같은 프로젝트로 옮기면 하나의 워크플로를 검토한다. 이관되는 업무의 상태와 직접 추가한 상태를 합쳐 사용한다. 실제 업무에는 원본에서 매핑한 상태를 유지하고, 새로 만드는 업무는 지정한 초기 상태에서 시작한다. 미리보기와 적용에서 상태 범위·전이 방향을 검증하며, 미리보기의 워크플로와 영수증의 설정을 함께 적용한다. 기존 프로젝트 추가 이관은 대상의 현재 워크플로를 사용한다. [워크플로 이관](API.md#새-jira-프로젝트의-워크플로-지정)

새 프로젝트의 이관 미리보기에서 Jira 원본 이력의 확인된 상태 전이 방향과 해당 방향에 대한 고유 업무 수를 표시한다. 원본 상태 ID와 업무 소유자를 확인하고, 이관할 업무로 구성한 대상 프로젝트 범위에서 집계한다. 선택한 방향을 매핑에 추가하면 이전에 설정한 초기 상태·상태 추가·수동 전이를 유지하고 새 미리보기를 요구한다. 원본의 유형별 조건과 검증기는 프로젝트 담당자가 검토한다.

내보내기 파일의 매니페스트를 워크스페이스 없이 검사해 해시와 형식, 객체·첨부 근거, 진단 코드별 건수를 보관한다. 파일명·경로·인스턴스 식별값과 원본 내용이 빠진 집계로 대상을 검토한다. 브라우저 원본 분석에서는 여러 파일의 제품과 인스턴스를 입력하고 기존 분석 API로 순차 처리한다. 실패·확인 대기 파일을 별도로 보여 주고, 확인된 패키지 ID를 실제 이관의 선택 항목으로 전달한다. 다른 매핑의 입력을 교체하기 전에 확인을 받고, 기본 매핑을 읽은 뒤 사용자가 미리보기와 적용을 별도로 진행한다.

이전에 옮긴 같은 Jira 인스턴스의 같은 원본 프로젝트에서 새 업무를 추가할 수 있다. 대상 Teamspace 프로젝트의 저장된 상태·유형·필드에 매핑하고 새 업무에 다음 키를 부여한다. 이미 연결된 원본과 그 하위 기록은 영수증에 원문으로 보관한다. 새 업무의 부모와 업무 관계는 현재 살아 있는 기존 연결도 사용한다. 프로젝트 설정·새 키·원본 연결이 미리보기 뒤 바뀌면 다시 검토한다. 새 티켓·관계·첨부와 영수증을 같은 적용으로 보관한다.

Jira 날짜 선택 필드의 이름을 `Start date` 또는 `End date`로 확인하면 티켓과 간트가 공유하는 시작일·종료일에 넣는다. 관리자 XML과 검색 XML은 필드 유형을, REST JSON은 필드 이름과 스키마를, CSV는 정확한 사용자 정의 열 제목을 확인한다. 원본 필드와 ID를 보존하고 견본에서 변환된 기간을 확인할 수 있다. 표준 날짜가 있으면 먼저 사용하며, 일정 필드 정의나 값이 여러 개이면 원본을 보관하고 검토 진단을 표시한다. 변경분의 생략된 날짜는 유지하며 REST의 명시적 빈 값이나 완전한 CSV의 빈 열을 지우기로 검토한다. [Jira REST 날짜 선택 필드](https://developer.atlassian.com/server/jira/platform/about-the-jira-server-rest-apis/)

이전 Jira REST 이관에서 원본 날짜를 보존하고도 목표 마감일이 비었던 업무는 티켓의 **원본 기록**에서 비교한다. 최초 연결, 당시 빈 값의 기준과 정확한 원본 날짜를 확인하고 후속 원본의 날짜 근거를 대조한다. 후속 원본은 변경 없이 보관한 경우에도 같은 원본 업무가 확인되면 검토에 사용한다. 현재 마감일이 비어 있고 업무 버전과 변경 이력으로 팀의 마감일 편집이 없음을 확인한 뒤 명시적으로 적용한다. 적용 시 원본 근거와 현재 업무 버전을 다시 검사하고 일반 업무 변경 이력을 남긴다.

Jira 관리자 XML의 숫자 우선순위는 같은 패키지에서 연결된 옵션 이름을 확인해 Teamspace 우선순위로 이관한다. 명시한 원본 값이 모호하거나 매핑할 수 없으면 미리보기에 표시하고 원본을 보존한 채 보통으로 가져온다. 기존 변경분 반영은 저장된 이관 기준과 현재 업무를 계속 비교한다.

Jira 컴포넌트는 프로젝트의 **Jira 컴포넌트** 여러 선택 필드로 옮긴다. 관리자 XML의 업무 연결, REST·검색 XML의 컴포넌트 ID와 프로젝트 범위를 확인한다. CSV의 반복 컴포넌트 열은 확인한 같은 프로젝트 안에서 이름별 선택지로 옮긴다. 같은 이름의 다른 ID는 구분하고, 업무에 붙은 컴포넌트를 모두 보존한다. 티켓 양식·업무 필터·필드 집계에서 값을 쓴다. 원본 관계와 확인할 수 없는 값은 이관 기록에 보관한다. [Jira 컴포넌트 관계](https://support.atlassian.com/jira/kb/sql-query-to-get-issue-components-from-jira-database/) · [Jira CSV 컴포넌트 열](https://confluence.atlassian.com/adminjiraserver/importing-data-from-csv-938847533.html)

추가 이관은 기존 여러 선택 필드와 확인한 선택지를 사용한다. 기존 업무의 변경분은 마지막 반영값과 현재 값을 비교해 팀 편집을 보존한다. REST의 명시적 빈 배열을 비우기로 검토하며 생략되거나 근거가 모호한 값은 현재 값과 원본 기록을 보존한다. 선택지가 대상에 없으면 업무 양식에서 먼저 확인하고 새 미리보기를 만든다.

프로젝트의 Jira 버전 정의를 릴리스 계획으로 만들고, 확인한 수정 버전 ID로 새 티켓을 연결한다. 출시일은 계획 목표일에 표시한다. 확정된 수정 버전이 여러 개이면 적용 미리보기에서 대표 릴리스 하나를 선택하거나 미지정으로 검토한다. 모든 원본 수정·영향 버전 관계는 이관 기록에서 확인할 수 있다. 추가 이관은 같은 인스턴스의 버전 ID와 대상 프로젝트를 사용해 기존 계획을 찾고, 팀이 바꾼 이름·날짜·상태를 이어서 사용한다. 원본 후보가 범위나 이름 제약에 걸리면 진단을 표시한다. [Jira 수정·영향 버전의 원본 관계](https://support.atlassian.com/jira/kb/query-jira-issues-by-fix-version-database/)

Jira 관리자의 스프린트 테이블과 확인된 업무 필드, Agile REST의 현재·종료 스프린트, 유형을 확인한 기존 Sprint 문자열에서 스프린트 ID·상태·기간·업무 연결을 읽는다. 선택한 업무가 속한 프로젝트마다 사이클을 만든다. 현재 후보가 하나로 확인되면 연결하고, 현재 후보를 하나로 정할 수 없으면 미리보기에서 대표 사이클을 검토한다. Agile 원본에서 현재 스프린트가 비어 있으면 과거 연결을 원본으로 보관한다. 보드에 같은 이름의 스프린트가 있으면 원본 ID를 이름에 표시해 구분한다. 추가 이관은 같은 사이클을 재사용하며 기존 업무와 팀이 편집한 계획을 유지한다. [Jira 스프린트 상태](https://support.atlassian.com/jira/kb/determining-sprint-status-from-the-database/) · [Jira Sprint 필드 형식](https://developer.atlassian.com/cloud/jira/software/rest/intro/#sprint-custom-field)

기존 Jira 업무 변경분을 함께 반영하는 옵션은 원본 수정 시각과 필드별 이관 기준을 사용한다. 현재 값이 이관 기준과 같은 필드만 새 원본 값으로 갱신한다. 이전 형식의 이관 기록에서는 원본과 당시 매핑으로 확인할 수 있는 기준을 복원한다. 충돌하거나 원본에서 생략한 값은 보존한다. 미리보기와 적용에서 현재 워크플로를 검사하고, 작업 버전·원본 연결·보고 수집 이력과 영수증을 같은 트랜잭션에서 처리한다.

상위 업무 변경은 명시적인 원본 업무 ID·키나 REST의 빈 상위 값을 근거로 비교한다. 검증한 같은 Jira 원본 프로젝트의 이미 이관한 업무와 같은 적용에서 생성할 업무를 상위로 지정할 수 있다. 검토 이후 관련 업무 버전이나 계층이 바뀌면 새 미리보기가 필요하다. 여러 업무를 옮길 때는 최종 계층에 순환이 있는지 확인하고 전체를 함께 적용한다. 형식 100 백업은 마지막으로 반영한 상위 업무의 원본 및 저장값 비교 기준을 보존한다. [Jira REST 상위 업무 필드](https://developer.atlassian.com/server/jira/platform/jira-rest-api-examples/)

Jira REST와 검색 XML에서 Jira Software의 실제 `Epic Link` 필드 유형과 업무 키를 확인하고, 관리자 XML에서는 확인한 `jira_gh_epic_story` 관계의 에픽과 하위 업무 방향을 사용한다. 같은 원본 프로젝트와 대상 프로젝트에서 확인한 에픽을 상위 업무로 이관하면 티켓과 간트에서 에픽·스토리·하위 작업을 따라갈 수 있다. 기존 에픽에 새 업무를 추가할 때는 현재 이관 연결을 대조한다. 원래 상위 작업과 에픽 근거가 충돌하거나 다른 원본 프로젝트를 가리키는 경우는 검토에 표시하고 원본을 보존한다. 후속 REST의 명시적 빈 `Epic Link`는 이전에 이 방식으로 적용한 연결만 해제로 검토한다. [Atlassian Epic Link 정의](https://support.atlassian.com/jira/kb/epic-name-vs-epic-link/) · [Jira 관리자 XML에 대응하는 관계 유형](https://support.atlassian.com/jira/kb/advanced-search-for-has-epic-link-type-fails-in-jira-server/)

Jira·Confluence의 한 필드를 적용하고 다른 필드의 팀 편집을 보존한 뒤에는, 더 새로운 내보내기에서도 미반영 필드를 마지막으로 반영한 값과 비교한다. 현재 값이 다르면 미리보기에 계속 표시하고, 마지막 반영 값으로 돌아온 필드는 새 원본을 적용할 수 있는지 다시 확인한다. 형식 98 자체 백업은 적용한 Jira 기본 필드와 Confluence 본문에 대한 원본 비교 근거를 보존한다.

티켓의 **변경 이력**에서 이관한 Jira 상태 변경의 전후 상태·원본 작성자·시각을 읽는다. 이력은 관리자 XML의 변경 그룹과 REST 변경 기록에서 원래 상태 항목과 업무 연결을 확인해 표시한다. 별도 REST 페이지는 원본 서버와 업무를 함께 확인할 수 있을 때 연결한다. 당시 이름을 확인할 수 없으면 확인된 원본 상태 ID를, 시각을 확정할 수 없으면 원본 값을 표시한다. 보존된 원본 기록에서 상세 내용을 열 수 있으며 Teamspace에서 발생한 변경과 Jira 원본 변경을 각각 확인할 수 있다. 보고서 관측은 Teamspace 이관 시점부터 시작한다. [Jira 상태 변경 원본 구조](https://developer.atlassian.com/server/jira/platform/database-change-history/)

기존 업무의 사용자 정의 필드는 원본 속성 ID와 Teamspace의 고정 필드 ID를 대조하고, 기본 필드와 별도의 비교 기준을 저장한다. 미리보기에서 보존할 팀 편집, 원본의 새 값과 지우기, 현재 표시·필수 조건을 확인한다. 같은 원본을 기본 필드와 사용자 정의 필드에 따로 적용할 수 있으며, 두 옵션을 함께 선택하면 티켓에 한 번의 변경으로 저장한다.

같은 Jira 원본에 연결된 기존 업무에 새 댓글과 작업 시간을 추가한다. 포함할 수 있는 기록은 원본 객체의 ID와 소유 업무, 작성자, 작업 시간·댓글 시각이 확인되는 경우다. 이미 옮긴 원본 ID는 팀의 편집이나 삭제 후에도 다시 추가하지 않는다. 새 기록과 원본의 연결, 이관 영수증을 함께 저장하고 보고서에는 기존 작업 시간과 동일하게 반영한다.

신규·추가 Jira 댓글의 Wiki, ADF, 지원하는 검색 XML의 HTML에서 표시 이름과 HTTP(S) 주소를 `이름 <주소>` 형태의 일반 텍스트로 옮긴다. 표시 이름이 주소와 같으면 주소를 한 번 기록한다. URL 안의 쿼리·프래그먼트·문장부호를 유지한다. 펼친 본문이 기존 한도를 넘으면 적용 검토에 링크가 원본에 남는다고 표시하고 이전 방식으로 변환한 본문을 쓴다. [Jira Wiki 렌더러](https://confluence.atlassian.com/adminjiraserver106/configuring-renderers-1573488767.html) · [Atlassian 문서 형식](https://developer.atlassian.com/cloud/jira/platform/apis/document/structure/)

이전 Jira 이관에서 본문에 빠진 주소는 댓글의 **Jira 원본 링크 확인**에서 연다. 서버는 활성 댓글과 티켓을 확인하고 유일한 보존 원본, 원래 업무 식별자와 적용 영수증을 대조한다. 다시 편집한 댓글에서도 당시 원본에 있었던 링크를 확인할 수 있다. 링크는 열기 요청 때 읽으며, 표시 이름과 주소만 반환한다. 목록에서 조회 가능 여부를 계산하며 자체 백업에는 원래 댓글과 보존 자료를 저장한다.

REST 업무 응답과 같은 ZIP에 있는 별도 댓글·작업 시간 페이지는 원래 서버와 업무를 확인해 이관한다. 업무 응답에 들어 있는 기록과 같은 ID가 겹치면 내용과 접근 제한이 일치하는지 검사한다. 응답이 보고한 범위를 모두 확인할 때까지 누락 진단을 유지한다. 별도 페이지에서 찾은 제한 기록도 기존 적용 검토를 거친다.

기존 Jira 업무의 새 첨부파일은 원본 ID, 소유 업무, 패키지의 파일 크기와 SHA-256을 확인해 추가한다. 이전 버전과 직접 올린 파일은 같은 ID로 계속 열리고, 삭제한 원본의 ID도 중복 검사에 사용한다. 새 첨부의 바이너리와 원본 연결, 이관 영수증은 한 번의 적용으로 저장한다.

Jira 후속 이관에서는 이미 옮긴 티켓 두 건의 새 관계를 추가한다. 같은 Jira 인스턴스의 두 프로젝트를 각각 Teamspace 프로젝트로 옮긴 경우에도 연결할 수 있다. 한쪽은 이번 추가 이관 대상이어야 하며, 양쪽 티켓의 원본 ID와 현재 프로젝트를 이전 이관 기록으로 확인한다. REST와 검색 XML에서 읽은 관계 방향과 두 프로젝트를 미리보기에 표시한다. 동일한 연결이나 이미 처리한 원본을 식별하고, 출처가 모호하거나 제외·제한된 관계는 원본에 보관한다. 검토 뒤 관련 업무나 관계·보존 원본이 바뀌면 다시 검토한다. 적용한 관계 ID와 양쪽 프로젝트를 영수증에 남겨 이후 이관과 백업 복원에서 대조한다. [Jira 관계 방향 모델](https://developer.atlassian.com/cloud/jira/platform/issue-linking-model/)

이전에 옮긴 Confluence 인스턴스의 같은 원본 공간에서 새 페이지를 추가할 수 있다. 새 페이지의 문서 이력·댓글·첨부를 함께 이관하고, 다시 제출한 페이지와 관련 기록은 원본으로 보관한다. 원본 ID나 확인한 공간 내의 유일한 원본 제목으로 기존 문서를 참조한다. 이미 옮긴 상위 문서가 원본 파일에 없어도 연결할 수 있다. 적용 시 기존 연결과 문서의 현재 프로젝트를 다시 확인하며 팀의 편집을 보존한다.

현재 페이지 본문의 이름 붙은 앵커와 제목 링크는 대상 제목을 유일하게 확인했을 때 절 링크로 변환한다. 대상이 모호하면 원본 표기를 보존하고 이관 검토에 표시한다. 이미 옮긴 문서의 절을 연결할 때는 미리보기와 적용 시 해당 절이 있는지 검사한다.

기존 Confluence 문서 변경분을 반영하는 옵션은 원본 버전 또는 수정 시각과 제목·본문의 비교 기준을 사용한다. 현재 값이 이전 이관 기준과 같은 필드만 갱신한다. 생략된 본문, 변환에 필요한 참조를 확인하기 어려운 본문과 팀이 편집한 내용은 보존한다. 본문 변경 전에 공동 편집 참여자와 적용 후 문서 포함 관계를 검사한다. 적용은 새 문서 이력과 비교 기준을 함께 저장하며, 공동 편집의 이전 세대는 사본 복구 흐름을 사용한다.

Confluence XML에 현재 페이지의 상위 페이지 또는 최상위 근거가 있으면 변경분에서 문서 위치를 함께 검토한다. 같은 원본 공간의 연결된 문서나 이번에 새로 가져올 문서로 이동할 수 있다. 원본의 버전이 같으면 제목과 함께 제공된 본문이 일치하며 수정 시각이 더 늦을 때 위치를 검토한다. 상위 정보가 생략되거나 대상이 불명확하거나 팀이 위치를 바꾼 경우에는 현재 위치를 보존한다. 적용 전에 최종 트리와 관련 문서 버전을 확인한다. 기존 형제 문서의 순서와 본문·공동 편집 상태를 보존하며, 자체 백업 형식 99는 다음 위치 비교에 사용할 기준을 저장한다.

Confluence XML에서 같은 원본 공간과 상위 페이지를 확인하고 모든 형제 페이지의 `position`이 서로 다른 0 이상의 정수이면 그 순서대로 팀 문서 트리를 구성한다. 새 프로젝트의 최상위와 하위 문서에 적용하고, 기존 프로젝트에 추가할 때는 이번에 만든 상위 문서 아래의 새 형제 그룹에 적용한다. 원본 위치가 없으면 기본 순서를 사용한다. 일부 위치가 빠지거나 중복되는 그룹은 진단과 적용 집계에 표시한다. 문서·형제 순서·영수증을 함께 저장하고 기존 백업과 복원 경로를 사용한다. [Confluence 형제 페이지 순서](https://confluence.atlassian.com/conf711/move-and-reorder-pages-1044781182.html)

Confluence 원본 라벨은 이관 당시 목록의 해시와 현재 문서를 대조한다. 검증된 전역 라벨은 더 새로운 부분 내보내기에서 추가하고, 전체 목록과 페이지 연결이 확인된 경우에만 교체·삭제를 검토한다. 원본 제목·본문이 일치하는 같은 페이지 버전도 검토할 수 있다. 적용 전에 내보내기 순서를 확인하며, 라벨만 바꾸는 경우 공동 편집을 유지한다.

같은 원본 페이지의 첨부는 원본 첨부 ID와 버전을 확인해 재사용한다. 기존 문서에 새 첨부와 새 원본 버전을 적용하는 옵션을 제공한다. 직접 올린 버전은 파일 목록의 최신 파일로 유지하고, 문서 본문과 이전 이력은 당시 파일 ID로 계속 열린다. 적용은 재사용할 저장 파일과 새 원본 파일의 바이트를 검사하고, 새로 저장한 파일과 영수증을 함께 처리한다.

기존 문서의 댓글과 이력은 같은 원본 인스턴스·공간의 문서에 추가한다. 이미 처리한 댓글 ID와 원본 버전 번호를 확인해 중복을 막고, 기록을 영구 삭제한 경우에도 연결 이력을 사용한다. 현재 제목·본문과 팀의 댓글을 보존한다. 추가한 원본 이력은 문서에서 비교하거나 고정해 포함할 수 있고, 복구 시 현재 문서의 새 저장본을 만든다.

패키지별 기본 주소를 지정하면 새 Jira 업무와 Confluence 페이지에 원래 업무 키와 페이지 ID로 링크를 만든다. 미리보기의 링크 예시와 연결·미연결 건수를 검토한 뒤 대상과 링크를 함께 저장한다. 영수증은 이관 당시 건수와 누락 사유를 보관한다. 이관 과정의 주소 계산은 오프라인으로 수행한다.

원본 이관 매핑은 버전이 있는 JSON 파일로 내려받고 다음 검토에서 복원한다. 원본의 제품·인스턴스·형식·SHA-256을 대조해 다시 분석한 동일 파일과 연결한다. 프로젝트·사용자·업무 양식·원본 설정·제외와 계획 선택을 복원하고, 현재 워크스페이스의 팀원과 기존 추가 대상을 확인한다. 적용에는 새 미리보기와 확인이 필요하다. [이관 리허설](PILOT.md#오프라인-원본-이관-리허설)

이관을 적용하거나 완료 결과를 같은 요청으로 다시 확인하면 해당 영수증에 초점을 옮긴다. 상세 상단에 제외한 원본과 적용 당시 경고를 표시하고, 경고 버튼으로 해당 진단을 바로 연다. 개별 원본이 지정된 진단에서는 같은 영수증에서 패키지와 원본 식별자를 대조한 보존 기록을 열며, 진단의 조건과 페이지를 유지한다. 적용 당시 진단이 없는 이전 영수증은 확인 가능 여부를 표시한다.

적용한 영수증의 **이관 결과 대조**에서 당시 원본과 현재 Teamspace 항목의 연결 상태를 확인한다. 패키지·원래 Jira 키·원본 ID·제목으로 찾고, 현재 업무·문서를 열거나 보존한 원본 기록을 읽는다. 첨부 버전은 이관할 때 기록한 크기와 SHA-256을 현재 파일 바이트와 비교한다.

Confluence 공간 XML과 현재 페이지의 사전 대조는 선택적으로 페이지 ID별 검토 파일을 저장한다. 현재의 직접 제한·상속 제한과 확인 불가, ZIP 제한 표시 차이, 누락·버전·계층·파일 증거를 확인하고 같은 내보내기의 적용 범위를 원본 ID로 검토한다. 같은 ZIP을 여러 차례 검토한 경우에는 각 파일의 확인 ID를 ZIP의 현재 페이지 목록과 대조하고 중복을 뺀 범위를 보고한다. 공간 권한은 수동 확인 대상으로 둔다. [Confluence 사전 대조](PILOT.md#confluence-공간-xml과-현재-페이지-대조)

오프라인 리허설은 선택적으로 Confluence 검토 파일을 받아 해시와 크기가 같은 ZIP 패키지 한 개에 연결한다. 검토 파일 사본은 리허설 디렉터리에 비공개로 보관하고 매 실행에서 해시를 확인한다. 적용 후에는 같은 패키지의 영수증을 조회해 제외·문서 연결·원본 보관·영수증에 없는 페이지를 집계한다. 별도 복원 결과와 건수·해시를 비교하고 보고서에서 원본 페이지 ID를 생략한다. 확인이 필요한 원본 대조는 자료가 일치해도 검토 상태를 유지한다. [오프라인 이관 리허설](PILOT.md#오프라인-원본-이관-리허설)

**전체 이관 검증**은 영수증의 대상 상태를 집계하고 모든 원본 첨부 버전의 파일을 읽어 결과를 JSON으로 내보낸다. 패키지별 티켓·문서의 상태 건수나 대상 연결 오류를 누르면 해당 패키지와 조건으로 원본 목록을 열고 집계는 계속 표시한다. 파일럿 리허설에서는 서로 다른 원본 제품의 티켓·문서·링크를 한 프로젝트에 적용하고, 별도 물리 복원본에서 같은 검증을 실행한다. 연결된 댓글·문서 이력·작업 시간·활성 업무 관계의 SHA-256도 건수와 함께 비교한다. 이관 때 자동으로 만든 현재 페이지 이력과 휴지통에 보관된 문서 이력도 검사한다.

연결된 Jira 업무와 Confluence 페이지는 보존 원본의 ID와 Jira 원래 키가 같은 Teamspace 대상을 가리키는지 확인한다. 이후 영수증은 앞선 이관의 연결 근거를 재사용할 수 있다. 연결 인덱스 오류는 **대상 연결 오류**에 집계하고 해당 패키지에서 **원본 주소·키 연결 오류**가 표시된 행과 보존 원본을 연다. 오프라인 리허설은 이 검사를 통과한 뒤 물리 백업과 복원을 진행한다.

Jira 상태 이력 검증은 영수증에 보관된 변경 중 현재 티켓에 표시되는 항목을 확인한다. 중복·제외·접근 제한·연결 미확인을 구분하고, 표시된 항목의 티켓 ID·원본 변경·상태·작성자·시각을 해시로 대조한다. 보고서에는 집계와 해시를 남긴다. 보관한 파일의 이력 범위는 Jira 내보내기 방식에 따라 확인한다.

Jira 업무 관계 검증은 영수증에서 적용한 관계의 식별자를 기준으로 양쪽 업무와 방향·유형을 현재 연결과 휴지통에서 대조한다. 연결 누락·불일치와 업무를 확인할 수 없는 경우를 구분하고, 검증 결과에서 해당 보존 원본을 연다. 관계 식별자를 저장하지 않았던 범위는 이관 당시 건수와 차이를 표시한다. 오프라인 리허설은 복원 전에도 누락을 탐지한다.

이관 검증에서 업무 연결·시각·작성자를 확인할 수 없는 변경이나 제외·접근 제한 건수를 선택해 해당 원본 변경 그룹을 연다. 집계와 원본 목록은 티켓의 표시 기준을 함께 사용한다. 페이지를 넘길 때 영수증 버전과 목록 해시를 확인한다.

새 이관 영수증은 패키지별 원본 수량, 첨부 버전 연결 수량, 보존 원본의 SHA-256 기준값을 적용과 함께 저장한다. 현재 검증에서 보존 원본 누락과 같은 건수의 원문·메타데이터 변경도 찾는다. 현재 티켓·문서의 편집이나 휴지통 이동은 원본 검증값과 별도로 대상 상태에 반영한다. 원래 제외한 객체와 함께 제외된 하위 원본도 이관 제외로 표시한다. 형식 33 자체 백업은 기준값과 제외 표시를 보존하며 기준과 다른 원본이 든 백업을 거절한다. 예전 영수증은 남아 있는 당시 수량을 사용한다.

주 입력은 Jira 관리자 XML 백업과 별도 첨부파일 묶음, Confluence Server 전체 공간 XML ZIP이다. Jira CSV의 반복 Comment/Attachment 헤더, 검색 XML과 REST/Importers JSON은 별도 형식으로 판별한다. CSV만으로 작성자·전체 이력·첨부 바이트가 보존된다고 판단하지 않는다. Jira 관리자 백업에도 첨부 바이트는 별도이며, JSON Importers 명세를 UI의 완전한 JSON 내보내기 명세로 취급하지 않는다.

원본 인스턴스·객체 종류·원본 ID를 기준으로 Teamspace ID를 매핑하고 원래 키·URL·시각·작성자·원문 해시를 보관한다. 이름만으로 팀원을 합치지 않는다. 이관 영수증과 원본 기록에 원본 신원·변경 이력·첨부 버전을 보존하고, 현재 업무·문서에서 원본을 찾아볼 수 있게 한다. Confluence Page/historicalVersions/BodyContent 관계를 따라 버전을 복원하고, 양쪽 ID를 확보한 뒤 문서/티켓/include 링크를 재작성한다. 모르는 매크로는 원문과 대체 표시·손실 항목으로 남기며 누락 첨부를 자동 다운로드하지 않는다. 제한된 문서/댓글을 팀 전체에 조용히 공개하지 않고 적용 차단 또는 명시적 제외로 보고한다.

Confluence 본문의 제목 참조는 원본 인스턴스와 명시한 공간 또는 현재 원본 문서의 공간에서 찾는다. 다른 페이지의 첨부 링크와 이미지는 본문이 지정한 소유 페이지에서 확인하며, 첨부 ID가 있으면 해당 버전을 사용한다. 후보가 없거나 원본에서 유일하지 않으면 원문과 변환 진단을 남긴다. 미리보기 진단에서 해당 패키지의 원본 객체를 바로 열어 확인할 수 있다. [Confluence 저장 형식의 리소스 식별자](https://confluence.atlassian.com/doc/confluence-storage-format-790796544.html#ConfluenceStorageFormat-Resourceidentifiers)

Confluence 본문에 복사한 첨부 다운로드 주소도 같은 소유 페이지 기준으로 확인한다. 명시된 원본 버전의 정확한 파일을 사용하며, 버전 없는 주소는 현재 본문에서 확인된 파일에 연결할 수 있다. 확인할 수 없는 주소는 원래 경로에서 열도록 남긴다. Jira 설명의 일반 ADF 텍스트 링크는 확인된 티켓 주소를 현재 업무로 연결하고, 댓글이나 세부 위치 주소는 원래 목적지를 유지한다.

PDF·Office 미리보기 매크로는 파일명, 소유 페이지와 첨부 ID를 확인해 같은 위치에 다운로드 링크를 저장한다. 대상이 모호하거나 과거 문서의 정확한 첨부 버전 근거가 없으면 원문과 진단으로 남긴다. 수동·공동 편집에서도 파일 패널에서 최신 또는 과거 버전을 골라 본문에 연결할 수 있다. 저장본의 링크는 해당 버전을 다운로드하며, 원본과 같은 문서의 첨부가 휴지통에 있어도 보관 파일을 읽을 수 있다. [첨부와 버전 API](API.md#첨부와-버전)

일반 본문 링크도 원본 패키지에 설정한 서버·설치 경로와 이관한 페이지 ID 또는 공간·제목을 대조한다. 상대 주소의 대상은 같은 원본 인스턴스에서 찾고, 절대 주소는 명시해 둔 다른 원본의 고유 대상도 확인할 수 있다. 변환한 참조에 원래 표시 이름을 사용하고, 확인한 절은 절 링크로 연결한다. 추가 이관과 변경분 반영은 원본 매핑이 남아 있는 기존 문서를 사용하며, 변경분은 현재 본문을 이전 이관 기준과 대조한 뒤 적용한다.

Confluence Server·Data Center의 짧은 주소를 페이지 ID로 해석하고 같은 서버·설치 경로의 원본 연결을 통합 검색에서 찾는다. 본문 이관에서 원본 대상이 확인되면 짧은 주소도 문서 참조로 변환하며, 같은 원본의 확인된 제목이나 앵커는 절 링크로 연결한다. 기존에 옮긴 본문에 남은 짧은 주소는 붙여넣어 검색한다. [Confluence 주소 형식](https://support.atlassian.com/confluence/kb/the-differences-between-various-url-formats-for-a-confluence-page/)

적용을 막는 개별 원본 항목은 이관 진단에서 정확한 패키지와 객체를 확인한 뒤 제외 목록에 추가한다. 제외 목록을 변경하면 기존 미리보기를 닫고 새 미리보기에서 하위 기록을 포함한 적용 범위를 다시 검토한다. 사전 검토 JSON은 패키지 해시, 변환·매핑·제외 집계와 진단 코드별 건수로 검토 상태를 기록한다. 리허설 검증은 별도 복원본이 일치해도 적용 영수증의 경고와 이전 영수증의 진단 부재를 검토 대상으로 기록한다.

서버가 보관한 미리보기 계획에 패키지 해시·매핑 버전·대상 버전을 고정한다. 같은 패키지 재적용은 중복 생성하지 않고, 대상 변경은 충돌로 중단한다. 적용은 DB와 새 첨부 바이트를 복구 가능하게 묶으며 기존 업로드를 전체 교체하지 않는다. `origin:import`를 사용해 상태 자동화와 외부 발신 이벤트를 만들지 않는다. 완료 근거는 개수·원본 ID·작성자·이력·첨부 해시·양방향 링크 대조와 실패/재시작 복구다.

합성 자료로 분석·매핑·적용·복원을 검증한다. 오프라인 리허설에서는 패키지 등록, 브라우저에서 검토한 매핑과 적용, 별도 물리 복원 및 대조를 한 절차로 실행한다. 팀 자료 규모의 합성 리허설에서는 Jira 티켓 간 관계와 Confluence 문서 계층·업무 참조, 첨부파일을 이관한 뒤 원본과 복원본에서 대조한다. 실제 패키지에서는 Jira 관리자 백업과 별도 첨부 구성, Confluence 6.9.1의 공간 내보내기 범위, 조직별 매크로와 권한, 누락된 자료를 확인한다. [오프라인 이관 리허설](PILOT.md#오프라인-원본-이관-리허설)

분할 수집한 Jira REST ZIP은 리허설 준비에 수집 계획을 연결해 묶음 누락·중복과 업무 구성이 달라진 ZIP을 적용 전에 걸러낸다. 원본 서버·프로젝트와 업무 ID·현재 키를 묶음별로 대조하고 같은 계획의 원본 인스턴스를 확인한다. 보관한 계획과 연결 범위를 별도 물리 복원본에서 재검증한다. [Jira 프로젝트 분할 수집](PILOT.md#jira-프로젝트-분할-수집)

영수증에서 Jira 업무와 Confluence 현재 페이지의 연결 상태를 파일별로 확인한다. 리허설은 분석 때 센 업무·페이지 수를 영수증의 원본 수와 대조한다. 원본만 보관되고 티켓이나 문서가 생기지 않은 행은 검토 대상으로 기록하며, 건수 불일치와 연결 오류는 실패로 기록한다. 복원 뒤에는 원본별 연결 상태와 대상의 해시를 비교한다.

사전 분석 보고서를 지정한 리허설 준비는 파일 바이트와 매니페스트의 순서·제품·인스턴스, 저장한 분석 결과를 대조한다. 실행 전과 실제 읽을 때 패키지 한도를 검사한다. 준비가 끝나면 사용한 보고서의 SHA-256을 준비·복원 검증 기록에 남긴다.

원본 Confluence XML에서 제한 대상이 정확한 객체로 확인되면 사전 분석은 검토 상태로 기록하고 원래 오류를 보존한다. 리허설 준비 때 오류의 종류와 원본 객체 연결을 다시 확인한다. 제한 페이지와 확인된 하위 기록은 적용 단계에서 명시적 제외가 필요하다. 제한의 대상이나 권한 집합이 불분명한 원본은 사전 분석에서 중단한다.

ZIP에 연결한 Confluence 검토에서 읽기 제한을 확인하면 오프라인 이관 미리보기에서 해당 페이지와 확인된 하위 기록을 제외할 때까지 적용을 보류한다. 확인된 제한은 동일한 Confluence 인스턴스의 다른 패키지에도 적용한다. 서버에 보관된 미리보기에는 확인된 제한 범위의 해시를 기록한다. 리허설 검증은 이전 영수증에서도 해당 페이지가 문서로 연결되어 있으면 실패를 기록한다. 페이지 ID는 집계 보고서에서 생략한다.

## Jira 작업 시간 이관

Jira 관리자 XML의 작업 기록과 REST·Importers JSON의 개별 작업 시간에서 이관할 업무, 작성자, 작업일, 초 단위 길이를 확인한다. 날짜는 기록에 명시된 현지 날짜를 유지한다. 팀원으로 명시적으로 매핑한 작성자의 기록을 업무의 작업 시간과 프로젝트 보고서에 함께 반영한다. 제한된 기록은 제외하기 전까지 적용을 차단한다. 매핑되지 않은 작성자나 기준이 불명확한 날짜·시간 단위는 원본에 보관하고 확인 항목에 표시한다. 부분 REST 페이지는 진단에 남긴다. [Jira Data Center 작업 기록 API](https://developer.atlassian.com/server/jira/platform/rest/v11003/api-group-issue/), [Jira JSON 작업 시간 예시](https://confluence.atlassian.com/servicedeskcloud/importing-data-from-json-1097176631.html#ImportingdatafromJSON-Worklogs).

적용 건수와 원본에만 보관한 건수를 미리보기와 영수증에 남긴다. 작업 시간과 보관 원본은 다른 업무 데이터와 같은 트랜잭션에 저장하며 원본 ID로 연결한다. 자체 백업은 원본과 정확한 초 단위를 함께 복원한다. 기존에 적용한 이관 영수증과 부분 데이터의 운영 리허설은 따로 검토한다.

## 보고서와 주간 문서 연결

프로젝트 개요는 현재 상태를 집계한다. 기간 보고서와 흐름 차트에는 업무 생성·삭제와 상태 전이를 구조화한 변경 기록이 필요하다. 업무 작업과 같은 트랜잭션에 이전·이후 상태, 당시 분류, 발생 시각, 출처를 기록한다. 수집 시작 전이나 원본 이력의 누락 구간은 보고서에 표시한다.

팀 보고서에 선택한 시간대의 날짜 경계, 완료 업무·완료 전이·재완료 구분, 관측 구간과 일별 상태를 구현했다. 주간 문서를 만들 때 기간·필터·기준 시각·집계·참조 업무를 다시 계산해 보관하고 양방향으로 연결한다. 실제 작업 시간은 티켓에 작성자와 작업일을 저장하고 별도 보고서에서 기간·작성자·업무를 기준으로 집계한다. 이후 결정 기록과 알림의 연결을 확장한다.

자동화 API에서 프로젝트 범위의 현재 집계와 보관본을 조회하고 쓰기 키로 주간 문서를 생성한다. 보관본·초안·첫 문서 버전·업무 링크·생성 요청을 한 트랜잭션으로 저장한다. 같은 작업자가 같은 제목과 조회 조건으로 재시도하면 저장 당시 보관본을 반환한다. 이동하거나 삭제한 업무의 관측 기록은 원래 프로젝트에 남기고 현재 문서는 현재 소속으로 조회한다.

상태별 체류 시간은 선택 기간 안에 실제로 다른 상태로 이동한 횟수를 출발 상태 ID별로 집계한다. 이탈 직전 유형과 담당자로 범위를 적용하고, 같은 관측 구간에서 진입과 이탈을 모두 확인한 표본의 중앙값·최장 시간을 계산한다. 조회 시점의 미완료 업무는 선택 기간과 독립적으로 현재 조건에 맞춰 가장 오래 체류한 순서로 보여준다. 기준점이나 복원 이후에 실제 진입을 관측하지 못한 업무는 진입 시점 미관측으로 표시한다. 보관본에는 조회 시각의 두 집계를 고정하고 주간 문서에 요약과 주요 업무 링크를 남긴다.

진행 차단 보고서는 현재 프로젝트 또는 저장된 보기의 미완료 업무를 집계한다. 방향을 확인한 차단 관계의 열린 원인 업무, 작업 달력으로 확인한 간트 일정 충돌, 저장된 GitLab의 병합 차단과 최신 실패·수동 실행 대기 파이프라인을 근거로 삼는다. 진행 차단과 릴리스 준비 점검의 파이프라인 집계는 보드와 같은 실행 그룹을 사용한다. 한 업무의 여러 GitLab 근거는 각각의 건수로 표시하고 원인별 업무 수에는 한 번만 센다. Jira 이관 관계는 원본으로 연결 대상과 방향을 확인해 같은 프로젝트와 다른 프로젝트의 차단 원인을 표시한다. 같은 방향의 Teamspace 관계가 있으면 우선한다. 마감일이나 계획 종료일, 우선순위, 업무 키 순서로 정렬한다. 차단 원인은 보기 밖에 있어도 조회할 수 있으며, 범위 제한 API 키는 연결의 양쪽 프로젝트가 허용되어야 건수와 근거에 포함한다. 다음 페이지를 읽을 때 보고서가 바뀌었으면 새 결과의 처음부터 조회한다.

릴리스 계획의 **릴리스 준비 점검**으로 연결된 미완료 업무의 일정 미정, 릴리스 기준일 뒤에 끝나는 일정, 업무 차단·일정 충돌·GitLab 조치를 함께 확인한다. 릴리스 목표일을 기준으로 삼고 비어 있으면 계획 종료일을 사용한다. 공유 보기를 함께 선택하면 두 조건이 모두 맞는 업무에 적용한다. 현재 릴리스와 원인을 보존한 주소, 계획·간트·티켓 이동, 프로젝트 범위 읽기 API를 제공한다. 릴리스와 연결 업무가 바뀌면 이전 보고서 버전으로 페이지를 읽거나 회의 초안을 만드는 요청을 보류한다.

회의 초안은 조회 버전과 프로젝트·보기·원인을 다시 확인한 뒤 집계와 처음 20개 업무의 당시 값을 일반 문서의 첫 저장본에 보관한다. 차단·일정 충돌은 업무마다 사례를 세 건까지 싣고 전체 건수를 함께 기록한다. 문서와 업무의 양방향 참조는 대상 업무부터 최대 30개를 연결한다. 현재 상태 링크는 같은 공유 보기와 원인으로 진행 차단 보고서를 다시 연다. 문서·첫 버전·참조·생성 요청 기록은 한 트랜잭션에 저장하고 같은 요청으로 저장 결과를 확인할 수 있다.

필드 집계는 전체 프로젝트 또는 저장된 보기의 현재 조건으로 업무를 선택해 필드 값으로 묶는다. 값이 비어 있는 업무와 필드 대상 유형에 속하지 않는 업무를 각각 표시한다. 숫자 통계와 그룹별 업무 이동을 제공한다. 그룹을 열 때 집계 이후 바뀐 데이터를 확인해 다시 조회할 수 있게 한다.

행과 열에 상태·담당자·요청자·우선순위·업무 유형 또는 프로젝트의 사용자 정의 필드를 선택한다. 현재 워크플로 상태, 업무 유형, 팀원, 사용자 정의 값에 대응하는 현재 이름을 표시한다. 다중 선택은 양쪽 선택값이 만나는 셀에 업무를 한 번씩 추가한다. 행·열 각각의 합계와 전체 업무 수는 해당 업무를 한 번씩 세며, 숫자 통계는 선택한 열에 속한 횟수와 관계없이 업무별 입력 한 건을 사용한다. 현재 보기와 비교 기준을 셀의 업무 목록 및 일괄 편집에 함께 적용하고, 범위나 관련 설정이 바뀌면 다시 조회한다.

합계 항목으로 스토리 포인트·계획 작업 시간·사용자 정의 숫자 필드를 선택해 업무 수와 합계를 함께 본다. 해당 행·열·셀 또는 전체 범위 안의 업무별 값을 한 번씩 더한다. 저장된 0과 미입력, 합계가 유한 범위를 넘은 경우를 구분한다. 합계를 구성하는 업무는 상세에서 값과 함께 열고, 값과 조회 조건을 버전 비교에 사용한다. 공유 주소와 저장 집계의 조건에 합계 항목을 보존하며 자체 백업 형식 107로 복원한다. [업무 필드 집계](API.md#업무-필드-집계)

저장된 업무 보기에서 해당 조건을 선택한 필드 집계를 열 수 있다. 조회가 성공한 뒤 프로젝트·저장 보기·집계 기준·비교 기준을 공유 주소에 기록한다. 공유 주소를 열면 현재 업무와 저장된 조건으로 집계한다. 삭제되었거나 다른 프로젝트에 속한 보기를 요청하면 해당 조회의 오류를 표시한다. 티켓을 열고 닫을 때 조회 조건을 유지하고, 결과에서 같은 저장 보기의 업무 목록이나 보드로 이동한다.

프로젝트 팀원은 조회한 필드 집계 조건을 이름으로 저장하고 목록에서 다시 연다. 행·열 기준과 저장된 업무 보기 ID를 보존하며, 현재 보기 필터와 업무 값을 사용해 집계한다. 이름이나 조건을 바꾸거나 삭제할 때 저장 버전을 확인한다. 원래 보기나 행·열의 필드가 삭제된 집계는 범위 확인 오류를 표시하고 조건 교체를 허용한다. 자체 백업 형식 92부터 저장 집계를 복원하며, 형식 95부터 사용자 정의 비교 기준을 함께 저장한다. 복원 전 수정 요청을 구분할 수 있게 버전을 관리한다.

## 완료 판단

화면 시안이나 좁은 기능 검사만으로 제품 완성을 선언하지 않는다. 실제 실행 상태·저장 및 재시작·핵심 업무 흐름·브라우저 동작·데이터 이동을 검증하고 미구현 범위를 명시한다. 최초 개발 묶음은 제품 전체 완료와 구분한다.
