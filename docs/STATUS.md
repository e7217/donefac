# 개발 상태

2026-11-20 기준 실행 가능한 개발본에 공동 편집·프로젝트 워크플로·공유 보기, 독립 계획 관리·API 키, 업무 달력·자동 일정 제안·마일스톤·기준 계획·프로젝트 간 작업량, 사용자 정의 업무 양식과 문서 참조·고정 버전 포함·접기·이력 비교·업무 현황과 GitLab 상태 자동화·외부 발신 웹훅, 오프라인 원본 이관, 프로젝트 보고서와 주간 문서, 간트의 스프레드시트 일정 붙여넣기, 티켓 작업 시간 기록·프로젝트 보고서, Jira 작업 시간 이관과 사용자 정의 필드 필터·집계를 구현했다. 전체 제품 목표는 진행 중이다. 복잡한 보안·SSO·기업용 계정 엔진은 최신 사용자 지시에 따라 범위에서 제외한다.

## 검사 결과

- 전체 서버 검사 649개와 최종 파일럿 빌드의 일정 Chromium 검사 14개를 통과했다. 360px에서 같은 후행 업무의 여러 입력 행을 검토해 날짜와 선행 연결의 추가·변경·해제를 함께 저장하고 되돌렸다. 충돌과 중복의 원래 행 표시, 적용 응답 유실 뒤 동일 결과 재확인을 검증했다. 합성 500행에서 업무 날짜 한 건과 선행 연결 500건을 한 번에 적용·되돌렸고, 연결 저장을 실패시켰을 때 모든 업무 날짜와 연결이 롤백됐다. 표준 파일럿과 별도 복원도 통과했다.
- 전체 서버 검사 644개와 최종 파일럿 빌드의 GitLab Chromium 검사 9개를 통과했다. 360px에서 웹훅으로 차단된 업무의 원본 MR·필수 필드·목표 상태를 확인하고, 제목·댓글 초안을 유지하면서 일반 저장으로 상태를 변경했다. 당시의 차단 기록과 중복 웹훅의 동작, 형식 64의 실행 기록 복원과 이전 형식 가져오기를 검증했다. 합성 팀원 20명이 HTTPS로 로그인해 공동 편집 160건을 보존했고, 재접속·재시작·별도 복원에서 문서와 티켓 일정·선후행 연결을 확인했다.
- 전체 서버 검사 642개와 최종 파일럿 빌드의 문서 Chromium 검사 14개를 통과했다. 360px에서 팀 템플릿 등록·이름 변경·보관·복원, 프로젝트 선택과 최신 버전 확인 중 제목 보존을 검증했다. 원본을 영구 삭제한 뒤 생성한 문서에 표와 서식이 남고 자체 절 링크가 새 문서로 연결됐다. 응답 유실 뒤 동일한 요청으로 첫 저장본 한 건을 확인했다. 프로젝트와 팀 공통 템플릿의 백업 복원, 문서 생성 실패의 원자적 롤백, 표준 파일럿도 통과했다.
- 전체 서버 검사 639개와 최종 파일럿 빌드의 Chromium 검사 22개를 통과했다. 360px 간트에서 금요일 종료와 월요일 휴무를 반영해 화요일을 제안했고, 저장 응답을 잃은 뒤 같은 요청으로 티켓 한 건과 연결 한 건만 확인했다. 티켓 상세에서는 선행 일정 충돌 뒤 새 업무의 날짜·제목과 기존 티켓·댓글 초안을 유지했다. 티켓·연결·알림·이력의 원자적 저장, 별도 자체 백업 복원의 날짜와 연결, 표준 파일럿도 확인했다.
- 전체 서버 회귀 검사 635개와 긴 이관 업무 키를 포함한 최종 알림 집중 검사 23개를 통과했다. 360px Chromium에서 다른 프로젝트의 업무를 차단 원인으로 연결하고 완료한 뒤 차단 추가·원인 해소 알림을 확인했다. 마감 연기 알림의 두 날짜, 원래 티켓 열기와 읽음 처리, 중복 및 본인 알림 제외를 검증했다. 알림 쓰기 실패 시 관계와 변경 이력 롤백, 기존 SQLite 테이블 업그레이드, 형식 62 백업의 읽음 상태 복원과 표준 파일럿도 통과했다.
- 서버 검사 627개, 최종 빌드의 Chromium 검사 4개와 표준 파일럿 리허설을 통과했다. 360px에서 바뀐 보고서를 다시 확인할 때 회의 제목을 보존했고 저장 응답이 유실된 뒤 같은 ID로 문서 한 건을 확인했다. 두 번째 페이지에서 처음 20개를 검토하는 흐름과 보고서가 갱신된 경우도 검사했다. 작성 당시 수치와 원인 업무 내용을 보존하면서 문서 링크로 같은 공유 보기와 원인 필터의 현재 보고서를 열었다. 서버에서는 연결 저장 실패 시 문서·첫 버전·연결·요청 기록이 함께 되돌아가고, 자체 백업 복원 후 문서와 양방향 연결이 유지되는 것을 확인했다.
- 360px 진행 차단 보고서에서 공유 보기·원인 필터, 다른 프로젝트 업무를 열고 원래 버튼으로 돌아오기, 차단 관계 수정 후 새로고침을 확인했다. 목록을 넘기는 동안 업무가 바뀌면 같은 조건으로 첫 페이지를 다시 읽었다. 읽기 API 키의 범위 밖 원인이 상세와 건수에서 모두 제외됐고, 같은 브랜치의 다음 실행이 성공하면 이전 실패가 집계에서 빠졌다. 전체 서버 실행 622개 중 621개가 통과했다. 응답에 추가한 업무 버전을 테스트 기대값에 반영한 후 보고서·API 키 서버 검사 14개를 다시 통과했다. 타입 검사, 최종 빌드의 Chromium 보고서 검사, 인접 업무·문서·보고서 검사와 파일럿 백업·복원 리허설도 통과했다.
- 서버 전체 실행 611개, 별도로 실행한 HTML 렌더러 검사 4개와 타입 검사를 통과했다. 빌드한 파일럿의 360px 간트에서 저장 보기·검색·완료 숨기기와 180일 표시 범위를 적용한 보고서를 내려받았다. 양쪽이 보이는 선후행 연결의 충돌과 근무일 간격, 계획·마일스톤·기준선, 범위 밖의 실제 날짜를 대조했다. 숨겨진 업무와 미저장 입력은 보고서에서 제외됐고 입력은 화면에 보존됐다. HTML을 오프라인에서 열어 가로 PDF로 인쇄했다. 별도 보고서에는 업무 72개와 연결 71개를 넣어 16페이지로 인쇄했다. 인접 간트 Chromium 검사 9개와 표준 파일럿 리허설도 통과했다.
- 전체 서버 검사 610개(신규 업무 붙여넣기 12개 포함)와 빌드한 파일럿의 360px Chromium 시나리오를 통과했다. 유효하지 않은 날짜가 있는 행의 줄 번호를 표시하고 번호 배정 전 전체 적용을 막았다. 정상 행의 실제 저장 순서, 상태·담당자·날짜, 티켓과 간트 표시를 확인했다. 생성 응답이 끊기면 같은 검토 ID로 두 업무의 결과를 읽었고, 결과 확인 뒤 목록 조회만 끊기면 새 생성 요청 없이 목록을 다시 읽었다. 서버에서는 두 번째 행의 저장 실패가 업무·번호·이력·알림·발신 이벤트를 함께 되돌리는 것과, 재시작 후 결과 재확인 및 양식·담당자 변경 시 적용 차단을 검증했다. 기존 CSV 내보내기와 간트 일정 붙여넣기 Chromium 검사 5개와 표준 파일럿 브라우저·백업 복원 리허설도 통과했다.
- 전체 서버 검사 598개와 빌드한 파일럿의 CSV 및 인접 Chromium 검사 8개를 통과했다. 360px에서 저장된 검색·상태 조건과 변경한 업무 순서를 적용해 현재 목록과 선택 업무 CSV를 내려받았다. 한글·따옴표·줄바꿈과 수식처럼 시작하는 제목을 확인했다. 내보낸 시작일·종료일을 수정해 간트 API에서 미리보기·적용·되돌리기를 검증했으며 목표 마감일과 다른 업무 속성도 대조했다.
- 전체 서버 검사 595개, 문서·후속 업무·연결 문서 미리보기 Chromium 검사 15개와 빌드한 파일럿 검사를 통과했다. 360px에서 다른 프로젝트의 직접 연결 업무와 본문 참조를 구분하고, 미완료·종료와 결정 근거 필터를 함께 적용했다. 요청 전 원문을 읽지 않았으며 문서 편집 뒤에도 결정 당시 버전을 열었다. 업무를 닫으면 원래 카드에 포커스가 돌아왔고, 다른 작업자가 바꾼 상태·담당자·마감일만 새로 불러온 뒤 문서의 미저장 초안이 유지됐다.
- 전체 서버 검사 593개, 일괄 편집·워크플로·필드 필터 Chromium 검사 4개와 빌드한 파일럿의 일괄 편집 검사 2개를 통과했다. 360px에서 마감일을 지정·해제하고, 쉼표가 포함된 기존 라벨을 선택해 정확히 제거했다. 다른 작업자의 편집을 감지하면 전체 적용을 중단했으며, 최신 검토에서 입력과 새 라벨을 보존했다. 필수 마감일·라벨을 비우는 상태 전이는 차단했고, 적용 응답은 재시작 후에도 같은 영수증을 반환했다.
- 같은 빌드에 HTTPS로 로그인한 Chromium 세션 20개가 92.5초 동안 일곱 차례 공동 편집해 편집 180건을 보존했다. 재접속 시 오프라인 편집을 한 번만 병합했다. 재시작·별도 복원 후 문서·복구 사본·티켓 일정·선후행 연결·업무 목록이 일치했다.
- 전체 서버 검사 591개, 후행 일정 Chromium 검사 3개, 기존 간트 Chromium 검사 6개와 빌드한 파일럿 검사 2개를 통과했다. 360px에서 필터에 숨겨진 후행 업무 두 단계까지 검토하고, 돌아간 뒤 날짜와 포커스를 보존했다. 한 번의 적용과 되돌리기로 기준 티켓과 후행 티켓 세 건을 함께 변경·복원했다. 적용 응답이 끊긴 경우 같은 결과를 읽어 중복 저장을 막았으며, 다른 작업자가 후행 티켓을 바꾼 경우 전체 적용을 중단했다. 서버는 한쪽 날짜와 주말 종료일을 그대로 보존하고 선행 조건이 맞지 않는 입력을 차단했다.
- 전체 서버 검사 589개, GitLab 관련 Chromium 검사 5개와 빌드한 파일럿 검사 2개를 통과했다. 360px에서 하위 그룹 저장소 검색·페이지 이동·초안 추가·연결 미리보기와 동기화한 MR을 확인했다. 조회 중 주소나 토큰을 바꾸면 이전 결과를 폐기했다. 별도 물리 복원에서 검색으로 추가한 저장소 매핑과 원래 Jira 키로 연결된 MR을 확인했다. HTTPS 팀 접속 모드에서 세션과 같은 출처를 확인했으며, 파일럿 Playwright에서는 브라우저 시나리오를 실행하고 Jira·Confluence 명령 검사는 각 Node 실행기로 통과했다.
- 모의 Confluence Server에서 페이지 500개와 제한 응답 1,000개를 확인하고 실제 이관 분석기로 XML ZIP을 대조했다. 501번째 페이지가 있을 때 범위를 나누도록 중단했다. 대조 검사 25개에서 누락·버전·상위 관계·공간 ID 불일치, 상속된 제한·확인 불가·첨부 바이트 누락·공간 권한, 결과의 원문과 인증 정보 비노출을 확인했다. 전체 서버 검사 586개와 기존 Jira 수집 및 오프라인 이관·복원 검사도 통과했다.
- 모의 Jira Data Center에서 합성 업무 355건을 검색 페이지 4개로 수집했다. 분석기는 업무·댓글·작업 시간을 각각 355건씩 읽었다. 별도 리허설에서 수집 ZIP을 검토·적용하고 간트 날짜, Jira 상태 변경, 91초 작업 시간, 제한 댓글 제외와 첨부 바이트를 확인했다. 물리 복원 후 첨부와 이관 결과가 일치했다. 전체 서버 검사 586개, 수집 검사 8개와 기존 이관 리허설 검사를 통과했다.
- 360px에서 UTF-8 Markdown 파일을 읽어 미리보기로 검토하고 하위 문서에 저장했다. 표와 체크리스트·코드·상대 링크가 본문에 남고 같은 파일의 제목 링크는 새 문서의 절을 열었다. HTML은 텍스트로 표시했고 미리보기와 편집기가 원격 이미지를 읽지 않았다. 잘못된 UTF-8, 늦게 끝난 파일 읽기, 미리보기 이후 입력 변경을 각각 확인했다. 저장 응답과 목록 조회가 끊겨도 초안과 첫 이력은 한 건이었다. 서버 검사 586개, 문서 Chromium 검사 6개와 빌드한 파일럿의 가져오기 검사 2개를 통과했고, 물리 복원에서 초안·절 링크·생성 요청 기록이 일치했다.

최초 계획 이관은 기존 이름·대소문자·공백을 보존하고 바뀐 업무의 버전을 올린다. 자체 백업 가져오기가 성공하면 기존 API 키를 모두 회수하고 자동화 규칙은 비활성으로 복원하며 외부 웹훅 설정·전송 대기·수신 기록을 초기화한다. 트랜잭션 도중 실패하면 기존 키·규칙·수신처·전송 대기도 보존한다. API 사용 범위와 호출 예시는 [API 사용법](API.md)에 기록했다.

일정의 입력·연결·자동 제안·기준 계획과 이전 형식 백업의 동작은 [일정·간트 사용법](SCHEDULING.md)에 정리했다. 업무 양식 사용과 자동화 입력 예시는 [API 사용법](API.md)의 사용자 정의 필드 절을 참고한다. 유형·필드·선택지 이름을 바꿔도 값의 ID는 유지되며, 이전 형식의 백업에 없는 업무 양식은 기본값으로 초기화한다. schema5·6의 달력·마일스톤·기준 계획과 schema6의 업무 양식은 보존한다. 참조·포함·접기 블록은 schema7 이상 자체 백업과 문서 JSON 형식 2에 보존한다. 업무 목록은 자체 백업 형식 20과 문서 JSON 형식 3부터, 업무 현황은 자체 백업 형식 22와 문서 JSON 형식 4부터 보존한다. 고정 버전 포함은 자체 백업 형식 26과 문서 JSON 형식 5에 기록한다. 전체 백업은 원본의 활성 이력과 휴지통 이력을 함께 복원한다. 안내 상자·상태 배지는 자체 백업 형식 46과 문서 JSON 형식 6에 기록한다. 절 ID는 자체 백업 형식 49와 문서 JSON 형식 7에 기록한다. 문장 댓글의 선택 범위와 원문 저장본은 자체 백업 형식 50에 기록한다. 본문 목차는 자체 백업 형식 54와 문서 JSON 형식 8에 기록한다. 라벨별 문서 목록은 자체 백업 형식 59와 문서 JSON 형식 9에 기록한다. 공동 편집 형식 1~8은 Yjs 데이터를 유지한 채 프로토콜 9로 원자적으로 이전한다. 이전 형식의 미전송 편집은 읽기 전용으로 열고 원하는 보관 데이터를 새 사본으로 복구할 수 있다.

자동 제안은 30분 유효한 서버 기록을 검토 후 적용하며, 적용 결과는 7일간 보관해 재시도로 날짜가 두 번 바뀌지 않도록 한다. 업무·이력·되돌리기·적용 기록은 같은 트랜잭션에 저장한다.

## 현재 한계

- 이력 비교 한도는 본문 JSON 8MiB·별도 제목 64KiB·30,000개 노드·구조 깊이 256이다. 반복이 많은 문서는 계산 한도에 도달한 구간 전체를 삭제/추가로 표시할 수 있으며 동일하다고 생략하지 않는다. 한 화면은 최대 60행이고, 변경 없는 부분과 구조 상세는 명시적으로 펼친다.

- 최신 원문을 가리키는 포함은 참조 새로고침 때 갱신한다. 표시 한도는 포함 5단계·구조 60단계·확장 노드 합계 최대 4,000개다. 검토본과 발행본에서는 해당 블록의 저장된 참조 이름과 ID를 보여준다. 고정 버전 본문은 포함·업무 목록·업무 현황 등 동적 블록의 당시 이름과 설정을 표시한다. 본문에 삽입한 외부 이미지는 해당 주소에서 제공하는 파일을 표시한다. 휴지통에서 원본을 영구 삭제하면 고정 버전 조회 불가 안내가 표시된다. 고급 데이터베이스 매크로는 개발 범위에 남아 있다.
- 업무 목록과 업무 현황은 한 문서에 합계 30개까지 추가할 수 있다. 목록은 전체 개수와 최대 20개 업무의 현재 상태·담당자를 보여준다. 현황은 현재 업무를 집계하고 그룹과 티켓을 페이지로 나눠 표시한다. 목록과 펼친 그룹 안의 티켓은 프로젝트 업무 순서대로 표시한다. 참조 새로고침으로 최신 정보를 불러오며 문서 버전은 그대로 유지한다. 저장한 보기가 삭제되면 해당 블록의 이름과 오류를 표시한다. 검토·발행본은 저장 당시의 범위와 집계 기준을 보여준다. 날짜별 집계를 고정해서 문서와 연결할 때는 기존 주간 보고서 보관본을 사용한다.
- 검토는 요청당 지정한 팀원 1명을 대상으로 한다. 검토함에는 현재 배정·수정 요청 상태가 표시되며, 이전 발행본은 문서 이력에서 확인한다. 배지는 현재 작업자 기준으로 앱을 열거나 전경으로 돌아올 때, 검토 상태를 바꿀 때와 전경에서 30초마다 조회한다. 본문의 삽입 이미지는 저장한 파일 버전을 참조한다. 일반 첨부 주소는 휴지통에서 복원하면 다시 열리고, 고정 버전 포함은 저장본에서 직접 참조하는 같은 문서의 보관 이미지를 계속 읽는다.
- 팀 알림은 상단의 앱 내 알림함에서 조회한다. 업무 댓글은 담당자·협력자·개별 및 프로젝트 구독자, 문서 댓글은 작성자·개별 및 공간 구독자에게 보낸다. 배지는 전경에서 30초 간격으로 갱신하며 목록은 한 번에 50개를 조회한다. 대상이 휴지통에 있는 동안 개별 구독이 보관되고, 영구 삭제하면 제거된다. 기존 알림 기록은 유지된다. 이메일·외부 알림은 남아 있다.
- 공동 편집은 문서별 명시적 활성화 방식이다. 본문은 자동 동기화하고 제목·상태·상위 문서·라벨은 별도 저장한다. 원격 커서와 텍스트 선택은 같은 문서·편집 세대에서 지원하는 브라우저끼리 공유하며 포커스를 잃거나 연결을 닫으면 표시를 지운다. 위치 갱신이 30초간 없으면 만료된다. 슬래시 블록 메뉴는 수동 편집에서 제공하며 공동 편집에서는 서식 도구모음을 사용한다. 업데이트 1MiB·문서 JSON 8MiB·누적 Yjs 상태 16MiB 한도가 있다.
- 사용자 정의 필드는 문자·숫자·날짜·단일 선택·다중 선택·확인 여부·팀원·URL을 지원한다. 양식 표시 조건의 기준 값은 확인 여부나 단일 선택을 사용한다. 수식 계산은 남아 있다. 필수 여부는 값의 존재를 검사하므로 숫자 0과 확인 여부 false도 유효하다.
- 자동 일정은 FS·SS·FF·SF 관계와 양수·음수 간격을 근무일 단위로 계산한다. 기간 산정에 필요한 날짜나 선행 연결 날짜가 없거나 완료·취소 업무의 고정 일정과 충돌하면 전체 적용을 막는다. 자동 계산은 프로젝트 10,000개 업무, 한 번 적용은 1,000개 변경, 개별 기간은 3,650근무일까지다. 공휴일은 날짜 예외로 직접 입력한다.
- 시간 배정은 서울 시간의 일별 화면과 서버의 분 단위 UTC 시각을 사용한다. 최대 24시간을 배정하며 날짜 단위 일정·계획 작업량·실제 작업 시간을 각각 관리한다. 겹친 배정을 저장하려 하면 충돌한 업무를 표시하고 입력을 보존한다. [팀원 시간 배정](SCHEDULING.md#팀원-시간-배정)
- 과부하 일정 조정은 프로젝트 안 또는 전체 프로젝트의 작업량을 기준으로 과부하에 기여한 업무를 표시 기간과 마감일 안에서 뒤로 이동한다. 업무의 근무일 수·담당자·계획 시간과 연결을 보존한다. 이동할 수 없는 일정의 초과는 남은 목록에 표시한다. [과부하 일정 조정](SCHEDULING.md#과부하-일정-조정), [프로젝트 간 과부하 조정](SCHEDULING.md#프로젝트-간-과부하-조정)
- 프로젝트별 담당자 작업량은 최대 180일을 계산한다. 기본 가용 시간은 근무일당 480분이며 조정할 수 있다. 주 담당자에게 작업량을 합산하며 프로젝트별 가용 시간과 비교한다. 프로젝트 간 작업량 화면은 14일씩 조회하고, 서버는 요청당 최대 180일·100개 프로젝트·10,000개 대상 업무·36,000개 팀원과 날짜 조합·100,000개 날짜별 업무 배분을 지원한다. 실제 작업 기록을 사용한 계획 자동 조정은 남아 있다.
- 계획 이동은 계획 한 개와 연결 업무를 대상으로 한다. 이동량은 최대 3,650일이며 업무를 포함할 때 연결 업무 1,000개, 프로젝트 업무 10,000개까지 검토한다. 마일스톤의 달성 여부는 수동으로 관리한다. 마일스톤과 업무의 계획 이동은 각각 다루며, 기준 계획 차이는 종료일의 달력일 차이로 표시한다.
- 휴지통에서 업무·문서와 개별 댓글·첨부를 복원한다. 상위 업무나 문서가 휴지통에 있으면 먼저 복원해야 한다. 다른 프로젝트로 옮겨진 문서의 개별 휴지통 항목은 현재 프로젝트 범위에서 찾을 수 있다. 사라진 이정표·관계나 현재 의존성과 충돌하는 연결은 복원 결과에 표시한다. 업무의 기존 상태·유형·필드 설정이 삭제되면 당시 자료를 휴지통에 유지하고 복원을 중단한다. 상위 항목의 영구 삭제는 개별 휴지통 자료와 본문 이력까지 포함한다. 변경·보고·이관 원본의 기록은 각 기능에 남는다.
- 첨부는 파일당 20MiB, 전체 자체 JSON 패키지는 64MiB−1KiB까지다. 초과하면 내용을 누락시키지 않고 오류를 반환한다. 이관한 파일에도 새 버전을 추가할 수 있다. 첨부파일의 복원과 영구 삭제는 전체 버전에 적용한다. 개별 버전 삭제는 남아 있다.
- 자체 JSON 가져오기와 Jira·Confluence 원본 분석·보존·미리보기를 제공한다. 신규 프로젝트 이관, 기존 프로젝트에 대한 새 Jira 업무·Confluence 문서 추가, 기존 Jira 표준·사용자 정의 필드와 Confluence 제목·본문의 변경분 반영, 기존 Confluence 문서의 댓글·이력과 첨부 추가를 지원한다. 기존 Jira 업무에 원본 댓글·작업 시간·첨부파일을 추가할 수 있다. 원본 권한 차이 검토와 운영 내보내기 파일 리허설은 남아 있다.
- 자동화 API는 읽기/쓰기·프로젝트 범위를 검사한다. 팀 접속 모드의 브라우저용 `/api`는 공용 키로 연 세션을 사용하고, 작업자는 앱에서 선택한다. 전체 기능의 자동화 API는 아직 없다. 연동·자동화·외부 수신처 관리는 브라우저용 관리 경로에서 수행한다. [지원 경로](API.md)
- 새 작업 시간은 분 단위로 직접 입력하며 기간 집계는 최대 92일이다. Jira 원본 이관은 매핑된 작성자의 초 단위를 유지한다. 기준 불명확·미매핑 시간은 원본에 보관한다. 이미 적용한 영수증의 소급 반영과 운영 원본을 사용한 검증은 남아 있다.
- 보고서는 최초 실행과 복원 이후 업무 변경부터 관측한다. 원본 이관은 이관 시점의 업무 상태로 시작한다. 조회 기간은 최대 92일, 한 번의 결과는 최대 5,000개 업무, 저장 목록은 최근 100개다. 문서에는 중요도 순으로 최대 30개 업무를 참조하고 전체 결과는 보관본에서 확인한다.
- 진행 차단 보고서는 조회 당시 업무·일정·GitLab 저장 상태를 사용한다. 방향을 확인해야 하는 이관 관계는 집계에서 제외한다. 한 페이지에는 업무 20개를 표시하며 업무별 차단·충돌 사례는 종류당 최대 20개와 전체 건수를 보여준다.
- 필드 집계는 조회 시점의 현재 값과 선택 업무 최대 10,000개를 대상으로 한다. 다중 선택은 선택지마다 업무 수를 집계하므로 그룹별 업무 수를 더하면 전체 업무 수보다 클 수 있다. 그룹의 업무는 50개씩 조회한다.
- GitLab 수동 동기화는 저장소당 MR 최대 1,000개와 최근 파이프라인 50개를 읽는다. 옵션을 켜면 브랜치 최대 500개와 최근 커밋 최대 100개를 추가로 읽는다. 인증된 Push 웹훅은 마지막으로 확인한 브랜치 상태의 기준이다. Push와 수동 조회는 개발 활동 연결만 저장한다. 상태 자동화는 발생 시각이 검증된 MR·파이프라인 이벤트를 사용한다. 실제 운영 GitLab 연결 검증과 웹훅 자동 등록은 남아 있다.
- 외부 웹훅은 최대20개 수신처·동시4건·요청10초·자동5회(기본5/10/20/40초 간격)·종료 기록30일·전체 전송50000건 한도다. 최소 한 번 전달 방식이므로 수신 측은 같은 이벤트 ID를 중복 처리해야 한다. 원문·댓글 내용·사용자 정의 값은 보내지 않으며 이력 UI는 최근50건, 관리 API는 최대100건이다.

## 다음 개발 범위

1. 사용자 정의 필드 집계, 결정 기록과 후속 업무의 연결 확장.
2. 계획·업무 보기와 사용자 정의 필드 보고서의 확장.
3. 실제 팀 접속 주소에서 장시간 공동 편집, 티켓·간트 사용과 재시작 후 접속을 확인.
4. 자동화 확장.
5. 실제 Jira·Confluence 내보내기 파일로 이관을 리허설하고 권한·누락·연결·작성자·이력·파일 해시를 검토.
6. 실제 팀 접속 환경과 장시간 동시 사용, 운영 데이터로의 배포·복원 검증.

목표의 전체 범위는 [개발 계획](PLAN.md)에 유지한다. 검사 통과만으로 미구현 범위를 완료 처리하지 않는다.
