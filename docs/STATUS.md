## 검사 결과

- 360px 화면에서 검색으로 일부 업무를 숨긴 상태에서 키보드로 순서를 저장했다. 숨겨진 업무끼리의 상대 순서와 이동 버튼의 포커스를 보존하고, 새로고침 뒤 목록·보드·문서에서 같은 순서를 확인했다. 데스크톱 드래그에서는 다른 상태의 대상 카드 앞과 빈 열로 이동했다. 서버에서 필수 필드·전이·프로젝트 범위·동시 변경 검증, 운영 데이터와 분리한 재시작 및 형식 23 백업 복원을 확인했다.

- 로컬 예시 자료는 프로젝트 2개·티켓 12개·문서 4개다. 브라우저 검사마다 생성한 고유 합성 자료는 정리한다.

실제 GitLab 운영 서버와의 연결, 여러 팀원의 장시간 동시 사용, 대규모 원본 자료의 이관 및 운영 복원 훈련은 아직 검증하지 않았다. 현재 GitLab 검사는 로컬 모의 서버를 사용한다.

최초 계획 이관은 기존 이름·대소문자·공백을 보존하고 바뀐 업무의 버전을 올린다. 자체 백업 가져오기가 성공하면 기존 API 키를 모두 회수하고 자동화 규칙은 비활성으로 복원하며 외부 웹훅 설정·전송 대기·수신 기록을 초기화한다. 트랜잭션 도중 실패하면 기존 키·규칙·수신처·전송 대기도 보존한다. API 사용 범위와 호출 예시는 [API 사용법](API.md)에 기록했다.

일정의 입력·연결·자동 제안·기준 계획과 이전 형식 백업의 동작은 [일정·간트 사용법](SCHEDULING.md)에 정리했다. 업무 양식 사용과 자동화 입력 예시는 [API 사용법](API.md)의 사용자 정의 필드 절을 참고한다. 유형·필드·선택지 이름을 바꿔도 값의 ID는 유지되며, 이전 형식의 백업에 없는 업무 양식은 기본값으로 초기화한다. schema5·6의 달력·마일스톤·기준 계획과 schema6의 업무 양식은 보존한다. 참조·포함·접기 블록은 schema7 이상 자체 백업과 문서 JSON 형식2에 보존한다. 업무 목록은 자체 백업 형식 20과 문서 JSON 형식 3부터, 업무 현황은 자체 백업 형식 22와 문서 JSON 형식 4부터 보존한다. 공동 편집 형식 1~3은 Yjs 데이터를 유지한 채 프로토콜 4로 원자적으로 이전한다. 이전 형식의 미전송 편집은 읽기 전용으로 열고 원하는 보관 데이터를 새 사본으로 복구할 수 있다.

자동 제안은 30분 유효한 서버 기록을 검토 후 적용하며, 적용 결과는 7일간 보관해 재시도로 날짜가 두 번 바뀌지 않도록 한다. 업무·이력·되돌리기·적용 기록은 같은 트랜잭션에 저장한다.

## 현재 한계

- 이력 비교 한도는 본문 JSON 8MiB·별도 제목 64KiB·30,000개 노드·구조 깊이 256이다. 반복이 많은 문서는 계산 한도에 도달한 구간 전체를 삭제/추가로 표시할 수 있으며 동일하다고 생략하지 않는다. 한 화면은 최대 60행이고, 변경 없는 부분과 구조 상세는 명시적으로 펼친다.

- 문서 편집에서 포함은 마지막 불러온 저장 원문을 읽기 전용으로 보여준다. 참조 새로고침으로 갱신하며 부모 문서의 이력에 원문 당시 내용이 고정되지 않는다. 표시 한도는 포함 5단계·구조 60단계·확장 노드 합계 최대 4,000개다. 검토본·발행본은 포함 블록의 저장된 참조 이름과 ID를 보여준다. 고급 데이터베이스 매크로와 포함 대상의 본문 버전 고정은 남아 있다.
- 업무 목록과 업무 현황은 한 문서에 합계 30개까지 추가할 수 있다. 목록은 전체 개수와 최대 20개 업무의 현재 상태·담당자를 보여준다. 현황은 현재 업무를 집계하고 그룹과 티켓을 페이지로 나눠 표시한다. 목록과 펼친 그룹 안의 티켓은 프로젝트 업무 순서대로 표시한다. 참조 새로고침으로 최신 정보를 불러오며 문서 버전은 그대로 유지한다. 저장한 보기가 삭제되면 해당 블록의 이름과 오류를 표시한다. 검토·발행본은 저장 당시의 범위와 집계 기준을 보여준다. 날짜별 집계를 고정해서 문서와 연결할 때는 기존 주간 보고서 보관본을 사용한다.
- 검토는 요청당 지정한 팀원 1명을 대상으로 한다. 검토함에는 현재 배정·수정 요청 상태가 표시되며, 이전 발행본은 문서 이력에서 확인한다. 배지는 현재 작업자 기준으로 앱을 열거나 전경으로 돌아올 때, 검토 상태를 바꿀 때와 전경에서 30초마다 조회한다. 본문의 삽입 이미지는 저장한 파일 버전을 참조한다. 첨부를 통째로 삭제하면 검토·발행 문서의 해당 이미지 링크도 사라진다.
- 팀 알림은 상단의 앱 내 알림함에서 조회한다. 업무 댓글은 담당자와 협력자, 문서 댓글은 작성자에게 보낸다. 배지는 전경에서 30초 간격으로 갱신하며 목록은 한 번에 50개를 조회한다. 알림의 업무·문서가 삭제되면 알림 기록은 남고 대상 이동 시 삭제를 안내한다. 구독과 이메일·외부 알림은 남아 있다.
- 공동 편집은 문서별 명시적 활성화 방식이다. 본문은 자동 동기화하고 제목·상태·상위 문서는 별도 저장한다. 원격 커서와 텍스트 선택은 같은 문서·편집 세대에서 지원하는 브라우저끼리 공유하며 포커스를 잃거나 연결을 닫으면 표시를 지운다. 위치 갱신이 30초간 없으면 만료된다. 슬래시 블록 메뉴는 수동 편집에서 제공하며 공동 편집에서는 서식 도구모음을 사용한다. 업데이트 1MiB·문서 JSON 8MiB·누적 Yjs 상태 16MiB 한도가 있다.
- 사용자 정의 필드는 문자·숫자·날짜·단일 선택·다중 선택·확인 여부·팀원·URL을 지원한다. 수식과 조건부 표시는 아직 없다. 필수 여부는 값의 존재를 검사하므로 숫자 0과 확인 여부 false도 유효하다. 사용 중 상태를 다른 상태로 일괄 이관하는 기능은 아직 없다.
- 자동 일정은 FS·SS·FF·SF 관계와 양수·음수 간격을 근무일 단위로 계산한다. 시간대별 예약과 자원 평준화는 남아 있다. 기간 산정에 필요한 날짜나 선행 연결 날짜가 없거나 완료·취소 업무의 고정 일정과 충돌하면 전체 적용을 막는다. 자동 계산은 프로젝트 10,000개 업무, 한 번 적용은 1,000개 변경, 개별 기간은 3,650근무일까지다. 공휴일은 날짜 예외로 직접 입력한다.
- 프로젝트별 담당자 작업량은 최대 180일을 계산한다. 기본 가용 시간은 근무일당 480분이며 조정할 수 있다. 주 담당자에게 작업량을 합산하며 프로젝트별 가용 시간과 비교한다. 프로젝트 간 작업량 화면은 14일씩 조회하고, 서버는 요청당 최대 180일·100개 프로젝트·10,000개 대상 업무·36,000개 팀원과 날짜 조합·100,000개 날짜별 업무 배분을 지원한다. 실제 작업 기록을 사용한 계획 자동 조정은 남아 있다.
- 계획 이동은 계획 한 개와 연결 업무를 대상으로 한다. 이동량은 최대 3,650일이며 업무를 포함할 때 연결 업무 1,000개, 프로젝트 업무 10,000개까지 검토한다. 마일스톤의 달성 여부는 수동으로 관리한다. 마일스톤과 업무의 계획 이동은 각각 다루며, 기준 계획 차이는 종료일의 달력일 차이로 표시한다.
- 휴지통은 업무와 문서에 적용하며 개별 첨부·댓글은 각 관리 화면의 기존 삭제 범위를 따른다. 상위 항목이 휴지통에 있거나 다른 프로젝트로 옮겨진 경우 원래 상위 위치를 복구한 뒤에 자식 항목을 복원한다. 사라진 이정표·관계나 현재 의존성과 충돌하는 연결은 복원 결과에 표시한다. 업무의 기존 상태·유형·필드 설정이 삭제되면 당시 자료를 휴지통에 유지하고 복원을 중단한다. 휴지통에서 영구 삭제하면 보관된 첨부와 본문 이력이 제거된다. 변경·보고·이관 원본의 기록은 각 기능에 남는다.
- 첨부는 파일당 20MiB, 전체 자체 JSON 패키지는 64MiB−1KiB까지다. 초과하면 내용을 누락시키지 않고 오류를 반환한다. 이관한 파일에도 새 버전을 추가할 수 있다. 파일 전체 삭제는 이력에 포함된 모든 바이트를 제거하며 개별 버전 삭제는 아직 없다.
- 자체 JSON 가져오기와 Jira·Confluence 원본 분석·보존·미리보기를 제공한다. 신규 프로젝트 적용은 합성 자료로 검증했다. 기존 프로젝트에 증분 병합하는 기능, 원본 권한 정책 재현, 실제 Jira·Confluence 운영 내보내기 파일 리허설은 남아 있다.
- 자동화 API는 [지원 경로](API.md)에서 읽기/쓰기·프로젝트 범위를 검사한다. 브라우저용 내부 `/api`와 작업자 선택은 로그인 기능이 아니다. 전체 기능의 자동화 API는 아직 없다. 연동·자동화·외부 수신처 관리는 신뢰하는 브라우저용 관리 경로에서 수행한다.
- 새 작업 시간은 분 단위로 직접 입력하며 기간 집계는 최대 92일이다. Jira 원본 이관은 매핑된 작성자의 초 단위를 유지한다. 기준 불명확·미매핑 시간은 원본에 보관한다. 이미 적용한 영수증의 소급 반영과 운영 원본을 사용한 검증은 남아 있다.
- 보고서는 최초 실행과 복원 이후 업무 변경부터 관측한다. 원본 이관은 이관 시점의 업무 상태로 시작한다. 조회 기간은 최대 92일, 한 번의 결과는 최대 5,000개 업무, 저장 목록은 최근 100개다. 문서에는 중요도 순으로 최대 30개 업무를 참조하고 전체 결과는 보관본에서 확인한다.
- 필드 집계는 조회 시점의 현재 값과 선택 업무 최대 10,000개를 대상으로 한다. 다중 선택은 선택지마다 업무 수를 집계하므로 그룹별 업무 수를 더하면 전체 업무 수보다 클 수 있다. 그룹의 업무는 50개씩 조회한다.
- GitLab MR 읽기는 저장소당 최대 1000개, 파이프라인은 최근 50개다. Push·수동 동기화는 업무 상태를 바꾸지 않는다. 이벤트 발생 시각이 없거나 미래이면 상태 자동화를 생략하며, 실제 운영 GitLab 연결·전체 과거 이력 동기화·웹훅 자동 등록은 검증/구현하지 않았다.
- 외부 웹훅은 최대20개 수신처·동시4건·요청10초·자동5회(기본5/10/20/40초 간격)·종료 기록30일·전체 전송50000건 한도다. 최소 한 번 전달 방식이므로 수신 측은 같은 이벤트 ID를 중복 처리해야 한다. 원문·댓글 내용·사용자 정의 값은 보내지 않으며 이력 UI는 최근50건, 관리 API는 최대100건이다.

## 다음 개발 범위

1. 사용자 정의 필드 집계와 포함 문서 버전 고정, 결정 기록과 후속 업무의 연결 확장.
2. 계획·업무 보기와 사용자 정의 필드 보고서의 확장.
3. 여러 팀원의 장시간 동시 편집과 복구를 실제 환경에서 검증.
4. 시간대별 일정과 자원 평준화.
5. 개별 첨부·댓글 복구, 알림 구독·대시보드와 자동화 확장.
6. 실제 Jira·Confluence 내보내기 파일로 이관을 리허설하고 권한·누락·연결·작성자·이력·파일 해시를 검토.
7. 실제 팀 접속 환경과 장시간 동시 사용, 운영 데이터로의 배포·복원 검증.

목표의 전체 범위는 [개발 계획](PLAN.md)에 유지한다. 검사 통과만으로 미구현 범위를 완료 처리하지 않는다.
